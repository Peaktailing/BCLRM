# 双仓分治与合并规程

> 定稿：2026-10-23 · 适用于 `Peaktailing/BCLRM`（主仓）与 `Peaktailing/BCLRM-Lims`（下一代仓）
> 本规程解决一个问题：**同一个功能，到底该提到哪个仓？**

---

## 一、为什么要分两个仓

两个仓不是版本号高低的关系，是**宿主和受众不同**：

| | BCLRM 主仓 | BCLRM-Lims |
|---|---|---|
| 定位 | 试剂库管理系统（当前版本） | 实验数据共享平台（下一代） |
| 宿主 | Streamlit 单页多 Tab | Flask + Jinja + JS 前端 |
| 底座隐喻 | 试剂在校园里的**流转全生命周期** | 实验从**开始到结束**的纵向追踪 |
| 主用户 | 管理员、教师（领用与保管） | 教师、学生（记录与复盘） |
| 当前版本 | v0.9.0 | feature 分支，未发版 |
| 已有内容 | 库存/领用/归还/采购/处置 + 物料交叉点（配方·需求·采购·流转） | 化学语义 C1–C6（chemlib、CAS、管控名录、实验方案、notebook 反应块、教学闭环） |

两者**不冲突**：主仓管「东西在哪、归谁」，Lims 管「东西用在哪、得出什么」。将来会合并，但现在分开跑，因为 Lims 的实验追踪线还没稳。

---

## 二、判断一个改动该进哪个仓

按顺序问三个问题，第一个「是」就定案：

1. **它是实验记录 / 实验过程管理 / 教学闭环吗？**
   → 只进 Lims。（例：实验方案、notebook 反应块、课程用量报告、实验过程步骤）
2. **换一个前端，这段逻辑还要一行不改地存在吗？**
   → 两仓都进。（例：分子式解析、计量引擎、FEFO 拣货、两段管线、路由匹配）
3. **它是对现有基础业务的修正或增强吗？**
   → 两仓都进。（例：借还校验、库存扣减、审批流、DDL 变更、字段常量）

三条都不成立 → 先停下来想清楚，别写。

### 常见的判错

| 直觉 | 实际归属 | 为什么 |
|---|---|---|
| 「配方能算出一节课要多少料」→ 这是教学功能，进 Lims | **两仓** | 计量引擎不知道自己服务谁；教学/科研只是 `BatchScale` 的两种填法 |
| 「调拨是 Lims 的实验流程一部分」 | **两仓** | 调拨是保管权的账面动作，与实验是否被记录无关 |
| 「实验方案引用试剂 → 属于交叉点，进主仓」 | **只进 Lims** | 它是「实验记录」的一种，主仓不做纵向追踪 |
| 「这个页面长得像 Lims 的风格」 | 看逻辑不看皮 | 皮可以不同，逻辑归 domain/capabilities 就两仓共享 |

## 三、文件级归属清单

### 3.1 内核：必须逐字节一致

只有「换宿主也不用改一行」的东西能进这份清单。两仓目录结构不同（主仓 `business/`+`services/`，Lims 单包 `app/`），所以**不要指望整个项目能字面对齐**。

```
domain/                       # 全部：量纲/分子式/物质/计量/配方/需求/保管权/两段管线
capabilities/                 # 全部：metering / supply / circulation
docs/开发基础文档.md
docs/物料交叉点模块.md
docs/双仓分治与合并规程.md
scripts/check_layers.py
scripts/layer_baseline.txt
tests/test_chemical_domain.py        # 只 import domain
tests/test_recipe_metering.py        # 只 import domain + capabilities
tests/test_supply_circulation.py     # 只 import domain + capabilities
tests/test_custody_pipeline.py       # 只 import domain + capabilities
```

四个测试能跨仓直接用，是因为它们**零宿主依赖**（不碰 db、不碰 streamlit）。`test_recipe_business.py` 依赖主仓的 `tests` 基座与 `business/`，属于宿主耦合测试，不进内核；Lims 侧要用得自己改写。

### 3.2 适配层：语义一致，文件不对应

同一个业务规则，两边各用各的技术栈实现。**不能复制文件，只能复制判断**。

| 主仓 BCLRM | BCLRM-Lims | 说明 |
|---|---|---|
| `business/borrow_service.py` | `app/services.py` | 领用单据与审批口令 |
| `business/allocation_service.py` | `app/reagent_workflow.py` | 调拨 / 工作流 |
| `business/manager_service.py` | `app/models.py` + `app/services.py` | 保管人变更 |
| `business/demand_service.py` | `app/reagent_workflow.py` | 需求单（Lims 侧待接） |
| `business/purchase_service.py` | `app/models.py` | 采购（Lims 侧较薄） |
| `business/material_pipeline_service.py` | （待并入） | 两段管线用例，需 Flask 侧适配 |
| `services/` | `app/models.py` | 表结构与 CRUD 各自实现 |
| `db/database.py`（`init_tables`） | `migrations/versions/`（Alembic） | 建表方式不同，列定义要对齐 |
| `utils/field_mapper.py` | 常量散在 `app/models.py` | 字段名不许裸写，两边都要守 |
| `views/13_配方与需求.py` | `app/templates/chem_*.html` | 同一能力的两个前端 |
| `config/settings.py` | `app/__init__.py` 配置区 | 版本号要对齐 |

改适配层的规矩：**先在本仓把规则讲清楚（注释或 docstring），再去另一仓找对应位置改一遍**，然后各跑一次自己的测试。工具用 `python tools/sync_check.py --list-aligned` 打印这张表。

### 3.3 Lims 独有（不要往主仓提）

```
app/chemlib.py                       # Flask 侧化学语义（与 domain/ 重复，见 5.2）
app/chemical_experiments*.py         # 化学实验方案
app/chemical_courses.py              # 课程与教学闭环
app/controlled.py                    # 管控名录业务
app/lab_notebook.py                  # 实验记录
app/reagent_workflow.py              # 试剂工作流
app/templates/chem_*.html
frontend/src/blocks/reaction.js      # notebook 反应块
migrations/versions/0046–0049_*.py   # 化学相关迁移
tests/test_chemical_*.py、test_chemlib、test_controlled、test_reaction_block
```

### 3.4 主仓独有

无。主仓是 Lims 的**子集**（在基础功能维度上）。这是刻意设计的：合并时主仓不需要摘出任何东西，只需要 Lims 吸收。

## 四、日常同步流程

### 4.1 改共享文件时

1. 先改**主仓**（`repos/BCLRM`）。它是共享逻辑的真理源，因为 Streamlit 侧跑起来最快、测试最全（339 个用例）。
2. 主仓测试全绿后，按两类分别处理：
   - **内核**（3.1）：`domain/`、`capabilities/` 整目录覆盖，四个测试与三份文档原样复制；
   - **适配层**（3.2）：**不复制文件**，对着表找到 Lims 侧对应位置，把「判断」重写一遍。
3. 在 Lims 侧跑它的测试（pytest + node 前端检查）。**Flask 侧失败往往不是逻辑错，而是宿主差异**（见 4.3）。
4. 两边都绿，再各提一次 commit。commit message 用同一句话，便于日后 grep 对齐。
5. 收尾跑 `python tools/sync_check.py`，内核必须返回 0。

### 4.2 同步工具

```bash
# 检查两仓内核是否一致（返回码 0 = 一致）
python tools/sync_check.py --repo-a repos/BCLRM --repo-b repos/biomanager

# 只看 domain/ 与 capabilities/
python tools/sync_check.py --only domain,capabilities

# 只列待同步项，省略已一致的
python tools/sync_check.py --plan

# 打印适配层的语义对齐对照表（不比对哈希）
python tools/sync_check.py --list-aligned
```

工具按 3.1 的内核清单逐个比对 sha256，跳过 `__pycache__`、`*.db`、`logs/`、`attachments/`。适配层不在比对范围内——这是设计取舍，不是遗漏：两边文件名都不一样，逐字节比对只会产生噪音。

### 4.3 已知的宿主差异（不是 bug，别硬改）

| 差异 | 主仓 | Lims | 处理 |
|---|---|---|---|
| 页面注册 | `app.py` 里 `st.Page(...)` 列表 | Flask 蓝图 + `NAV_SECTIONS` | 各自维护，只对齐「有哪些页面」 |
| 错误提示 | `st.error(...)` | `flash(...)` + 模板 | 由视图层适配，业务层只抛异常 |
| 会话用户 | `session_state` | `flask.g` / `current_user` | `utils/user_context` 两边各自实现 |
| 迁移 | `db/database.py` 的 `init_tables()` | Alembic `migrations/versions/` | 表结构以 domain 需要为准，两边各自落地 |

### 4.4 禁止事项

- ❌ 在 `domain/` 或 `capabilities/` 里 import `streamlit` / `flask` / `sqlite3` / `db`。这是硬约束，`scripts/check_layers.py` 会拦。
- ❌ 只改一边就宣布完成。共享文件分叉是最难查的故障。
- ❌ 在 Lims 侧「顺手优化」共享文件而不回流主仓。要改就两边同改。
- ❌ 把 Lims 的实验记录相关 import 写进 `business/` 通用服务。

## 五、将来合并时的对账

### 5.1 合并触发条件

同时满足再做：

1. Lims 的实验追踪线（方案 → 执行 → 记录 → 报告）在真实教学场景稳定跑满一个学期；
2. `domain/` + `capabilities/` 在 Lims 侧接入完成，且 `sync_check.py` 连续 4 周返回 0；
3. 主仓的 5 张新表在 Lims 的 Alembic 里有等价迁移（`0050_material_pipeline.py` 之类）。

### 5.2 最大的对账障碍：两套化学语义

现状：

- 主仓 `domain/chemistry.py`：`MolecularFormula`、`molar_mass`、`CasNumber`（带校验位）
- Lims `app/chemlib.py`：独立实现，服务于 Flask 侧实验方案与 notebook

**合并时以 `domain/` 为唯一真理源**，`app/chemlib.py` 降级为适配层（函数签名保持不变，内部转调 `domain.chemistry`），而不是反过来。理由：`domain/` 有 339 个用例护着，且零框架依赖，能被两边同时用。

对账步骤：

1. 列出 `chemlib` 的公开函数，逐个在 `domain/chemistry.py` 找对应实现；
2. 有对应 → 改 `chemlib` 内部转调，跑 Lims 测试确认行为不变；
3. 无对应 → 判断是「Lims 独有」还是「domain 缺」；后者补到 `domain/`，前者留在适配层；
4. 全部转调后，`chemlib.py` 应只剩薄薄一层转发，可考虑删除。

### 5.3 数据表对账

主仓新增 5 表（`recipe`、`recipe_component`、`requirement_sheet`、`requirement_line`、`custodian_route`）是 SQLite 直建表，Lims 是 Alembic。合并时**以 domain 需要的列定义为准**，两边各自落地：

```bash
# 生成主仓侧的列定义
python -c "import sqlite3;[print(r) for r in sqlite3.connect('db/main.db').execute('pragma table_info(recipe)')]"
# 在 Lims 侧写 Alembic 时逐列对齐，注意 SQLite 的 ALTER 限制（加列可以，改类型要重建表）
```

### 5.4 合并后仓库形态（建议）

不合并成单仓，而是 Lims 作为**主仓的上层分发**：

```
BCLRM-Lims/
├── core/          ← 从主仓同步的 domain/ capabilities/ business/ services/
├── lims/          ← 实验记录与过程管理（Flask 应用）
└── ...
```

主仓继续独立维护 Streamlit 版本，Lims 拉取 `core/` 时用 `sync_check.py` 对账。这样两边都能独立发版，不必为了一个 bug 联动发两个包。
