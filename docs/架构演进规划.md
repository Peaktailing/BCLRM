> 权限校验中台化。均为规划性内容，不随版本迭代实施，触发条件满足时再启动。
>
> 最后更新：2026-10-12（v0.8.12）

## 一、服务端权限守卫：现状与中台化演进

### 1.1 当前方案（已实施，v0.8.12）

已实现「不在每笔业务里加代码」的统一拦截：

```
components/auth.py          登录/页面刷新 → utils/user_context.py（ContextVar 写入当前用户）
        ↓
utils/permission_guard.py   集中规则：ADMIN_WRITE_TABLES / ADMIN_WRITE_FIELDS
        ↓
db/base_service.py          create / update / delete / update_by_field / delete_by_field
                            执行 SQL 前统一调用 enforce_write()
```

- **规则集中在一处**：新增敏感表或敏感字段只需在 `permission_guard.py` 加一行，无需改任何业务代码
- **放行策略**：无上下文（脚本/测试/初始化）放行；管理员及以上全放行；其余按规则校验
- **当前规则**：`person` / `controlled_list` 整表写保护；`approval_status` 字段级写保护
- **与页面级权限互补**：页面管按钮可见性，服务端守卫是数据库写入前的最后拦截

### 1.2 中台化演进（未来方向）

若系统拆分为独立中台服务（或暴露 API 层），本方案可平滑迁移：

| 现状（单体 Streamlit） | 中台化后 |
|------------------------|----------|
| `ContextVar` 存当前用户 | 请求上下文中间件（FastAPI dependency / JWT claims） |
| `permission_guard.py` 规则表 | 鉴权中间件的策略配置（可迁移为声明式规则） |
| `BaseService` 内联拦截 | 统一 Repository/Service 网关拦截，规则复用 |
| 页面 `require_auth()` 注入 | 网关/中间件统一注入身份 |

**迁移原则**：规则文件（`permission_guard.py`）与上下文接口（`user_context.py`）保持零 Streamlit 依赖，
中台化时只替换「上下文注入端」，规则与拦截点不变。

## 二、FastAPI 后端层（API 网关）

### 背景
`docs/API接口规范.md` 已定义 35+ RESTful 端点（登录/库存/领用/归还/审批等），
供 React 前端（login-frontend）或其他系统对接。**当前零实现**——系统为 Streamlit 一体化架构。

### 启动触发条件（满足其一）
- 需要独立前端（React/小程序）正式上线对接
- 需要第三方系统（教务/采购平台）调用试剂库数据
- 需要将本系统拆为多端共享的中台服务

### 实施范围（预估）
```
api/                      新增：FastAPI 路由层
  ├── schemas.py          Pydantic 请求/响应模型（对齐 API接口规范.md）
  ├── auth.py             JWT 签发/校验 + 依赖注入
  └── routers/            按规范分组：auth / inventory / borrow / purchase ...
```
- **业务逻辑零重复**：路由层只做「参数校验 + 身份注入 + 调 business 层 + 转响应」
- 鉴权复用 `permission_guard.py` 规则（见第一节迁移表）
- `requirements` 增加 `fastapi` + `uvicorn`（uvicorn 已装未用）

### 分层约束
路由（api）→ 业务（business）→ 服务（service）→ 模型（db），与现有页面层同级，
**禁止** api 层直连 db 层。

## 三、登录失败锁定持久化

### 背景
当前登录失败锁定基于 `st.session_state`（`components/auth.py`）：
- 连续 5 次失败锁定 15 分钟
- **Streamlit 重启即清零**，可被重启绕过；且按浏览器会话隔离，不跨会话累计

### 实施方案
1. 新增表 `login_attempt_log`（主库）：
   ```sql
   CREATE TABLE IF NOT EXISTS login_attempt_log (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       user_name TEXT NOT NULL,
       ip TEXT,
       success INTEGER,
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   );
   ```
2. 登录失败时落库累计（按 user_name 统计最近 15 分钟内失败次数，≥5 锁定）
3. 登录成功时清空该用户失败记录
4. 锁定状态查询从数据库读取（`person_service` 或新 `login_attempt_service`）
5. 可选增强：记录 IP，支持按 IP 维度限流

### 工作量与优先级
- 约 30-50 行 + 一张表；低风险
- **优先级低**：当前威胁模型下（内网系统、无公开登录端点）收益有限
- **实施时机**：对外开放 Web 访问或启用 FastAPI 登录端点时一并做（与第二节合并实施）

## 四、归档冷库数据搬运（四库分离的后续）

### 背景
v0.8.12 已完成四库分离的**基础设施**：启动时自动创建并初始化
`operation_log.db`（审计日志，已切写）、`attach_cold.db`（附件索引，已启用）、
`archive_cold.db`（归档冷库，已建 `archive_batch` 元数据表）。

**未实现**：把主库过期数据搬运到 archive_cold.db 的实际归档逻辑。

### 规划
- 触发条件：主库行数超过 `MAIN_DB_MAX_ROWS`（当前 100000）或数据超过 `ARCHIVE_AFTER_YEARS`（3 年）
- 归档对象：`borrow_order` / `borrow_order_item` 等高频流水表的历史记录
- 流程：事务内复制到冷库同名表 → 主库删除 → `archive_batch` 记录批次 → 查询入口按需 UNION 冷库
- 当前主库数据量（1290 瓶、131 测试级数据）远未触发，**无实施紧迫性**
