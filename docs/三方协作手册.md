# 三方协作手册（Trae · Qoder · CodeBuddy）

> **目的**：三个团队/助手并行维护同一仓库（`Peaktailing/BCLRM`），做到**并行不撞车、版本不打架、日志不丢失、出问题能溯源**。
>
> **配套文档**（本手册不重复其内容）：
> - `docs/开发基础文档.md` —— 架构、分层、编码规范的唯一权威依据
> - `docs/业务实现说明.md` —— 业务规则与单据口径的裁决依据（**现行**）
> - `docs/代码关联地图.md` —— 改一块代码要连带改哪些文件、表、测试（动手前查）
> - `docs/领用关系与状态机设计.md` —— 为什么这么设计（拍板记录与切片状态）
> - `docs/更新日志.md` —— 版本与变更事实源
> - `docs/业务流转逻辑.md` —— **历史文档**（最后核对约 v0.8.8），不再作为口径依据
>
> **适用对象**：任何要在本仓库写代码的团队或 AI 助手。每次开工前通读本手册。

---

## 一、三条铁律

1. **动手前先同步**：`git fetch` + `git status` + `git log`，别人可能在你读代码期间已经提交。
2. **别人未提交的文件不碰**：工作区里不是你的改动，动手前先问归属。
3. **提交小而原子**：一个提交一个主题，message 写清动了哪些区间，方便对方 rebase。

---

## 二、开工 / 收工检查单

### 开工（每次会话开始，30 秒）

```bash
git fetch origin
git status --short      # 有未提交文件 → 先确认归属，加入自己的禁改清单
git log --oneline -6    # 看其他方最近提交了什么
.venv/bin/python -m unittest discover -s tests -t . -q   # 记录基线测试数
```

### 收工

- `git status` 干净，或明确报备"在飞"内容与预计完成时间；
- 已提交的 **push 到 origin/main**（小步快跑，不积压）；
- `docs/更新日志.md` 已同步（见第五节）。

---

## 三、"在飞"文件协议

| 情况 | 处理 |
|---|---|
| 发现工作区有**别人未提交**的改动 | 该文件加入本人禁改清单；确有紧急需要 → 先联系对方，不静默覆盖 |
| 文件已合并、三方共同编辑 | 可以改；同文件同区域（±20 行）错峰，或在提交信息里说明动机 |
| 该文件最近 3 个提交有对方署名 | 动手前在对齐渠道发一句"我要动 X 的 Y 区间，理由 Z" |
| 测试文件 | 各自新增 `tests/test_*.py`；**不删改对方的测试文件**，除非对方已交付并明确解锁 |

---

## 四、提交规范（对开发基础文档 4.4 的补充）

```text
<类型>: <摘要>（版本号）

- 改动：<文件:行号区间>（做了什么）
- 未触碰：<对方可能关心的区间>（明确让出，便于 rebase）
- 测试：全量 N 通过（+新增 M）
```

- 类型沿用：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`；
- **一个提交只做一个主题**，不把无关改动混入；
- 提交前全量测试必须绿；不为本批引入的既有失败，记录后放行并在提交信息注明；
- **不要在 commit message 里发明版本号**（见下一节）。

---

## 五、版本号与更新日志（历史上最容易打架的地方）

**唯一事实源**：`docs/更新日志.md` 的最高版本节 + `config/settings.py` 的 `VERSION`，二者**必须同批提交、保持一致**。

规则：

1. 升版本前先 `git fetch`，看 changelog 当前最高版本，**只升一个 minor**；
2. **版本被对方占用时**：不抢占、不改写 git 历史；把自己批次的条目**合并进对方已占用的版本节**，以 changelog 为准；
3. commit message 尾标的版本号只是备注，与 changelog 不一致时**以 changelog 为准，不回写历史**；
4. 升版本的一方负责在对齐渠道通报，其他方 pull 后以 changelog 对齐。

## 六、热点文件地图（按历史活跃度）

| 文件 / 区域 | 常见改动方 | 注意事项 |
|---|---|---|
| `db/database.py`（建表迁移、`transaction()`） | 多方 | 动 `init_tables` / 事务语义前先广播；迁移必须幂等 |
| `db/base_service.py` | 多方 | 新增方法保持向后兼容；守卫调用点别漏 |
| `utils/permission_guard.py` | 守卫维护方 | 权限规则**只集中在这一个文件**加，不散落到业务层 |
| `business/work_order_service.py` 审批区（approve/reject/withdraw、双签） | 多方 | 改动必标注行号区间；状态跃迁用 `update_where` 原子抢占 |
| `business/assignment_service.py` + `services/core/issue_queue_service.py` | 归属/队列维护方 | 权限口径只在 `domain/assignment.py`；SQL 一律 `custodian_key IN (...)` 且兼容空值 |
| `business/transfer_service.py` + `services/core/transfer_order_service.py` | 调配维护方 | 事务在 services（business 不许 import db）；一瓶都没转成必须整单回滚 |
| `app.py` 导航 | 多方 | 新页面必须同时加 `st.Page`，否则有文件没入口；管理员页/超管页分别注册 |
| `business/purchase_service.py`、`business/manager_service.py` | 采购 / 管理权维护方 | 批量操作注意事务边界 |
| `components/auth.py` | 多方 | 登录 / 超时 / 登出三处口径要保持一致 |
| `views/3_领用归还.py` | 多方 | 单文件多 tab，改动标注区间 |
| `docs/更新日志.md` | 所有人 | **只追加**，不改写历史条目 |
| `db/*.db`、`attachments/`、`logs/` | — | 已在 `.gitignore`，**任何情况下不提交** |

## 七、测试与质量门禁

- 提交前：`.venv/bin/python -m unittest discover -s tests -t . -q` **全量通过**；
- **测试数是三方对账信号**：changelog 与提交信息写明"全量 N 通过"；
- **不写真实库**：测试隔离由 `tests/__init__.py` + `conftest.py` 统一负责，新增测试不得绕过；
- 发现**对方引入的回归**：记录复现步骤 → 通报 → 不越权修对方在飞文件；对方交付后按"审查修复"批次统一处理（参考 v0.8.14 的两次审查修复）。

## 八、沟通协议

| 时机 | 动作 |
|---|---|
| 要动热点文件 / 表结构 / 守卫规则 | 动手前发"我要动 X 的 Y 区间，理由 Z" |
| 完成一批 | 发提交清单：sha + 摘要 + 测试数 |
| 发现疑似对方 bug | 先记录复现步骤并通报，**不静默修改** |
| 升版本 / 发版 | 升版本一方负责通报，其他方以 changelog 对齐 |
| 业务口径争执 | 以 `docs/业务实现说明.md` + `docs/领用关系与状态机设计.md` 的拍板记录为裁决依据；文档没写 → 问用户（项目 owner） |

---

## 九、冲突解决流程

1. **git 合并冲突**：`git fetch` → `rebase` → 逐 hunk 确认归属 → **保留双方的注释与逻辑**，不整块覆盖；
2. **版本撞车**：以 changelog 最高版本为准，低的一方合并条目，不回写历史；
3. **同一功能两套实现**：双方贴代码位置 + 设计意图，由最近改动方说明，合并为一套；
4. **拿不准**：问用户，不在代码里留互相矛盾的 TODO。

## 十、历史踩坑记录（真实案例，引以为鉴）

| 事件 | 处理方式 | 教训 |
|---|---|---|
| `manual_map` 未定义导致 3 个测试红 | 归属方修复 | 测试红先排查是否别人在飞，别抢修 |
| v0.8.14 版本号被一方占用，另一方已按 0.8.15 归档 | changelog 合并回 v0.8.14 | 版本以 changelog 为唯一事实源 |
| 部分 commit message 版本尾标与 changelog 不一致 | 不改写 git 历史 | message 不发明版本号 |
| 权限守卫误伤教师提交管控课程单 | 归属方改为"按写入值放行" | 守卫规则改动必须跑全量测试 |

| 批量指派嵌套事务"失败不回滚" | `db.transaction()` 嵌套段改 SAVEPOINT | 事务语义变更必须配测试 |
| 审批/撤回 check-then-act 并发窗口 | 新增 `BaseService.update_where` 原子抢占 | 状态跃迁一律条件更新 |

## 十一、一页速查（贴墙版）

```text
开工：fetch → status → log → 测试基线
动手：不碰在飞文件；热点区间先打招呼
提交：小步原子，message 写区间；全量测试绿才提交
版本：changelog 是老大；被占了就合并，不抢不改历史
沟通：完成发清单；bug 先通报；口径争执问用户
```
