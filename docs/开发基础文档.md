二、整体架构与分层职责
项目采用六层架构，严格遵循「单一职责原则」，各层之间只能向下调用，不能反向依赖。数据库采用四库分离架构（详见第八节），主库16张表支撑全部业务。
┌─────────────────────────────────┐
│ 页面层 (pages/)                 │  只负责UI渲染和用户交互，无业务逻辑
├─────────────────────────────────┤
│ 业务逻辑层 (business/)          │  核心！所有业务规则、数据校验、流程控制
├─────────────────────────────────┤
│ ORM 服务层 (services/)          │  封装数据库操作，单表标准化CRUD
├─────────────────────────────────┤
│ 数据库访问层 (db/)              │  数据库连接管理、通用CRUD基类
├─────────────────────────────────┤
│ 数据模型层 (models/)            │  数据表对应的 dataclass 实体类
├─────────────────────────────────┤
│ 配置与工具层 (config/ + utils/) │  全局配置、通用工具函数
└─────────────────────────────────┘
各层职责完整说明
1. 页面层：只写 Streamlit 组件（输入框、按钮、表格、弹窗、筛选控件），仅调用业务层类方法获取数据并渲染展示。永久禁止直接操作数据库、编写业务校验逻辑、拼接SQL语句。
2. 业务逻辑层：系统核心层，全部业务规则统一在此实现，例如领用数量校验、管控化学品审批、库存自动更新、多表关联统计等；与前端UI完全解耦，仅依赖ORM服务层完成数据读写，便于独立单元测试。所有业务方法统一返回 ServiceResult 对象。
3. ORM 服务层：基于 db/base_service.py 继承扩展，每张数据表对应独立 Service 类，仅负责单表增删改查、基础查询，不承载任何业务判断、流程规则。
4. 数据库访问层：封装 SQLite 数据库连接管理、表结构初始化、基础 CRUD 方法（execute_query、execute_insert、execute_update 等），提供 BaseService 通用 CRUD 基类供 services 层继承。
5. 数据模型层：使用 Python dataclass 定义数据实体类，每个类与 SQLite 数据表一一对应，字段、数据类型在类内统一声明；全项目数据流转统一使用实体对象传递，禁止裸字典传输数据。
6. 配置与工具层：全局数据库连接参数、系统常量、编号生成、日期转换、统一异常处理等通用能力统一存放，所有硬编码常量、字段标识全部移入此处，业务代码禁止手写固定字符串、数字。
全项目统一编码范式（强制规范）
项目所有核心代码优先使用面向对象Class开发，严格限制面向过程脚本式写法，分层强制约束如下：
1. models层：全部为 dataclass 实体类，数据表结构与类定义强绑定，禁止零散字典、元组承载表数据；
2. services、business层：全部能力封装为独立Class，关联属性、复用读写/校验逻辑收拢为类内方法，不批量创建无归属全局函数、全局变量；
3. utils、components通用层：通用工具、复用UI组件统一封装为工具类、组件类，避免堆砌零散独立过程函数；
4. 例外规则：仅一次性简易运行脚本可采用面向过程写法，models/services/business核心业务代码一律禁止纯面向过程实现；
5. 数据库编码约束：通过 db/ 层统一进行数据库读写，禁止在页面层和业务层直接拼接、手写原始 SQL 字符串执行查询/修改操作。

4.2 代码规范
1. 缩进：使用4个空格，禁止使用Tab
2. 注释：
- 所有功能块必须先写注释：类、函数、方法必须先写文档字符串（docstring），说明功能、参数、返回值
- 复杂业务逻辑必须加行内注释
- 临时注释必须标注日期和作者
3. 错误处理：
- 所有数据库ORM请求必须加异常捕获
- 业务逻辑错误必须返回明确的提示信息
- 禁止使用裸except，必须捕获具体异常
4. 硬编码：
- 所有字符串常量、数字常量必须定义在config/settings.py中
- 所有字段名必须定义在utils/field_mapper.py中，禁止直接写字符串
5. 文档更新：
- 每次更新代码必须同步更新开发文档（docs/开发基础文档.md）和对应的使用说明（docs/用户使用手册.md）
6. 编码范式强制要求：
项目所有核心层（models / services / business / components）必须采用面向对象编程，使用类封装数据与行为；禁止将业务逻辑、数据库操作、数据实体拆分为大量独立全局函数；数据传输统一使用 ORM 实体对象，不裸传 dict；仅 utils 内一次性简单辅助函数可使用面向过程写法，业务流程、数据库交互全部封装类；禁止在页面层编写大量过程式判断、循环、数据计算，复杂逻辑封装至 business 类内调用。
4.3 数据操作规范
1. 管控化学品数据表：只能读取，不能修改。该表为系统参考数据，用于判断试剂是否为管控试剂，测试后必须删除对应的测试数据。
2. 试剂瓶信息表：核心业务表，所有操作需经过业务逻辑层校验。
3. 领用/归还记录表：自动生成，禁止手动修改。
4.4 Git 提交规范
所有代码开发完成、审查通过后，由主智能体统一整理、合并、提交代码，严格遵循以下提交格式：
<类型>: <描述>
类型说明：
- feat: 新增功能
- fix: 修复bug
- docs: 文档更新
- style: 代码格式调整（不影响功能）
- refactor: 代码重构
- test: 测试相关
- chore: 构建工具或依赖更新
示例：
feat: 实现试剂入库核心业务逻辑
fix: 修复领用数量超过剩余量的bug
docs: 更新开发基础文档，适配SQLite架构
4.5 页面层与业务层 职责分离规范（永久强制）
4.5.1 页面层（pages/） 绝对职责
1. 只负责 UI 渲染：输入框、下拉框、单选框、复选框、按钮、表格、表单布局
2. 只负责数据展示：列表、详情、状态、提示语（成功/失败/警告）
3. 只负责调用 business/ 层的类方法，不编写任何业务逻辑
4. 禁止编写：编号生成、数据校验、状态判断、附件处理、数据库直接调用
5. 下拉选择框数据：必须从业务层动态获取，禁止硬编码
6. 表单提交：仅收集参数 → 调用业务类方法 → 展示结果
4.5.2 业务层（business/） 绝对职责
1. 所有业务规则唯一实现地：编号生成、数据校验、关联匹配、状态计算
2. 所有数据处理：附件解析、格式转换、模糊查询、自动匹配
3. 统一调用 services/ 层 ORM 方法完成数据库 CRUD
4. 统一返回 ServiceResult 对象（定义在 utils/error_handler.py），包含：
   - success: bool — 是否成功
   - message: str — 提示信息
   - data: Any — 返回数据
   - is_success() / is_failure() — 便捷判断方法
5. 禁止包含任何 Streamlit 前端代码（st.xxx 语法）
6. 禁止直接操作页面，只处理数据与逻辑
7. 强制面向对象约束：所有业务能力封装为业务 Service 类，相关操作作为类方法，禁止分散全局过程函数；业务所需数据统一传入 ORM 实体对象，不裸字典交互。
4.5.3 关联表下拉框开发规范
1. 试剂类型 → 从 reagent_type 表获取
2. 存储要求 → 从 storage_requirement 表获取
3. 供应商 → 从 supplier 表获取
4. 存储位置 → 从 storage_location 表获取
5. 人员 → 从 person 表获取
6. 所有下拉框必须动态加载，禁止手写固定选项；读取数据后统一转换为 ORM model 实体对象，页面仅读取对象属性展示，避免过程式字典取值。
4.5.4 搜索功能规范
1. 关键字搜索默认使用模糊匹配
2. 多字段搜索：同时匹配主名称 + 显示名称
3. 搜索不区分大小写
4. 搜索逻辑必须写在 business/ 层，页面只传关键词
4.5.5 附件上传规范
1. MSDS 等附件：页面只负责上传文件
2. 业务层负责处理文件、存储路径/内容
3. 禁止在页面层处理文件逻辑

5.1 页面打不开
1. 检查Streamlit是否启动：看终端是否有You can now view your Streamlit app提示
2. 检查端口是否被占用，若被占用，更换端口重启服务
3. 检查服务器防火墙，放行对应端口
4. 检查访问地址，使用服务器真实IP访问
5.2 页面能打开，但没有数据
1. 检查SQLite数据库文件是否存在、是否损坏
2. 检查数据库初始化是否完成，数据表是否正常创建
3. 检查config/settings.py数据库配置是否正确
4. 查看终端日志，定位ORM查询异常、数据为空等问题
5.3 操作失败（入库/领用/归还没反应）
1. 检查表单必填字段是否完整填写
2. 检查字段传入类型是否与ORM实体类类型匹配
3. 核对业务层校验规则（如领用数量不大于库存数量）
4. 查看终端报错，定位对应业务类、ORM服务类异常
5.4 代码修改后页面没变化
1. 刷新浏览器页面（F5）
2. 重启Streamlit服务
3. 清除Streamlit本地缓存

5.5 错误日志管理
1. 系统运行时产生的所有错误、警告信息统一记录在 `logs/error.log` 文件中
2. 错误日志格式：`时间 | 级别 | 模块 | 错误信息 | 文件位置 | 解决方案`
3. 常见错误级别：
   - ERROR：严重错误，影响系统运行
   - WARNING：警告信息，需要关注但不影响运行
4. 遇到问题时，优先查看 error.log 文件定位问题原因
5. 修复问题后，需在 error.log 中补充解决方案说明

八、数据库四库分离架构

8.1 架构概述

系统采用四库分离架构，将不同访问频率、不同用途的数据物理隔离到四个独立的 SQLite 数据库中，实现高性能、高可维护性的数据管理。

四个数据库：
| 数据库 | 文件名 | 用途 | 访问频率 | 数据特征 |
|--------|--------|------|----------|----------|
| 主业务库 | `main.db` | 核心业务数据 | 高频在线 | 16张业务表，必须在线 |
| 业务归档冷库 | `archive_cold.db` | 过期数据归档 | 极低 | 3张归档表，按需查询 |
| 附件索引库 | `attach_cold.db` | 附件文件索引 | 低 | 1张附件索引表，仅下载时访问 |
| 审计日志库 | `operation_log.db` | 操作审计日志 | 中等 | 1张日志表，纯追加写入 |

8.2 数据库职责划分

8.2.1 主业务库 (main.db)
- 存储全部 16 张业务表（person、reagent_bottle、borrow_record、return_record、chemical_info、controlled_list、supplier、storage_location、storage_requirement、reagent_type、manufacturer、consumable、experiment_project、experiment_reagent_usage、reservation_order、purchase_order）
- 所有增删改查操作的主目标库
- WAL 模式，同步级别 NORMAL
- 数据行数监控：超过 100,000 行时触发归档提醒

8.2.2 业务归档冷库 (archive_cold.db)
- 存储超过 3 年的过期试剂瓶数据及其关联的领用、归还记录
- 表结构：`archived_reagent_bottle`、`archived_borrow_record`、`archived_return_record`
- 归档时自动添加 `archived_date` 和 `archive_reason` 字段
- 非关键业务库，初始化失败不影响主业务流程

8.2.3 附件索引库 (attach_cold.db)
- 存储所有文件附件（MSDS、审批文件等）的索引信息
- 表结构：`attachment`（字段：file_name、original_name、file_path、file_size、file_type、related_table、related_id）
- 支持按关联表名和关联ID快速查找附件
- 实际文件存储在 `attachments/` 目录

8.2.4 审计日志库 (operation_log.db)
- 记录所有关键操作的审计日志
- 表结构：`operation_log`（字段：log_type、user_name、action、target_table、target_id、detail、ip_address）
- 纯追加写入，不修改、不删除
- 同步级别设为 OFF（日志库可接受少量丢失）
- 日志保留期：730 天（2 年），超期自动清理

8.3 WAL 日志目录配置

每个数据库的 WAL 日志独立存储，避免与数据库文件混放，便于备份和清理：

| 数据库 | WAL 目录 | 说明 |
|--------|----------|------|
| `main.db` | `db_wal/main/` | 主库 WAL 日志 |
| `archive_cold.db` | `db_wal/archive/` | 归档库 WAL 日志 |
| `attach_cold.db` | `db_wal/attach/` | 附件库 WAL 日志 |
| `operation_log.db` | `db_wal/logdb/` | 日志库 WAL 日志 |

WAL 配置参数：
- `journal_mode = WAL`：启用预写日志
- `wal_autocheckpoint = 1000`：每 1000 页自动检查点
- 主库 synchronous = NORMAL，日志库同步 = OFF

8.4 备份策略

- 主库 (main.db)：每日全量备份 + 持续 WAL 增量备份
- 归档库 (archive_cold.db)：每周全量备份
- 附件库 (attach_cold.db)：每周全量备份 + 附件文件同步备份
- 日志库 (operation_log.db)：备份策略可适当放宽（日志库可接受丢失）

备份命令参考：
```bash
# 备份主库
sqlite3 db/main.db ".backup backup/main_$(date +%Y%m%d).db"

# 备份归档库
sqlite3 db/archive_cold.db ".backup backup/archive_$(date +%Y%m%d).db"
```

8.5 容错设计

- 主库（main.db）初始化失败 → 系统启动失败（必须在线）
- 归档库、附件库、日志库初始化失败 → 记录警告日志，不阻塞主流程
- 数据库连接管理：MultiDatabaseManager 单例模式统一管理四个数据库连接
- 冷库定期 VACUUM 整理碎片（归档库、附件库、日志库）
- 日志脱敏：SQL 参数在写入日志前进行脱敏处理，仅记录参数数量和类型，不记录实际值

8.6 相关配置文件

数据库配置集中在 `config/settings.py`：
```python
DB_MAIN_PATH = "db/main.db"
DB_ARCHIVE_PATH = "db/archive_cold.db"
DB_ATTACH_PATH = "db/attach_cold.db"
DB_LOG_PATH = "db/operation_log.db"

WAL_DIR_MAIN = "db_wal/main"
WAL_DIR_ARCHIVE = "db_wal/archive"
WAL_DIR_ATTACH = "db_wal/attach"
WAL_DIR_LOG = "db_wal/logdb"

LOG_RETENTION_DAYS = 730  # 2年
MAIN_DB_MAX_ROWS = 100000  # 主库数据行数上限
ARCHIVE_AFTER_YEARS = 3    # 过期数据归档年限
```

数据库连接管理代码在 `db/multi_database.py`（MultiDatabaseManager 类）。

十、预定单管理

10.1 功能概述

预定单管理模块用于教师/实验员在学期开始前预定所需试剂，便于统一采购和库存准备。

10.2 数据表结构

**reservation_order（预定单表）**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER | 自增主键 |
| `order_number` | TEXT | 预定单编号（UNIQUE，格式：RES + YYYYMMDD + NNNN） |
| `semester` | TEXT | 学期（如：2025-2026-2） |
| `reagent_name` | TEXT | 试剂名称（必填） |
| `cas_number` | TEXT | CAS号 |
| `quantity` | REAL | 预定数量 |
| `unit` | TEXT | 单位（默认：g） |
| `applicant` | TEXT | 申请人 |
| `status` | TEXT | 状态（pending / approved / rejected / fulfilled） |
| `created_at` | TIMESTAMP | 创建时间 |
| `updated_at` | TIMESTAMP | 更新时间 |

10.3 业务规则

- 审批不通过：`pending` → `rejected`
- 支持按学期、申请人、状态进行筛选
- 预定单审批通过后，可创建对应的采购单

10.4 相关API接口

- `DELETE /api/reservations/{id}` — 删除预定单

13.1 接口文档

前后端 API 接口规范详见 `docs/API接口规范.md`，该文档定义了 Streamlit Python 后端与 React 前端（login-frontend）之间的 RESTful API 契约。

13.2 接口覆盖范围

API 接口规范覆盖以下功能模块：

| 模块 | 接口数量 | 说明 |
|------|----------|------|

- 分页参数：`page`（默认 1）、`page_size`（默认 100，最大 500）
- 错误码标准化：`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`CONFLICT`、`BUSINESS_ERROR`、`INSUFFICIENT_STOCK` 等
- 管控化学品接口仅返回提示，不阻塞操作（审批功能预留）

13.4 开发说明

- 后端优先实现 Streamlit 原生页面，API 接口作为 React 前端对接的并行通道
- 前后端共享同一套 `business/` + `services/` 业务逻辑层
- API 层仅做参数解析、认证校验、调用业务层、返回 JSON 响应
- 禁止在 API 层编写业务逻辑或直接操作数据库
