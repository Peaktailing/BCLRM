# 物料交叉点模块说明（v0.8.16）

> 适用范围：**BCLRM 主仓（当前版本）**。
> 本模块只覆盖「试剂怎么算、怎么买、怎么调」——配方 → 需求 → 采购 → 流转。
> 不包含实验记录、实验过程管理、教学闭环追踪，那些属于下一代版本（BCLRM-Lims），见文末边界说明。

---

## 一、这个模块解决什么问题

原有系统回答的是「库里有什么、谁领了、还了没有」。它回答不了三个问题：

1. **一节实验课到底要多少试剂？** 库存上的 500 mL 乙醇，够不够 40 人做一次蒸馏？
2. **要的东西库里没有，该买几瓶？** 不是买 500 g，是买「500 g 一桶的，两桶」。
3. **我要的东西在别人名下，怎么调过来？** 而且调完账面不能乱。

这三问对应四个子能力，共用一套物质与计量语义：

| 子能力 | 输入 | 输出 | 所在层 |
|---|---|---|---|
| 配方 | 实验步骤里的「加 5 g 无水硫酸铜」 | 结构化组分清单 | `domain/recipe.py` |
| 计量 | 配方 + 实验规模（人数/批次） | 需求单（每项多少） | `capabilities/metering/` |
| 采购 | 需求单 − 现有库存 | 拆包采购计划 | `capabilities/supply/procurement.py` |
| 流转 | 需求单 + 保管账 | 发放单 + 调拨提案 | `capabilities/circulation/` |

## 二、物质与计量：先解决「同名不同物」

配方里写的是「乙醇」，库存里存的是 `64-17-5`，目录里可能还有「无水乙醇」「95% 乙醇」。模块的第一步是把名字归一到物质：

- `SubstanceRef.of(name, cas, formula)` 生成物质键，优先级 **CAS > 分子式（Hill 式）> 规范化名称**。
- CAS 号按 `^\d{2,7}-\d{2}-\d$` 校验，并校验校验位。
- 分子式解析支持结晶水写法 `CuSO4·5H2O`，摩尔质量按元素表累加。

计量策略共六种，配方组分行声明用哪一种：

| 策略 | 场景 | 例 |
|---|---|---|
| `fixed` | 固定量 | 催化剂 0.5 g |
| `per_person` | 人均 | 每人 5 g 硫酸铜 |
| `per_batch` | 每批 | 每批次 200 mL 蒸馏水 |
| `equivalents` | 当量（需基准物） | 1.2 当量乙酸酐（相对 0.5 mol 水杨酸） |
| `ratio` | 配比（需基准物） | 展开剂 石油醚:乙酸乙酯 = 3:1 |
| `concentration` | 目标浓度（需容器体积） | 配 0.1 mol/L 溶液 |

依赖型策略（当量/配比/浓度）在引擎里走**第二轮**计算，因为它们的答案依赖第一轮算出来的基准量。缺物性（如液体密度）时不是猜，而是抛 `MeteringError` 并带上行号。

## 三、两段管线：这个模块的核心

这是本模块唯一需要理解透的概念。

**管理员本身就是试剂的临时所有人。** 教师缺东西，找的是「这门课对应的管理员」；管理员发现自己名下不够，才去找其他管理员。所以一次申领在业务上是两段，不是一张单据的两个状态：

```
教师  ──①要料──▶  课程管理员  ──②若不够──▶  其他管理员
      第一段：实物出库                    第二段：账面平账
      保管权不变                          保管权流转，瓶子不动
```

### 第一段：受理（`capabilities/circulation/stage1.py`）

- 输入：需求单 + 受理人（课程/班级路由查到的那位管理员）。
- 行为：只在这位管理员**名下**的批次里按 FEFO 拣货，实物出库。
- 输出：`Acceptance`，含 `issued`（已发）与 `shortfalls`（缺口）。
- **不变量**：Σ已发 + Σ缺口 ≡ 原始需求，一项都不能凭空消失。
- **类型约束**：`IssueLine` 结构上**没有** `to_custodian` 字段。第一段永远不换保管人，这一点由类型保证，不靠注释和自觉。

### 第二段：平账（`capabilities/circulation/stage2.py`）

- 输入：只能是 `Acceptance`（`TransferBroker.broker()` 的签名就限定死了）。
- 行为：拿 `Acceptance.shortfall_sheet()` 生成的缺口单，向其他管理员找货，产出 `TransferProposal`。
- **不变量**：永远排除受理人自己（`beneficiary` 硬性排除），否则会自己调给自己。
- 找不到任何来源时不编造，返回空提案，由业务层转采购。

### 收口：逐项兑付（`business/requirement_issue_service.py`）

第一段算出「发哪几瓶、各多少」只是纸面结论。**料真的从架上扣下来、记在一张领用单上，这条链才算走完**，也只有那一刻需求单的**那几项**才退出学年保底。

```
需求单（受理结论，逐瓶）
    → 勾选本次要发的项（一项一项来，不必整单）
    → borrow_order + borrow_order_item（一单多瓶，明细指回需求行）
    → 逐瓶 reagent_borrow（扣库存、写领用流水）
    → 逐行 issued_quantity 累加 + status 推进
    → 单头状态由行状态聚合：issued / partial
```

五个要点：

| 决定 | 原因 |
|---|---|
| 兑付粒度是**行**，不是单头 | 一门课 20 项今天只到 5 项，整单置 `issued` 会把剩下 15 项静默吞掉：不在保底里、不在待办上，永远没人管 |
| 单头状态是**聚合**，不独立驱动 | `partial` 说明「这张单还欠着」，同时能按行算余量。停在 `submitted` 会按全量锁料，把已经发出去的当成欠量 |
| 转单与兑付是**一个动作** | 拆成两步会留下「有单没发、账已占着」的中间态，下次申领又被压 |
| **不重算**瓶与量 | 取自受理那一刻的 `Acceptance`；此刻重算会用变了的库存，结论与承诺不一致 |
| 逐瓶分配一路带到底 | `IssueLine.picks` 记「这瓶扣多少」；只剩 `"A,B"` 串号，扣库存时只能猜 |

借出单与工单是同一张表，不另造单据：`order_type` 记「课程领用 / 零星领用」，`requirement_number` 记来源需求单，`applicant` 是领用的老师、`created_by` 是发料的管理员。来源「课程/实验」直接拆进 `course_name` / `item_name`，用量统计与学期报表不用另接一条链。

**余量截断在服务端**：分两次发时第二次拿到的还是「受理那一刻的实发量」，所以每次签发都按 `quantity − issued_quantity` 截断。不截断就是重复兑付同一批料，而调用方传来的数字不能作为依据。

**受理即提交**：页面生成的需求单落库是 `draft`，`DemandReserve` 不认草稿（老师自己算着玩的不该锁料）。受理那一刻把单推到 `submitted`——这是承诺的起点，也是「逐项兑付」能把状态往前推的前提。只推草稿，已经 `partial` / `issued` 的单不回退。

### 为什么不是一张单据的状态机

因为两个申报人是两个人。合成一张票会让「已发放」变成假终点——货只到了一半，库里却显示流程结束。拆成两段后，第一段可以正常结束（发完了，或者发了一半），第二段独立开跑，各记各的账。

### 路由是配置，不是算法

不存在「猜」这个动作。`custodian_route` 表存两级规则：

| scope_type | scope_key | custodian | 含义 |
|---|---|---|---|
| `course` | `有机化学实验` | 李某 | 这门课找李管理员 |
| `course_class` | `有机化学实验/应化2301` | 王某 | 更精确，优先匹配 |
| `department` | `化学系` | 赵某 | 兜底（谨慎使用） |

匹配顺序：整键 → 课程名（去掉 `/班级`）。两级都查不到就抛 `RoutingError`，页面提示「请先在路由配置里指定这门课的受理人」。**宁可报错，不可猜人**——猜错的后果是把试剂发给不相干的人。

### 抽卡：两周窗口内的局部最优

从管理员名下取料，本质是「从若干瓶里挑哪几瓶」。这件事有三个诉求，但**只有一个是目标**：

| 诉求 | 性质 | 落点 |
|---|---|---|
| 我够用（需求被填满） | 硬约束 | `CoverageLine` 判定，不够就是缺口 |
| 他也够用（他窗口内还要的量不动） | 硬约束 | `ShelfPolicy.drawable()` 按物质总量留水位 |
| 少开新瓶 | 软目标 | `ShelfPolicy.order_key()` 全序字典序 |

**为什么局部最优够用**：设需求 D、已开封余量之和 S。若 D ≤ S，新开瓶数下界是 0，任何「能不开就不开」的规则都达到下界，此时局部即全局；若 D > S，同规格下新瓶数下界是 ⌈(D−S)/规格⌉，按 Best-Fit 抽正好达到。只有多规格混存才退化成装箱近似——而那种场景在本系统里是少数。装箱问题本身不是拟阵，纯贪心在一般情形下没有最优保证，这里的成立是**目标函数特殊**，不是算法普适。

**两个时间尺度，各管一件事**：

| 尺度 | 长度 | 管什么 |
|---|---|---|
| 抽卡窗口 | 当前周 + 下一周（`HORIZON_DAYS = 14`） | 局部最优的边界：哪些需求算「已知」 |
| 学年 | 9/1 → 次年 9/1（`domain/academic_year.py`） | 需求的自然周期：哪些账已经翻篇 |

抽卡窗口是 rolling horizon：窗口内需求已知可枚举，窗口外还不存在，每过一周往后滚一格。它只界定「他还要用的量」怎么算，不影响排序键本身。

学年是**需求真正的周期**。实验大多一年只做一次，所以需求不会每周出现——按「最近两周」算保底，两周内根本没有数据；按「无限期」算，去年没结完的单会年年叠成一座搬不动的山。9 月 1 日这条线一划，累计自动截止：去年 8 月 31 日的单还在旧学年，9 月 1 日之后的单进新学年，两边的账互不干扰。标识沿用系统里已有的 `2026-2027` 写法（`experiment_course.semester`、采购预估都是这个格式），`utils/semester_utils.py` 退化成一层薄壳，边界只在 `AcademicYear` 里实现一次。

**排序键**（`capabilities/circulation/picking.py`）：

```
1  临期/过期先出         落在窗口内用不掉就是报废，压过省瓶
2  已开封先出             少开一瓶是一瓶；开封后保质期本就缩短
3  一瓶够 > 要拼瓶        能用一瓶别动两瓶
4  组内：够用时余量越贴越好；不够时先清小瓶
5  到期日
6  瓶号                   全序兜底
```

第 6 位不是装饰：两瓶到期日相同时若比较到此为止，谁先谁后取决于数据库返回顺序，同一个需求每次抽到的瓶都不同，审计对不上。

**「他也够用」按物质算，不按瓶算**。这一瓶抽完、旁边那瓶还在，完全合法；要守的是总量水位。上限 = 总量 − 留给他的量，且每抽一次从预算里扣减——不扣减的话每瓶都按同一个上限算，会整体超抽。

**保底按学年接通了**（`services/demand_reserve.py`）。它回答一句话：他名下、这一学年、还没发的单里，这种物质占多少。四条边界同时成立才算：本学年、状态 `submitted`、落在他的 `custodian_route` 范围内、不是当前这张单自己。任一条放宽都会出问题——尤其最后一条，当前单若不排除，它会把自己算成自己的保底，需求永远抽不出来。

算不出来时返回 `None`，表示**不锁料**。这个默认方向是刻意的：料没发出去，实验当堂停；料多抽了一点，下一节还能补领。让一件事「宁可发不出」比「多发了一点」危险得多。

## 四、数据表

`db/database.py` 的 `init_tables()` 幂等新增 5 张表，老库升级直接生效，无需手工迁移：

| 表 | 作用 | 关键字段 |
|---|---|---|
| `recipe` | 配方头 | `recipe_key`、`title`、`source_course`、`status` |
| `recipe_component` | 配方组分 | `substance_key`、`amount_kind`、`amount_value`、`unit`、`basis_key` |
| `requirement_sheet` | 需求单头 | `sheet_no`、`recipe_key`、`persons`、`batches` |
| `requirement_line` | 需求行 | `substance_key`、`required_qty`、`unit`、`source_component_id` |
| `custodian_route` | 保管人路由 | `scope_type`、`scope_key`、`custodian`、`department` |

旧库升级后**必须重启应用**。路由表若尚未创建，页面会提示「请重启应用」而不是崩溃。

## 五、页面：配方与需求（侧边栏 ⚗️）

五个 Tab，按工作顺序排列：

1. **📚 配方库** —— 浏览已有配方，看组分与来源。
2. **✍️ 配方编制** —— 新建/编辑配方，逐行选计量策略。保存前跑 `validate()`，缺基准物或缺物性当场报错。
3. **🧮 需求试算** —— 选配方 + 填人数/批次/配液体积，算出需求单。可看到每行的推导说明。
4. **📄 需求量与单据** —— 把需求单落库，生成单号，供后续引用。
5. **🔀 申领流转** —— 两段管线的操作台：
   - 保管账：按管理员看名下的批次（含未认领批次提示）
   - 路由配置：维护课程 → 管理员映射
   - 第一段受理：选需求单，系统自动解析受理人，展示发放明细与缺口；受理即把单推到 `submitted`
   - 转借出单：逐项勾选签发，逐瓶扣库存、生成领用单，勾中的需求行记已兑付
   - 第二段平账：基于第一段结果产出调拨提案
   - 执行调拨：把提案落到实际批次
   - 完整推导：一次跑完两段，看整链（含缺口如何转为采购）

## 六、已知限制（诚实清单）

| 限制 | 现状 | 影响 | 计划 |
|---|---|---|---|
| `chemical_info` 无密度列 | 液体跨量纲只能算折合体积，说不出是哪一瓶 | 需求 44 g、库存 500 mL 时，`lot_id` 留空，note 写「由发放人现场指定」 | 加 `density` 列，液体必填 |
| 路由表初始为空 | 需手工配置或跑 `seed_from_courses()` | 未配置的课程申领直接报错 | 提供批量初始化入口 |
| 未认领批次不进流程 | `manager` 为空的瓶子不参与任何一段 | 库存看起来有、发不出来 | 在保管账页提示「需先认领」 |
| 两段尚未接原有单据表 | 第一段已接：转成 `borrow_order` + 明细（v0.8.16）；第二段仍只在内存提案里 | 调拨结果尚未写 `allocation_order`，与老业务账未合并 | 下一步做第二段落库 |
| 采购计划仅拆包 | 只按包装规格算桶数，不含比价与供应商 | 输出是人看的结果，不直接下单 | 后续接采购管理页 |
| 科室级/个人级路由不参与保底 | `custodian_route` 的 `department` / `person` 无法从单据来源反查 | 只配了科室兜底时算不出保底，退化为不锁料 | 需求单落库时记下当时的受理人快照 |

**为什么不硬算保底**：需求单只有 `created_at` 和 `status`，没有计划使用日期。同一门课每周都申领、历史单一直挂着，若按「需求总量」累计，保底会等于历史需求总和，此后任何申领都抽不出料——一个看起来在工作、实际把系统锁死的规则，比不保底更糟。三道闸依次补上：学年边界解决「跨年累计」，逐项兑付解决「同一学年内重复占量」（按 `quantity − issued_quantity` 算余量），受理即提交解决「草稿单从不进入统计」。仍存的限制是：受理之后、兑付之前这段时间里，保底照常占着——那是应该的，料还没发出去。

**兑付时的并发**：受理时选定的瓶，到发料那一刻可能已被别人借走。`reagent_borrow` 会拒绝，该瓶落进 `failed`，已发的照常兑付。这是有意的：料可能已经在老师手上，账必须留下，不能因为一瓶失败把整单回滚掉。该需求行的 `issued_quantity` 只按**真正扣成功**的量累加，没发出去的量留在余量里，下次还能发。

## 七、与 BCLRM-Lims 的边界

两个仓库当前是**分治**关系，不是主从：

| 内容 | BCLRM 主仓（本仓） | BCLRM-Lims |
|---|---|---|
| 试剂库存、领用归还、采购、处置 | ✅ 现有业务 | ✅ 继承 |
| 配方 / 需求 / 采购拆包 / 两段流转（本模块） | ✅ v0.8.16 | ✅ 将来同步 |
| 实验记录、实验过程管理、教学闭环追踪 | ❌ 不做 | ✅ 下一代版本 |
| 化学实验方案、notebook 反应块、课程用量闭环 | ❌ 不做 | ✅ 已实现（feature 分支） |

判断标准很简单：**换一个前端还得原样存在的东西**（`domain/` + `capabilities/`），两仓共享；**需要知道「这个页面写给谁看」的东西**（实验记录、过程管理），只进 Lims。

共享部分的改动请同时提两个仓。若只改了一边，`docs/双仓分治与合并规程.md` 里有对账方法。
