## 0. 决策摘要

1. 三条轨道并行：生产（稳定、自己用）、beta（其他老师用、真实生产数据）、开发（新功能与修 bug）。
2. 数据单向流动：生产 → beta。beta 的写入不回灌生产；beta 每次候选发版从生产快照重建。
3. 版本号只保证同一时刻的通道顺序：常态下 `生产 < beta < 开发`。不固定 `.1`/`.5` 后缀，不使用 `-dev` 字符串；版本号是纯数字点分，按数值比较。
4. 首次引导期是唯一例外：没有旧生产版可当稳定版，所以生产 `0.8.17.1` 与 beta `0.8.17.5` 使用同一份代码，手机 UI 都关闭，老师第一次使用。0.8.18 起 beta 常态必须领先生产（晋升瞬间除外）。
5. beta 发版前停生产做冷备、校验、恢复生产，再从该快照重置 beta；beta 单纯出错重置时不碰生产。
6. beta 只保留超管强密码，其余账号（包括管理员）全部重置为初始密码。
7. 生产可公告停机；回滚 = 升级前快照 + 旧 release，不做 down migration；重新开放后视为越过回滚点。
8. 备份保留：每日 7 天；过去 3 个自然月每月 1 日、15 日；升级前 2 份；beta 2 份。
9. 进程管理先用 systemd，不引入 Docker；隔离靠 release 目录、`BCLRM_DATA_DIR`、环境变量和端口。
10. 0.8.17.x 生产与 beta 都关闭手机相关 UI；以后 beta 可独立打开新功能，生产保持稳定，直到晋升。

## 1. 目标与非目标

### 1.1 目标

- 代码与数据解耦：同一份代码可以在不同数据根上运行，不会因为启动目录不同产生“分裂库”。
- 发布可复现：每次上线都有确定的代码制品、依赖锁、版本、git sha 和校验和。
- 升级可回滚：生产升级前有可验证的冷快照，失败能退回旧 release。
- beta 可用真实数据：老师测试的是真实业务数据上的新逻辑，不是造出来的假数据。
- beta 不污染生产：beta 只读生产快照，写自己的数据目录；每次发版丢弃。
- 迁移有闸门：旧代码不能打开新库；升级前自动快照；破坏性迁移必须先演练。
- 备份可验证：备份不是“文件存在”，而是完整性、清单、可启动、可冒烟。
- 版本关系清楚：任何时候都能看出生产、beta、开发谁在前，且允许回滚/降级。

### 1.2 非目标

- 不做多机高可用、负载均衡、远程灾备。
- 本期不引入 Docker / Kubernetes。
- 不做数据库 down migration。
- 不做 beta → 生产的数据回灌。
- 不把端口暴露到局域网；继续只绑 `127.0.0.1`，走 SSH 转发。
- 不把 GitHub Actions 作为唯一发布闸门；本地脚本必须能独立完成。

| 术语 | 含义 |
|---|---|
| 生产 / prod | 稳定实例，端口 8501，数据根 `data/prod` |
| beta | 测试实例，端口 8601，数据根 `data/beta`，水印标记 |

| 渠道 | `prod` / `beta` / `dev`，记录在 `release.json` 或环境变量，不拼进版本字符串 |
| 候选 | beta 上待验收的构建 |
| 晋升 | 把验收通过的 beta 构建原样部署到生产 |
| 快照 | 某一时刻四个 SQLite 库 + 附件 + 清单的集合 |
| 冷备 | 停服后做的快照，保证没有写入 |
| 在线备份 | 服务运行时用 SQLite backup API 做的一致快照 |
| schema 版本 | 每个库的 `PRAGMA user_version`，用于阻止旧代码打开新库 |
| 引导期 | 0.8.17 首次上线阶段，允许生产与 beta 同版 |

## 3. 版本规则

### 3.1 版本格式

- 版本号是纯数字点分，例如 `0.8.17.1`、`0.8.18.5`、`0.8.19.2`。
- 允许任意段数；比较时按整数元组逐段比较，缺省段按 0 处理。
- 禁止使用 `-dev`、`-beta`、`rc` 等字符串参与排序；渠道信息放到 `release.json` 的 `channel` 字段或环境变量。
- 不允许字符串排序：`0.8.17.10` 必须大于 `0.8.17.9`。
- `.1` / `.5` 只是本次引导期的实际值，不是版本规则；以后生产和 beta 可以用任意数字。

### 3.2 通道顺序

常态下：

```text
生产版本 < beta 版本 < 开发版本
```

以下情况允许：

- **引导期**：首次没有旧生产版，允许生产 = beta；必须在 `release_train.json` 标记 `bootstrap_until`，当前为 `0.8.18`。
- **晋升瞬间**：生产可以沿用验收通过的 beta 版本号，此时生产 = beta；晋升完成后 beta 必须立即推进到更高版本。
- **beta 降级**：beta 可以回退到更低的候选，但必须仍高于当前生产版本。
- **开发回滚**：开发可以回滚，但必须仍高于当前 beta 版本。
- 版本顺序只在部署时检查，不要求历史版本单调递增；允许 beta 降级、开发回滚，只要当时仍满足通道顺序。

以下情况视为破坏通道序，部署脚本必须拒绝，除非人工记录例外：

- beta 版本 ≤ 生产版本（引导期除外）。
- 开发版本 ≤ beta 版本。
- 生产版本 ≥ beta 版本且 beta 没有立即推进计划。

### 3.3 版本来源

- `env/prod.env`、`env/beta.env`、`env/dev.env` 各自设置 `BCLRM_VERSION`。
- `release.json` 记录 `version`、`channel`、`git_sha`、`artifact_sha256`、`schema_version`、`built_at`。
- `config/settings.py` 只提供默认值；实际显示以环境变量为准。
- 侧边栏、首页、beta 水印显示实际生效版本与渠道。

### 3.4 版本状态检查

新增 `scripts/release_status.py`，输出类似：

```text
prod: 0.8.17.1  channel=prod  schema=2  git=abc123  data=/.../data/prod
beta: 0.8.18.5  channel=beta  schema=3  git=def456  data=/.../data/beta  age=3d
dev : 0.8.19.2  channel=dev   schema=3  git=ghi789  data=/.../data/dev
order: prod < beta < dev  OK
```

检查项：

- 解析三个版本并比较。
- 引导期内允许 `prod == beta`；晋升窗口内允许短暂相等；窗口结束后必须 `prod < beta`。
- 必须 `beta < dev`。
- 生产 git sha 是否等于最近一次验收通过的 beta 候选 sha；不等时给出警告。
- beta 候选已运行天数；低于约定观察期时给出警告。

### 3.5 版本示例

```text
首次引导期：
生产 0.8.17.1  =  beta 0.8.17.5     同一 commit，手机都关

0.8.18 测试：
生产 0.8.17.1  <  beta 0.8.18.5      beta 测试新东西

0.8.18 验收通过：
生产 0.8.18.5  =  beta 0.8.18.5      同一候选构建晋升

beta 继续：
生产 0.8.18.5  <  beta 0.8.19.2

beta 降级示例：
beta 0.8.19.2 → 0.8.19.1，仍 > 生产 0.8.18.5，允许

开发回滚示例：
开发 0.8.20.3 → 0.8.20.1，仍 > beta 0.8.19.2，允许
```

### 5.3 进程管理

- 优先 systemd 系统级或用户级服务；按当前权限选择。
- 每个实例一个 unit：`bclrm-prod.service`、`bclrm-beta.service`。
- `EnvironmentFile` 指定 `env/*.env`；`WorkingDirectory` 指向 `current`；`ExecStart` 指定端口和 `127.0.0.1`。
- `Restart=on-failure`、`TimeoutStopSec=30`，日志进 journal 和 `logs/`。
- 启动日志必须打印：`env`、`version`、`channel`、`data_root`、`mobile_ui`、`schema_version`。

### 5.4 为什么先用 systemd，不引入 Docker

这次的核心问题是代码/数据解耦、迁移、备份和回滚，不是进程打包。

- systemd 提供开机自启、崩溃重启、环境注入、干净停止和日志，足够两套单进程 Streamlit。
- 隔离由 `releases/` + `BCLRM_DATA_DIR` + `env/*.env` + 端口完成，不依赖容器。
- Docker 能提供镜像不可变、依赖隔离、资源限制，但当前机器没有 compose 插件，当前用户也没有 docker socket 权限；还要处理 UID 映射、SQLite/附件 volume 归属、端口映射、日志和备份路径。
- 容器不解决数据库迁移顺序、备份一致性、回滚；这些仍然要脚本。
- 将来需要多机、资源限额或依赖冲突时，再把同样的 release 和 data 目录挂进容器；`BCLRM_DATA_DIR` 就是现成的 volume 挂载点。

### 5.5 访问控制

- 生产、beta、开发都只绑 `127.0.0.1`。
- 通过 SSH 端口转发访问；不开放局域网端口。
- beta 含水印，但水印不是权限控制；SSH 访问名单要单独收口。
- beta 的 `super_admin` 保留强密码；其他账号重置为初始密码。

## 6. 发布列车与数据流

### 6.1 列车模型

```text
首次引导期（只有这一次）：
生产 0.8.17.1  =  beta 0.8.17.5     同一 commit，手机都关

常态：
生产 0.8.17.1  <  beta 0.8.18.5      beta 测试新东西
开发 0.8.19.x  >  beta 0.8.18.5

beta 验收通过：
生产 0.8.18.5  =  beta 0.8.18.5      同一候选构建晋升
beta 随后推进到 0.8.19.x

下一轮：
生产 0.8.18.5  <  beta 0.8.19.2
开发 0.8.20.x  >  beta 0.8.19.2
```

### 6.2 数据流

- 生产是唯一真实数据源。
- beta 每次候选发版从生产快照重建。
- beta 的写入、附件、日志全部留在 `data/beta`。
- 生产升级不回读 beta 数据。
- 生产热修要回合到 beta 候选，避免 beta 测的代码缺热修。

### 6.3 发布角色

- beta 用来验证新功能、迁移和业务流程。
- 生产只接收验收通过的候选。
- 开发不直接部署；开发版本必须高于 beta，但可以回滚到仍高于 beta 的版本。
- 引导期 beta 是“首批老师试运行同一套稳定版”，不是新功能测试。

### 6.4 晋升规则

- 晋升使用 beta 验收通过的那个构建，`git_sha` 和 `artifact_sha256` 不变。
- 生产版本号可以沿用 beta 版本号；也可以另取一个仍低于下一版 beta 的版本号，不强制后缀。
- 晋升后 beta 必须立即推进到更高版本，或者明确停止 beta，避免长期同版。
- 晋升前检查：beta 候选观察期、无阻塞问题、生产 < beta、备份可用、副本演练通过。

## 9. 关键流程

### 9.1 备份

`scripts/backup.py`：

```text
--data-dir <dir> --out <dir> --label daily|semimonthly|pre_change|beta --cold
```

步骤：

1. 四个库逐个用 `sqlite3.Connection.backup()` 生成临时副本。
2. 对副本做 `PRAGMA integrity_check`。
3. 统计每张表行数和关键业务聚合。
4. 附件打包 `attachments.tar.gz`，记录文件数、总字节、sha256。
5. 生成 `manifest.json`。
6. 全部通过后原子移动到目标目录；失败保留现场并告警。

`manifest.json` 至少包含：

- 时间、主机、源数据根、备份类型。
- 应用版本、渠道、git sha、schema 版本。
- 每个库的文件名、大小、sha256、表行数、关键聚合。
- 附件文件数、总字节、tar sha256。
- 备份工具版本、是否冷备。

### 9.2 恢复与校验

`scripts/restore.py`：

1. 校验 manifest 与每个文件 sha256。
2. 对每个库做 `integrity_check`。
3. 恢复到目标数据根；目标像生产时默认拒绝，必须 `--force`。
4. 恢复后再次校验行数和关键聚合。
5. 可选：用备用端口启动，跑健康检查和冒烟。

`scripts/verify_backup.py`：

- 只对照“备份时写入的 manifest”，不和当前热库逐行比较。
- 热库对比只用于评估“回滚会丢多少写入”，不作为备份合格判据。

### 9.3 beta 重置

`scripts/beta_reset.py --mode release`：

1. 预检：`BCLRM_ENV=beta`、目标 `data/beta`、beta 服务已停。
2. 公告短停机。
3. 停生产。
4. 冷备 + 校验。
5. 校验通过后立即恢复生产；失败则中止，beta 不动。
6. 部署 beta 候选版本。
7. 恢复生产快照到 `data/beta`。
8. 清空或改写 `mobile.base_url`。
9. 只保留 `super_admin` 密码；其他账号重置为 `DEFAULT_INITIAL_PASSWORD`；快照中没有 `super_admin` 时中止，不生成可登录的 beta。
10. 灌入当前 schema 版本的边缘 fixture。
11. 启动 beta，健康检查 + 冒烟。
12. 写 `reset_manifest.json`。

`scripts/beta_reset.py --mode repair`：

1. 不停生产，不新做生产备份。
2. 优先用最近一份已验证的生产快照；如果只是代码部署失败、数据没坏，可用 beta 最近快照。
3. 恢复到 `data/beta`，清 `mobile.base_url`，重置账号，灌 fixture，启动冒烟。
4. beta 快照保留 2 份。

`reset_manifest.json` 至少包含：

- 源快照、备份类型、备份时间。
- beta 版本、git sha、schema 版本。
- fixture 版本。
- 重置账号数量、保留的超管用户名。
- 操作人、时间、模式。

### 9.4 生产部署、晋升与回滚

`scripts/deploy_prod.py`：

1. 预检：制品存在、sha 对、依赖锁对、副本演练通过、备份可用。
2. 如果从 beta 晋升：校验 beta 候选观察期、验收记录、`git_sha` 一致、`prod < beta`。
3. 公告停机。
4. 停生产。
5. 冷备 + 校验；失败则恢复生产并中止。
6. 切 `current` 到目标 release。
7. 启动，等待迁移和健康检查。
8. 冒烟：登录、库存、借出、归还、统计、系统设置、`/m` 按开关。
9. 失败：停服 → 恢复快照 → 切回旧 release → 启动验证；恢复也失败则保持停机并告警。
10. 成功：记录部署日志，重新开放。

`scripts/rollback_prod.py`：

```text
--snapshot <dir> --release <old-version>
```

- 停服、恢复快照、切回旧 release、启动、健康检查、冒烟。
- 不做 down migration。
- 重新开放后视为越过回滚点；之后的写入不属于本次回滚。

### 9.5 晋升

`scripts/promote_beta.py` 或 `deploy_prod.py --from-beta`：

1. 读取 beta 当前版本、git sha、artifact sha、schema 版本。
2. 检查 beta 已运行天数、无阻塞问题、验收记录。
3. 检查 `prod < beta`；引导期例外。
4. 选择生产版本号（可沿用 beta 版本，也可取仍低于下一版 beta 的版本）。
5. 走生产部署流程。
6. 晋升后提醒把 beta 推进到更高版本。

## 10. 备份保留

| 类型 | 保留 | 说明 |
|---|---|---|
| 每日 | 最近 7 天 | 在线备份，不停生产 |
| 半月 | 过去 3 个自然月每月 1 日、15 日 | 最多 6 份；从当日备份复制/硬链接 |
| 升级前 | 最近 2 份 | 生产升级或 beta 发版前的冷备 |
| beta | 最近 2 份 | beta 重置前快照，便于排查 |

清理规则：

- 新备份校验通过后才允许清理旧备份。
- 永远不删“最后一份已验证快照”。
- 清理脚本支持 `--dry-run`。
- 异地副本跟着同一套策略；异地删除前先确认本地副本完整。
- 每月做一次完整恢复演练，记录结果。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 0.8.17.1 从开发仓库构建，带上 13/15/16 和已有迁移 | 生产行为变化超出“关手机” | 副本演练；迁移前快照；升级前核对页面和迁移清单 |
| 版本号字符串排序导致误判 | 0.8.17.10 被当成小于 0.8.17.9 | 只用整数元组比较；测试覆盖多段版本 |
| beta 含水印但仍是真实数据 | 老师误改、误以为生产 | SSH 限制；水印；重置丢弃；用户手册说明 |
| beta 全部账号重置为初始密码 | 初始密码扩散 | 只保留超管强密码；beta 只开 SSH；重置清单记录 |
| 生产停服做 beta 冷备 | 短暂停机 | 备份校验完立即恢复生产；beta 重置在后台继续 |
| 冷备/恢复脚本本身出错 | 回滚失败 | 备份后立即校验；副本演练；失败保持停机并告警 |
| WAL 导致直接复制损坏 | 备份不可用 | 只用 SQLite backup API；禁止 `cp` |
| 破坏性迁移 | 数据丢失 | schema 闸门；升级前快照；副本演练；expand/contract 规则 |
| 附件目录增长 | 备份变慢 | tar + 校验；监控；beta 单向复制 |
| systemd 权限不足 | 无法托管 | 优先系统级；不行用用户级 + lingering；再不行 supervisor/nohup |
| GitHub Actions 被代理挡住 | CI 不可用 | 本地 `check_all.sh` 作为发布闸门 |
| 版本回滚/降级破坏通道序 | beta 不再领先生产 | `release_status` 部署前检查；例外必须记录 |

### 15.2 P0 修订

**R1 构建不可复现（对应 5.3、8 Stage 2 第 1 项、14.2）。**

问题：生产 `.venv` 是 Python 3.10.12，beta 与开发环境是 3.13.12；`requirements.txt` 全部是 `>=` 下限，没有锁版。规划第 421 行提到 `requirements.lock`，但没有规定基础解释器版本由谁定、lock 在哪个环境生成。结果「0.8.17.1 与 0.8.17.5 是同一构建」这句话现在是假的——同一个 git sha 在两个解释器上装的是两套包。

修订：定一个基础解释器（建议 3.10.12，与生产现状一致且 `setup.py` 声明 `>=3.10`），三轨统一；每个 release 在自己目录下建 `.venv` 并从 lock 安装；`release.json` 记录 `python_version` 与 `requirements_lock_sha256`；准备离线 wheelhouse（远端走 gh-proxy，装包通道随时可能断），发版闸门包含「从 lock 离线安装成功」。

**R2 健康检查不能证明迁移成功（对应 8 Stage 0 第 6 项、9.4、9.1 第 7 步）。**

问题：`_ensure_database()` 在 `app.py` 模块级执行，而 Streamlit 的 `/_stcore/health` 不加载页面脚本。没人访问过页面时，迁移可能根本没跑，但健康检查已经返回 200。规划多处「启动，等待迁移和健康检查」依赖的正是这个端点。

修订：部署与演练脚本先以一次性进程显式执行迁移（或请求登录页触发脚本运行），随后断言四个库的 `PRAGMA user_version` 等于 release 声明值；冒烟必须真实取一次首页数据，而不是只看端口活着。「本次升级无数据库变更」要由前后 `user_version` 与表/列集合 diff 证明，不能靠声明。

**R3 测试隔离会被数据根改造打穿（对应 8 Stage 0 第 2 项、14.3）。**

问题：`tests/__init__.py` 把默认库实例硬编码注册在 `<仓库>/db/main.db` 这个 key 上，用来兜住 `BaseService` 内部无参的 `Database()`。一旦 `config/settings.py` 的默认路径改由 `BCLRM_DATA_DIR` 派生，这个 key 就对不上，无参 `Database()` 会新建连接指向真实库——四道门禁会直接读写 prod/beta 数据。规划完全没提这条副作用。

修订：Stage 0 第 2 项同步改测试引导，key 也从 settings 读取；再加一条断言「测试进程的默认库路径必须位于临时目录内」，让这类泄漏在测试里炸而不是在真实库上炸。这是 Stage 0 的准入门槛，不是后续优化。

**R4 降级与回滚缺数据库生命周期规则（对应 3 节示例、5.2、8 Stage 0 第 5 项）。**

问题：schema 闸门规定「旧代码打开新库拒绝启动」，而第 3 节又明确允许 beta 降级、开发回滚。两件事一起做必然踩闸门，实施时会当场卡住且找不到依据。

修订：补一节明确三条规则。beta 与开发的「回滚」定义为换代码 + 从对应 schema 的快照重建数据（走 `beta_reset.py --mode repair`），不承诺回滚后还能读现有数据；生产回滚只允许切到与升级前快照 `user_version` 一致的 release；`release.json` 携带每库 schema 版本的 map，切换前先比对，不匹配就拒绝启动并提示走重建。

**R5 第二副本目标已存在，且必须写清限制（对应 13 节待评审点 8、10 节、14.2）。**

问题：规划写成「没有异地目标」，实际有一块已挂载的 362G 外接盘。误判会导致两条坏结果：要么重复找目标，要么脚本按「不存在」跳过第二副本。

修订：把第二副本目标定为该挂载点，并在 `rsync`/`prune` 前强制三项检查。它是同一台物理机上的另一块盘，防单盘故障，不防火灾、电源、勒索软件——把它叫「第二副本」而不是「异地备份」；可被卸载、重启后不保证自动挂载，脚本必须先探测挂载点存在且可写，失败要明确报错而不是静默跳过当前用户；文件系统是 fuseblk（非 ext4），`chmod 600` 与属主语义不生效，含真实人员的快照落在这块盘上必须先加密或只放脱敏副本（M1：现阶段无真实数据，但这条要在引入真实数据之前完成）。

### 16.2 P0 新发现

**S1 单一 `current` 指针撑不起三轨并行（对应 5.1、5.3、3.2、6.1）。**

问题：5.1 的目录布局只有一个 `current -> releases/0.8.17.5`，5.3 又规定两个 systemd unit 的 `WorkingDirectory` 都「指向 `current`」。但本文档的常态恰恰是生产与 beta 同时跑不同 release（3.2「生产 < beta < 开发」；6.1 示例中生产 0.8.17.1 与 beta 0.8.18.5 并存）。一个指针指向一个目录，两个 unit 跟同一个 `current` 就永远同码运行，通道模型在第一天就不成立。这不是排版笔误：晋升瞬间「同一构建、两轨同码」正是靠指针切换实现的，指针必须每轨一个。

修订：每轨一个指针（`current_prod`、`current_beta`），unit 的 `WorkingDirectory` 各指各的；`release_status` 输出每轨的 release 目录与指针目标；晋升 = 把 beta 正在跑的那个 release 目录原样指到 `current_prod`（release 目录共享、指针分开，天然满足 `git_sha` / `artifact_sha256` 不变）；`BCLRM_RELEASE_FILE` 由各 unit 的 env 指到自己的 `release.json`。注意：共享 release 目录在两轨引用期间不得被 R19 的保留策略 prune。

**S2 「同版」一词二义，引导期例外名不副实（对应 0 节第 4 条、3.2、3.5、14.4）。**

问题：文中「同版」时而指「同一构建（同 commit / 同 artifact）」，时而指「版本号相等」。引导期实际值是生产 `0.8.17.1` 与 beta `0.8.17.5`——同 commit 但版本号并不相等；3.5 与 14.4 用「=」连接它们，而 3.2 的例外写的是「允许生产 = beta」（版本号相等）。按 3.2 字面规则，引导期根本用不上这条例外（`0.8.17.1 < 0.8.17.5` 天然满足常态序）；真正需要的例外「允许同构建不同号」从未被写出。同时 3.2 第三条拒绝规则「生产版本 ≥ beta 版本且 beta 没有立即推进计划」被第一条完全覆盖，「立即推进计划」也无法机器判定。

修订：拆开两个概念——「构建同一性」由 `git_sha` + `artifact_sha256` 判定，「通道序」由版本号整数元组判定；例外改为「引导期允许同构建不同号；晋升瞬间允许同构建同号」；拒绝谓词收敛为一条：不满足 `prod < beta < dev` 一律拒绝（引导期按构建同一性放行）。3.5、14.4 的示例建议用「≡（同构建）」与「<（号小）」区分，别再用「=」。

**S3 beta 定位自相矛盾：真实生产数据 + 写入丢弃（对应 0 节第 2 条、1.1、6.2、12 节「老师误改」行、15.5）。**

问题：决策摘要把 beta 定位为「其他老师用、真实生产数据」，6.2 同时规定「beta 的写入不回灌生产；每次候选发版从生产快照重建」。这两条在有真实数据之后必然相撞：老师在 beta 做真实的领用/归还，写入在下一次重置被丢弃——瓶子物理上已经动了，台账却回退到快照原状；若老师因水印淡化而把 beta 当正式系统使用，事故只会更糟。15 节的 M1 只把密码/隐私/加密推迟到「引入真实数据」，没有覆盖「真实业务写入的归属」。

修订：在第 6 节明文二选一并落到验收：本期定为「beta 是验收试用场，真实业务只在生产录入」——beta 的一切写入视为可丢弃，用户手册与 beta 首页文案必须写明「此处录入的数据会在下次发版时清空，不做正式记录」，验收加一条文案扫描；若未来要让老师在 beta 办真实业务，那是 beta→prod 回灌的新项目（当前 1.2 明确非目标），落地前不得对老师开放写操作。同步在 15.5 触发表加一行：「beta 真实业务写入策略 | 现阶段 beta 只做验收 | 对老师开放写操作之前」。

**S4 四库跨库迁移没有编排与半程状态定义（对应 4.4、3.3、9.1 manifest、15.2 R4、15.4 R16）。**

问题：系统有四个 SQLite 库，迁移可能跨库（`chemical_info` 重建、`purchase_plan` 改名都可能连带冷库与日志库）。R4 补了「schema map 不匹配拒绝启动」，但没定义迁移本身的执行编排：四库 `user_version` 各自更新、谁先谁后、半程失败（main.db 已迁、operation_log.db 未迁）算什么状态、恢复是整份快照回滚还是可断点续跑，全部未写。另外 3.3 与 9.1 的 `schema_version` 是单数，与四库各自版本矛盾（R16 说「字段清单」也没定形状）。

修订：`release.json` 与 manifest 的 `schema_version` 改为 per-DB map；`db/schema_guard.py` 增加迁移台账（`schema_migrations`：迁移 id、所属库、开始/结束时间、结果），每库迁移在单事务内完成、成功后才升 `user_version`；跨库迁移按声明顺序执行，任一步失败即整体走 R4 的「恢复快照」路径，不做断点续跑（数据量 5.6MB，全量回滚比续跑简单可靠）；启动时若台账存在「开始未结束」记录，拒绝启动并提示恢复。

**S5 失败/回滚过的版本号禁止复用（对应 3 节、6.4、9.4）。**

问题：3 节允许历史不单调，但没有禁止「同一个版本号装不同的构建」。一次失败的 `0.8.18.5` 晋升回滚后，若下一个构建仍叫 `0.8.18.5`，所有基于号的判断（「晋升瞬间允许 prod == beta」、候选观察期计时、部署日志检索）都会把两次不同构建混为一谈；事故复盘时连「当时跑的到底是哪份代码」都要靠 sha 考古。

修订：版本号一经部署（进过 `releases/` 或打过 tag）即作废、不得复用，回滚后的新候选顺延取号；`release_status` 对照 `releases/` 目录与部署日志检查候选号未用过；`release_train.json` 记 `retired_versions[]`。

### 16.3 P1 新发现

**S6 备份不覆盖配置与发布元数据（对应 9.1、10 节）。** 快照只有四库 + 附件；`env/*.env`、`release_train.json`（`bootstrap_until`、例外记录）、systemd unit、`requirements.lock`、历史 `release.json` 都不在内。机器级故障后即便快照完好，也重建不出服务——数据根、开关、密码策略参数全丢。修订：备份清单增加 config bundle（上述文件 + S4 的迁移台账导出），`manifest.json` 记其 sha256，restore 校验齐全。

**S7 备份调度器根本没定（对应 10 节、15.3 R13）。** R13 引入 `cron_status.json`，但两轮全文都没说「谁每天跑 `backup.py`」——cron？systemd timer？半月的 1 日/15 日谁触发？机器重启错过窗口补不补跑？修订：与 R9 的用户级服务一并定为 systemd user timers（`bclrm-backup-daily.timer` 等，linger 生效），写明错过窗口的补跑策略；半月「从当日备份复制」挂同一 timer 链。

**S8 半月备份「硬链接」跨盘失效（对应 10 节、R5）。** 硬链接只在同文件系统内有效；第二副本在外接盘（fuseblk），rsync 过去只能是独立复制，「从当日备份复制/硬链接」写成默认选项会误导实现。修订：同盘内才允许硬链接，跨盘一律复制并各自校验；文案改为「复制（同盘可用硬链接）」。

**S9 验收记录、例外记录、观察期都没有载体（对应 3.2、6.4、9.5、11 节）。** 「验收记录」「无阻塞问题」「观察期天数」「人工记录例外」在晋升与部署脚本里都是机器校验项，但全文未定义格式、存放位置、由谁写。实现时只能跳过这些检查，等于把「验收」退回口头。修订：`acceptance/<version>.json`（评审人、日期、测试结果、遗留问题、是否阻塞）；`release_train.json` 增加 `exceptions[]`（理由、批准人、失效时间）与 `observation_days` 参数；`promote` 预检读不到验收记录即拒绝。

**S10 水印是信任边界，却没有渲染级回归（对应 7.2、8 Stage 1、15.2 R1）。** 「老师误以为生产」的缓解全靠水印，验收却是人工「18 页验证」；依赖未锁版（R1）意味着 Streamlit 一次自动升级就可能静默弄坏 CSS 叠层，没有人会发现。修订：Stage 1 起加自动断言（测试取页面 HTML 断言水印节点/样式存在，生产 profile 断言不存在），进四道门禁；水印实现避免依赖 Streamlit 内部 DOM 结构。

**S11 dev 轨道没有发布身份（对应 3.2、4.1、5.2）。** dev 跑在脏工作区、无 tag 无 `release.json`，「开发版本必须高于 beta」拿什么比？`BCLRM_VERSION` 手填的「计划号」与制品号混进同一个比较器，脏工作区还可能改出比制品更高的假象。修订：明确 dev 不产制品——dev 版本号是计划号，`release_status` 对 dev 只做「号 > beta」的登记性检查并显示 `git_sha` 与 dirty 状态；不建议强制 dev 走 `releases/` 流水，成本高于收益。

### 16.4 P2 备查

### 17.2 P0 新发现

**T1 制品里的 `.streamlit/config.toml` 把服务绑到 `0.0.0.0`，与全文「只绑 127.0.0.1」的基线直接冲突（对应 1.2、4.1、5.5、8 Stage 2 验收、7.1、15.2 R15、15.2 M2）。**

问题：开发仓库 `.streamlit/config.toml` 写着 `address = "0.0.0.0"`（注释明说是为了「手机在局域网里要能连上」）和 `port = 8501`。0.8.17.1 从开发仓库构建，这份 config 就坐进制品，而 R15 的修订恰恰要求把 config.toml 纳入跟踪与 `git archive`——危险默认值随每次发版扩散。现状之所以安全，只是因为两个实例的启动命令行都显式传了 `--server.address 127.0.0.1`；而 `app.py` 头部 docstring 写的启动方式是 `streamlit run app.py`（不带任何参数），照文档启动就是全网卡监听。规划 1.2 把「继续只绑 127.0.0.1」当成现状陈述写进非目标，但它描述的只是运行时巧合，不是制品行为。M2 已判定手机是预研、不发版——`0.0.0.0` 更没有任何理由进生产制品。

修订：① 制品内 config.toml 的 `address` 收回 `127.0.0.1`，`port` 一并删掉（端口只由 `ExecStart` / CLI 传入，见 T3 相邻问题：config 里写死 8501 对 beta/dev 也是隐患）；② `app.py` docstring 与部署文档统一为「只允许经 systemd unit 启动」，裸 `streamlit run` 标注为开发专用且必须显式传参；③ 启动自检断言「实际监听地址 == 127.0.0.1」，纳入 deploy 预检与 `release_status`（可复用 `views/0_环境自检.py`，见 T6）；④ 手机局域网调试确需 `0.0.0.0` 时只允许 dev 轨用 CLI 覆盖，禁止写进任何被跟踪的 config.toml。

**T2 部署冒烟清单包含写操作，会在真实生产台账上留下永久测试痕迹（对应 9.4 第 8 步、8 Stage 2 验收、9.2 第 5 步、15.3 R2）。**

问题：冒烟清单是「登录、库存、借出、归还、统计、系统设置、`/m`」。其中**借出、归还、系统设置都是写路径**：在升级完成的生产上跑一遍，就是在真实领用/归还记录里写入测试数据，`operation_log.db` 还会同步记一笔审计，且没有任何机制事后清除。一次成功部署就永久污染台账；用真实账号跑还可能触发审批流或真的扣减库存。R2 把冒烟加强为「真实取一次首页数据」只覆盖了只读部分，两轮评审都没有质疑这份清单本身。此外自动化冒烟以什么身份登录（凭据从哪来）全文未定义，实现时只能把密码写进脚本。

修订：冒烟分级——**生产冒烟只读**（登录、首页聚合、库存查询、统计、`/m` 开关断言、水印断言）；**写路径冒烟只在副本/演练器与 beta 上做**（那里数据本来就可丢弃）。若坚持生产必须验写路径，用专用冒烟账号 + `SMOKE-` 前缀数据，部署脚本内置事后按前缀清理并做行数对账（业务表行数回到冒烟前快照值才算通过），清理结果写进部署日志。自动化凭据走环境变量或交互输入，不落盘、不进制品。

### 17.3 P1 新发现

**T3 6.4 的「生产另取版本号」与 S1 的「共享 release 目录」组合后是矛盾的（对应 6.4、3.3、16.2 S1、16.2 S5）。**

问题：S1 的修复依赖「两轨指同一个 release 目录」来保证 `git_sha` / `artifact_sha256` 不变；但 6.4 明文允许生产「另取一个仍低于下一版 beta 的版本号」。同一个目录里的 `release.json` 只有一个 `version` 字段——号不同就没法共享目录（要么复制两份制品再证明字节一致，S1 的指针方案作废），要共享目录就不能另取号（6.4 的选项作废）。两个修订各自都对，叠起来没有裁决规则，实施时会在 promote 脚本上撞车。

修订：晋升**只允许同号**——版本号是构建身份的一部分（与 S5「号禁复用」同向），删除 6.4「另取版本号」选项；若未来确需给生产单独取号，必须走显式路径「复制 release 目录 + 两份 `release.json` 互校 `artifact_sha256`」，并写死在 `promote_beta.py` 的行为里，不允许静默二选一。

**T4 `archive_cold.db` 是长期台账载体，但备份窗口只有 3 个月——S12 的缺口比它写的更具体（对应 10 节、16.4 S12、14.2、9.1）。**

问题：系统的长期留存机制是把过期数据搬进 `archive_cold.db` / `attach_cold.db`（`ARCHIVE_AFTER_YEARS = 3`，冷库只增不减），而备份保留策略的最长窗口是「过去 3 个自然月的半月备份」。冷库里的数据恰恰是年代最久、最不可重建的部分——现在的保留策略实际只保护「最近的数据」，法定留存角色的冷库只有 3 个月的副本深度。S12 提出「声明不承担合规留存或加年度冷存」，但没点名冷库这个载体，读者容易把「留存」理解为主库。

修订：备份策略为 `archive_cold.db` / `attach_cold.db` 单列「年度冷存」档（每年 1 份全量、保留 N 年、随外接盘第二副本走，同库同快照原子打包按 R14）；或明文声明冷库数据的法定留存由其他介质承担，并把「冷库不在备份窗口」写进第 12 节风险表。请业务侧确认后二选一，不要留白。

### 17.4 P2 备查

**T5 登录防爆破是会话级的，R17/S13 的缓解押上来就不成立（对应 15.3 R17、16.4 S13、7.2、5.5）。** 失败计数存 `st.session_state`，刷新页面即清零，锁定不跨会话；`DEFAULT_INITIAL_PASSWORD = "123456"` 还写死在仓库里。当前 SSH 是真实边界、库里无真实人员，影响低；但引入真实数据后，「初始密码扩散」风险表不能把应用层锁定算作防线。修订：与首登强制改密一起进 M1 触发表（补「失败计数落库、按账号锁定」一行），风险表注明应用层锁定当前只是体验功能。

**T6 收口清单补三件（对应 8 Stage 0 第 1 项、15.4 R15、15.2 R3、4.5）。** ① `db_wal/{main,archive,attach,logdb}` 全是 `.gitkeep`，是 7 月 WAL 重定位试验的死目录，收口时删除，免得备份/迁移脚本误扫。② `views/0_环境自检.py` 未注册进导航（死页面），且在 `main()` 里调 `st.set_page_config`——将来谁把它加回导航就会和 `app.py` 顶部的 `set_page_config` 冲突。建议直接改造成 T1 的启动自检载体，或从制品剔除。③ 4.5「手机功能现状」是开发仓库现状，生产目录没有 `14_手机取证.py`（4.2 只列了 13/15/16，把 14 也补上）；标题建议改「开发仓库手机功能现状」，避免误读为生产已有手机功能待关。

**T7 R3 的补强：测试隔离还有两个目录没关（对应 15.2 R3、8 Stage 0 第 2 项）。** `tests/__init__.py` 把四个库路径都重定向到了临时文件（比 R3 说的更全），但 `ATTACHMENTS_DIR` 与 `LOG_DIR` 没有——测试里凡是走附件上传/写日志的用例，物理文件仍落仓库真实目录。Stage 0 的 `BCLRM_DATA_DIR` 落地后，测试引导应收敛为「整体设 `BCLRM_DATA_DIR` 指向临时目录」一处，替换现在按路径逐个打补丁的做法，并保留 R3 的泄漏断言（默认库路径必须在临时目录内，附件/日志同样断言）。
