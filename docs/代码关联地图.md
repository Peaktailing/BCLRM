# 代码关联地图

> 用途：给后续开发一张**影响面索引**——动了哪一块，还要同步看哪些文件、
> 补哪些测试、过哪道门禁。**只写关联，不写实现。**
>
> 想知道「业务怎么运转」读 `docs/业务实现说明.md`；想知道「为什么这样设计」
> 读 `docs/领用关系与状态机设计.md`；想知道「这一版改了什么」读
> `docs/更新日志.md`。本文不重复它们的内容。

**维护规则**：新增、删除、重命名模块/表/页面，或改状态值、权限、编号格式时，
在**同一个提交**里更新本图对应小节。只改函数内部实现不用动它。地图过期比
没有地图更糟——看到明显不对的关联，先改地图再改代码。

## 1. 依赖方向

```
views/ ─────────────┐
components/ ────────┤
                    ├──► business/ ──► capabilities/ ──► domain/
                    │         │              │
                    │         └──────────────┴──► services/ ──► db/
                    └────────────────────────────► services/ / db/（历史允许）
utils/ · models/ · config/：横切，任何层可用；但 utils 不得反向取业务数据
```

`scripts/check_layers.py` 是这条边界的唯一仲裁者，`scripts/layer_baseline.txt`
是既存债务清单。当前 9 条债务分三类：

- 7 个 `business/*.py` 直接 `import db.database`（事务边界该下沉，尚未做）；
- `business/course_import_service.py` 直接用 pandas（导入适配）；
- `services/core/reagent_bottle_service.py` 反向依赖 `business/bottle_state.py`（状态机该迁 `domain/`）。

**改任何 import 都要跑这条门禁。** 新增违规不能写进 baseline——它是记账本，
不是豁免书。

三点容易踩：

1. **导航注册和页面文件是两件事。** 加页面只写 `views/` 不注册 `app.py`，等于没上线；
   `views/0_环境自检.py` 就是现成的例子（诊断页，故意不注册）。
2. **页面可见角色只决定入口。** 真正能不能写由 `business/` 里的 `enforce_role`
   和 `utils/permission_guard.py` 判；两边都要改，不能只改导航。
3. **`views/15` 与 `views/3` 有重叠。** 审批/发料入口在 15，历史操作仍在 3；
   改任一页的动作按钮都要看另一页是否还留着同一入口。

## 3. 八条主链

每条链按「页面 → 业务 → 数据/领域 → 表」排列。改链上任何一环，至少要把
同链其他环扫一遍。

### 3.1 登录与权限

`app.py` → `components/auth.py` → `utils/user_context.py` → `utils/permission_guard.py`
→ `services/base/person_service.py` → `person`
辅助：`business/assignment_service.py`（角色/组判定）、`business/permission_service.py`（旧权限链）
测试：`tests/test_auth_session.py`、`tests/test_permission_guard.py`

同步点：角色名、默认密码、登录态字段、导航可见性、写操作白名单，任意一项改动都
要同时看这四处。`permission_guard` 在 `role is None` 时当前是放行（已知风险），
改权限前先决定是否保留。

### 3.2 入库与两段管线

`views/2`、`views/13` → `business/inventory_service.py`（单瓶）/ `business/material_pipeline_service.py`（批量）
→ `capabilities/circulation/{pipeline,routing,stage1,stage2,ledger,picking}.py`、
`capabilities/supply/{availability,evaluator,procurement,stock}.py`
→ `services/demand_reserve.py`、`services/custodian_route.py`、`services/custody_ledger.py`、`services/bottle_ledger.py`
→ `services/core/reagent_bottle_service.py`
→ 表：`reagent_bottle`、`bottle_lot`、`bottle_placement`、`custodian_route`
测试：`test_custody_pipeline`、`test_supply_circulation`、`test_picking`、`test_bottle_ledger`、`test_demand_reserve`

同步点：入库时是否抽卡、批次与瓶的双写、位置表、保管权台账，四者共用同一批
`capabilities` 输出。改 `capabilities/` 会同时影响调配与需求单兑付。

### 3.3 借还（工单）

`views/3`、`views/1`、`views/12` → `business/work_order_service.py`（建单/审批/驳回/改派/归还）
→ `business/borrow_service.py`、`return_service.py`、`expiry_service.py`
→ `services/core/{borrow_order_service,borrow_record_service,return_record_service,reagent_bottle_service}.py`
→ `business/bottle_state.py`、`utils/bottle_status.py`
→ 表：`borrow_order`、`borrow_order_item`、`borrow_record`、`return_record`、`reagent_bottle`
测试：`test_borrow_return`、`test_work_order`、`test_approval`、`test_bottle_state`

同步点：借出/归还同时改「瓶状态、借用流水、工单状态」三处，少改一处账就对不上。
`borrow_service` 是旧动作层，`borrow_order_service` 是数据层，名字像但职责不同。

### 3.4 需求单：配方 → 需求 → 兑付

`views/13` → `business/recipe_service.py`（配方与计量）→ `business/requirement_service.py`（需求单与模拟）
→ `business/requirement_review_service.py`（管制复核）→ `business/requirement_issue_service.py`（兑付）
→ `services/core/requirement_sheet_service.py`、`borrow_order_service.py`、`borrow_service.py`、`controlled_list_service.py`
→ `domain/{recipe,requirement,pipeline,units}.py`、`capabilities/{metering,supply,circulation}`
→ 表：`requirement_sheet`、`requirement_line`、`recipe`、`recipe_component`、`borrow_order*`、`controlled_list`
测试：`test_requirement_issue`、`test_controlled_review`、`test_recipe_business`、`test_recipe_metering`、`test_picking`

同步点：`views/3` 仍展示兑付后的工单；`views/15` 管理需求单的归属。改需求单状态
或兑付签名，三页都要对一遍。状态目前是裸字符串（技术债 3），没有唯一常量源。

### 3.5 待办、归属、退回、改派

`views/15`、`views/13`、`views/16` → `business/assignment_service.py`
→ `domain/assignment.py`、`services/core/issue_queue_service.py`、`services/base/work_group_service.py`、`services/custodian_route.py`
→ 视图 `v_issue_queue`（定义在 `db/database.py`）
→ 表：`custodian_route`、`work_group`、`work_group_member`、`requirement_sheet`、`borrow_order`、`reagent_bottle`
测试：`test_assignment`、`test_custody_pipeline`、`test_transfer`

同步点：归属三级（人 → 组 → 全院）同时写在 `domain/assignment.py`、
`issue_queue_service` 的查询与 `v_issue_queue` 的 SQL 里；改一级要三处一起改。
「退回修改」与「逐级上交」是两个相反动作，都叫 return，改文案前先分清。
组与成员目前**没有维护页面**，只能改库（技术债 7）。

### 3.6 管制试剂双签

`views/3`（工单）、`views/13`（需求单）、`views/8`（名录）→
`business/work_order_service.py`（`approve_order` / `approve_second` / `reassign_approver`）、
`business/requirement_review_service.py`（复核）
→ `services/base/controlled_list_service.py` → `controlled_list`
→ 常量 `models/core/borrow_order.py` 的 `SECOND_PENDING` / `SECOND_APPROVED`
→ `utils/permission_guard.py`
测试：`test_controlled_review`、`test_approval`

同步点：两条审批链（工单双签、需求单复核）共用管制名录，但状态字段不同；
改名录判定要同时看两边。第二签人必须与第一签不同，这条约束在两个服务里各写一次。

### 3.7 调配

`views/15`、`views/16` → `business/transfer_service.py`
→ `capabilities/circulation/stage2.py`（撮合建议）、`services/core/transfer_order_service.py`
→ `business/manager_service.py` → `services/core/{reagent_bottle_service,manager_change_log_service}.py`
→ `domain/transfer.py`
→ 表：`transfer_order`、`transfer_order_item`、`reagent_bottle`、`manager_change_log`
测试：`test_transfer`、`test_assignment`、`test_custody_pipeline`

同步点：调配只改保管权，不动库存总量；与 `allocation_service` 的旧链（`allocation_order`
→ `manager_service`）是两条路，改管理权语义两边都会受影响。发起、点头、撤回、
标记取货四个动作的权限判定都在服务层，页面只发指令。

### 3.8 手机取证与二维码

`views/14`（`/m?bottle=`）→ `business/evidence_service.py`
→ `utils/photo_utils.py`、`utils/attachment_store.py`、`services/base/attachment_index_service.py`
→ `services/core/borrow_order_service.py`、`services/core/reagent_bottle_service.py`
→ `services/base/system_config_service.py`（取证开关、大小/格式限制）
→ 表：`attachment_index`（附件库）、`borrow_order_item`、`reagent_bottle`、`system_config`
二维码打印：`views/1` → `utils/qr_label.py`（标签尺寸、内容格式、短路径 `/m`；
`normalize_base_url()` 负责补协议与校验）
手机访问入口：`app.py` 未登录/已登录两处都要注册 `/m`（`url_path="m"`）；
`views/6` 保存 `mobile.base_url` 前过 `normalize_base_url()`。
跟随当前入口：`views/1`、`views/14`、`views/6` → `utils/qr_label.app_root_of()`
（读 `st.context.url`，从当前页 URL 反推应用根；页内扫码跳转用它，标签打印的
「跟随当前访问地址」也用它）
测试：`test_evidence`、`test_photo_utils`、`test_qr_label`、`test_attachment_store`

同步点：二维码内容与手机端解析必须同时改；取证限制从配置读，页面不写死。
短路径 `/m` 在 `app.py` 注册，改路径会让已打印的标签全部失效；未登录分支漏注册
`/m` 会让「扫码 → 登录」回不到这一瓶。
`app_root_of()` 依赖「Streamlit 页面路径只有一段」这一前提；若以后给页面配
嵌套 `url_path`，反推会多切一段。打印标签的三种来源（固定地址/当前入口/短码）
任一改动，都要同步 `views/1` 的探测载荷与 `views/14` 的页面扫码跳转。

## 8. 双仓同步点

详见 `docs/双仓分治与合并规程.md`。只记关联：

## 9. 已知双实现与陷阱

这些地方「看起来只有一个，实际有多个」，是最容易漏改的关联：

1. **瓶的显示状态有 4 份实现**：`utils/bottle_status.py`（服务层）、
   `business/query_service.py`、`views/1_实时库存.py`、`views/4_综合查询.py`。
   改「可借/借出/耗尽/过期」的判定，四处一起改。
2. **瓶的可用状态另有一套**：`business/bottle_state.py` 管借出/归还/处置时写的
   `borrowable_flag`，与显示状态不是同一件事。改借还动作先看它。
3. **借还有两层**：`business/borrow_service.py` 是对外动作，`services/core/borrow_*_service.py`
   是数据层。名字相近，改下层不会自动改上层。
4. **管理权有两条路**：`business/transfer_service.py`（调配，需对方点头）与
   `business/allocation_service.py`（旧分配链，直接调 `manager_service`）。
   改 `manager` 语义两条都要看；`allocation_order` 尚未退场。
5. **需求单状态是裸字符串**：`draft/submitted/partial/issued/returned` 散在
   `business/`、`services/`、`views/` 多处，没有唯一常量源（技术债 3）。
6. **「退回」有两个方向**：管理员 `return_for_revision`（退给申请人改，离开在办）
   与申请人 `escalate`（逐级上交，状态不变）。改文案/权限前先分清。
7. **组与成员没有维护页面**：只有 `work_group_service` 与迁移回填；
   `views/6` 不是组管理页（技术债 7）。
8. **页面文件 18 个，导航最多 17 条**：多出来的是未注册的 `views/0_环境自检.py`；
   登录后教师 14 条、管理员 16 条、超管 17 条（不含隐藏登录页）。
   `check_pages` 会跑 18 个文件，导航只认注册过的。
9. **两个版本字符串**：`config/settings.py` 的 `VERSION` 与
   `deploy/build_package.py` 的 `VERSION` 不一致，升版本要一起决定。
10. **权限守卫在角色为空时放行**：`utils/permission_guard.py` 的 `enforce_role`
    对 `role is None` 直接返回。改权限模型时这是第一个要处理的口子。
11. **借出记录没有「未结清」标记**：`borrow_record` 没有 `borrower` /
    `open_borrow_record` / `settled_at` 之类的字段，`business/return_service.py`
    靠「该瓶最新一条借用记录」推断归还对象。改归还、并发归还或补历史数据时，
    这个推断是单点，必须连同 `services/core/borrow_record_service.py` 一起看。
12. **初始密码写死在配置里**：`config/settings.py` 的
    `DEFAULT_INITIAL_PASSWORD = "123456"`。改密码策略要同时看
    `components/auth.py`、`utils/password_utils.py`、`views/6_系统设置.py`
    以及已有账户的首次登录流程。
13. **没有 `schema_version` 表**：`db/database.py` 的迁移靠「查列是否存在 +
    幂等补列」推进。加迁移时必须保证可重复执行，并同步
    `scripts/check_consistency.py` 的表/字段口径。
14. **需求单有两条链**：旧链 `business/requirement_service.py` +
    `capabilities/circulation/gateway.py` 的 `InMemoryCirculationGateway`
    （重启后清空，对应 `views/13` 的「申领单据」标签）；新链
    `services/core/requirement_sheet_service.py` +
    `business/requirement_issue_service.py`（落库，对应「需求量与单据」「申领流转」）。
    改需求单前先确认改的是哪条，别把新链的字段加到旧网关上。
