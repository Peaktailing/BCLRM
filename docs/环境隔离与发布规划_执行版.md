## 1. 终审结论

总体方向通过：采用 **prod / beta / dev 三轨、release 与 data 分离、systemd 用户级服务、冷备升级、快照回滚、beta 原构建晋升**。本期不引入 Docker，不做 down migration，不做 beta → prod 数据回灌。

但必须在动工前统一以下最终裁决，执行者不得再从旧稿中挑另一套说法：

| 编号 | 最终裁决 |
|---|---|
| D01 | prod、beta 使用独立指针 `current_prod`、`current_beta`；release 目录可共享，指针不得共享 |
| D02 | 常规晋升必须 **同版本、同 git sha、同 artifact sha、同 release 目录**；禁止生产另取版本号 |

## 3. 目标布局与运行契约

### 3.1 目录

```text
/home/biochm/BCLRM/
├── releases/<version>/
│   ├── payload/                 # 不可变代码与锁定依赖清单
│   ├── .venv/                   # Python 3.10.12，按 lock 安装
│   └── release.json             # 位于 payload 外，避免哈希自引用
├── current_prod -> releases/<version>
├── current_beta -> releases/<version>
├── data/{prod,beta,dev}/{db,attachments,logs}
├── backups/prod/{daily,semimonthly,pre_change,annual}
├── backups/beta/
├── config-backups/
├── env/{prod.env,beta.env,dev.env}
├── systemd/user/
├── acceptance/<version>.json
├── deployments/{prod,beta}.json
├── releases-index.json
├── release_train.json
└── logs/cron_status.json
```

release 至少保留最近 3 个，并额外保留所有仍被指针、部署记录或回滚点引用的 release。禁止仅按数量删除共享 release。

### 3.2 环境变量

| 变量 | 规则 |
|---|---|
| `BCLRM_ENV` | 必填：`prod` / `beta` / `dev` |
| `BCLRM_DATA_DIR` | prod/beta 必填且必须位于预期环境目录；dev 可缺省 |
| `BCLRM_RELEASE_FILE` | prod/beta 指向本轨当前 release 的绝对路径 |
| `BCLRM_MOBILE_UI` | prod/beta 默认 `0`；dev 默认 `1` |

`BCLRM_VERSION` 不再作为版本事实源；若暂时保留，只能用于和 `release.json` 交叉校验，不一致即拒绝启动。

### 3.3 `release.json` 最小契约

```json
{
  "version": "0.8.18.5",
  "git_sha": "完整40位sha",
  "artifact_sha256": "payload制品哈希",
  "python_version": "3.10.12",
  "requirements_lock_sha256": "lock文件哈希",
  "schema_versions": {
    "main.db": 3,
    "archive_cold.db": 1,
    "attach_cold.db": 1,
    "operation_log.db": 1
  },
  "built_at": "ISO-8601时间"
}
```

渠道、部署时间、验收状态写入 `deployments/<env>.json`，不得回写共享 `release.json`。制品哈希针对 payload，不针对包含 `release.json` 的整个目录。

### 3.4 版本与通道

- 常态部署候选前必须满足 `prod < beta`；dev 仅登记计划号和 dirty 状态，要求计划号大于 beta，但不走 release 流水。
- 晋升后允许 `prod == beta`，因为两轨指向同一 release；beta 可保持该版或停止，下一候选必须取更高版本。
- 引导期只豁免“同 commit 不同版本”的构建关系，不豁免备份、迁移、演练和验收。
- `release_train.json` 记录 `retired_versions[]`、观察期、引导期截止版本和有时效的人工例外。
- 晋升前执行 `git merge-base --is-ancestor <prod_sha> <beta_sha>`，防止 prod 热修未进入候选。

## 4. 数据、迁移、备份与恢复

### 4.1 数据根和测试隔离

1. `config/settings.py` 统一派生四库、附件、日志路径；禁止其他模块再自行拼仓库路径。
2. prod/beta 缺少或错配数据根时 fail-fast，启动日志打印 env、版本、release、数据根、手机开关和 schema map。
3. 测试不再逐个 monkeypatch 真实路径；在导入业务模块前设置临时 `BCLRM_DATA_DIR`。
4. 测试断言四库、附件、日志全部位于临时根，并在套件结束检查真实路径未新增或修改文件。
5. 原有关闭外键的测试隔离行为不得被本次改造悄悄扩大；另补至少一组外键开启的基础设施测试。

### 4.2 迁移

1. 盘点当前各库真实 schema，建立首个可信基线。禁止给未核验的旧库直接批量盖章为最新版本。
2. 每库使用 `PRAGMA user_version` + `schema_migrations` 台账；记录 migration id、开始/结束、结果和错误。
3. 每库迁移在单事务内执行，成功后才能推进 `user_version`；存在“开始未结束”记录时拒绝启动。
4. `release.json` 声明四库 schema map，启动、部署、回滚均逐项比对。
5. 跨库按显式顺序执行；失败不做断点续跑，整组恢复到升级前冷快照。
6. 破坏性变更按 expand/contract 拆分，本版本只做 expand；旧代码与新 schema 不兼容时不得启动。
7. 部署顺序：停服 → 冷备校验 → 用目标 release 显式迁移 → 校验 → 切指针 → 启动。迁移失败先恢复快照，再启动旧 release。
8. Streamlit 健康端点不作为迁移成功证据；迁移结果以 CLI 退出码、schema map、台账和真实只读查询共同判定。

### 4.3 快照内容

每份快照包含：

- 四 SQLite 库及各自完整性、schema、表/列/索引/视图、行数和关键聚合信息；
- `attachments/` 包、文件数、大小、sha256，索引引用文件必须存在；多余物理文件记为孤儿；
- 独立配置包：非秘密 env、systemd unit/timer、lock、release/deploy 元数据、release_train；
- `manifest.json`：来源、时间、冷热备类型、版本、git sha、工具版本及各文件哈希。

数据包与配置包分别存放、分别校验。**常规升级失败和 prod 回滚只恢复数据包，不恢复配置包**，避免把 beta 的新部署状态、版本退役记录和例外记录回写成历史值。配置包仅用于整机灾难重建或经负责人批准的人工合并；prod 回滚时保留当前 `deployments/`、`release_train.json` 和另一轨全部元数据，再追加本次回滚记录。

env 不得保存明文密码。自动冒烟凭据只能交互输入或存在于内存，不落盘、不入制品、不写日志。

### 4.4 备份与恢复纪律

- 热备按“库后附件”执行并检查索引引用；发现缺失文件即失败重试，不得把该校验降级为警告。热备只代表各库一致性，不冒充四库全局同一时刻冷快照。
- pre_change、回滚和 beta release 重建一律冷备；beta repair 不触碰 prod，可使用最近已验证快照。
- 恢复前校验哈希和完整性，恢复到目标后再次校验，并用对应 release 做备用端口只读冒烟。
- 恢复 prod 必须核验 env、绝对目标路径、服务已停和明确人工确认；禁止仅凭一个通用 `--force` 覆盖数据。
- 每周自动选择快照做真实恢复演练；结果写入 `cron_status.json`，系统设置页展示最近成功时间和失败原因。
- 第二副本目标为 `/media/biochm/3696A6CB96A68B47` 下独立目录；复制前检查挂载和可写，跨盘只能复制并重新校验，不能硬链接。
- 根分区低于 10 GiB 警告，低于 5 GiB 拒绝新 release/备份；清理前始终保留最后一份已验证快照。

### 4.5 保留策略

| 类型 | 保留 |
|---|---|
| 每日在线备份 | 最近 7 天 |
| 每月 1 日、15 日 | 过去 3 个自然月，跨年由测试覆盖 |
| 升级前冷备 | 最近 2 份，且不得删除当前回滚点 |
| beta 快照 | 最近 2 份 |
| release | 最近 3 个 + 所有仍被引用者 |
| 年度全量冷存 | 每年 1 份；合规期限确认前禁止自动删除 |

由 systemd user timers 调度，开启补跑；半月和年度任务从已验证备份复制。第二副本失败必须显式告警，不得静默跳过。

## 5. beta 与生产运行规则

### 5.1 beta

- 首页固定提示：`测试环境 BETA：此处数据会在下次候选发布时清空，不作为正式台账。`
- 全页横幅和水印不依赖 Streamlit 私有 DOM；自动测试 beta 必须存在、prod 必须不存在。
- release 模式：停 beta → 短停 prod → 冷备校验 → 立即恢复 prod → 恢复快照到 beta → 清生产手机地址 → 重置独立凭据 → 灌入版本化 fixture → 显式迁移 → 启动验收。
- repair 模式：只处理 beta；不得停 prod、不得读取 prod 热库直接覆盖。
- fixture 使用 `BETA-` 前缀、幂等，覆盖过期、零余量、部分归还、待审批、附件、多单位和归档场景。
- `reset_manifest.json` 记录快照、版本、fixture 和账号数量，不记录任何密码。
- 引入真实人员数据前，额外完成 SSH 名单复核、日志隐私窗口、副本加密、首登强改密验证和服务端账号锁定。

### 5.2 手机开关

关闭时同时处理导航已登录/未登录分支、页面直接执行守卫、二维码标签、系统设置文案和领用归还提示。`/m` 返回“当前环境未开启手机取证”，不得空白或裸 404。

自动测试覆盖 dev 开、prod/beta 关两套 profile；prod 页面不得出现手机入口、扫码或手机访问地址。后端证据能力和既有表结构本期不改。

### 5.3 prod 部署、晋升和回滚

部署前必须具备：不可变制品、lock/wheelhouse、有效验收 JSON、schema map、最近恢复演练成功、已验证冷备、维护窗口和负责人批准。

部署后只做只读冒烟：健康端点、登录页/人工登录、首页聚合、库存查询、统计查询、设置页读取、监听地址、水印和手机开关。完整写链路已在同快照副本和 beta 通过。

任何预检、迁移、启动或只读冒烟失败：保持停机 → 恢复对应冷备 → 切回旧 release → 旧版只读冒烟。恢复失败不得开放服务，保留现场并告警。

重新开放后产生的新写入不自动并入旧快照；再次回滚会丢失回滚点之后的写入，必须由负责人重新确认。

### Stage 1：beta 引导

- 收口旧 8601 实例和实际数据根，先复制后校验，旧目录设只读保留一周。
- 部署 `0.8.17.5`，启用独立数据根、用户级服务、水印、独立凭据和 fixtures。
- 完成 release 与 repair 两种重置；老师验收前明确“数据可丢弃”。

**出口**：beta 可重复重建，prod 只在冷备窗口短停，所有账号与手机地址检查通过。

### Stage 2：prod 首次切换

- 从已验收代码构建 `0.8.17.1`；引导期允许与 beta 同 commit，但不复用其 release 元数据。
- **首次回滚落点**：上线前把现有生产代码和其可用 `.venv` 冷复制为 `/home/biochm/BCLRM/legacy/prod-<git_sha>/`，记录 legacy manifest，准备独立但默认禁用的 `bclrm-prod-legacy.service`，仅绑 8501。旧应用不识别新数据根，因此其回滚数据恢复到该 legacy 目录原有的 `db/`、`attachments/`，不得假称支持 `BCLRM_DATA_DIR`。
- Stage 0C 必须实际验证“legacy 副本启动 → 新版升级失败 → 停新版 → 恢复 legacy 数据 → legacy 只读冒烟”。首次回滚使用这条专用路径；后续常规版本才使用 `current_prod` 旧 release 路径。
- 公告 1–2 小时窗口，停服冷备，复制到 `data/prod` 并校验，显式迁移，切换 `current_prod`。
- 只读冒烟通过后开放；原生产目录、legacy 副本和回滚快照保留一周以上，全部设为非默认启动，回滚点不得被清理。

**出口**：负责人签署验收；服务仅监听 127.0.0.1:8501，备份 timer、状态展示和两种已演练的回滚能力均有效。

### Stage 3：常态发布

- 常规候选走 beta 构建 → 3 日观察/人工验收 → 同版本同制品晋升 → 下一候选取更高号。
- 完成 `docs/部署说明.md`、更新日志、用户手册和恢复/回滚 runbook。
- 每月复核自动恢复结果、第二副本、磁盘、release/备份保留；年度冷存暂不清删。

**出口**：由未参与实施的人仅按文档完成一次副本升级和回滚。

## 7. DeepSeek / Qwen 分工与合并顺序

| 执行者 | 独占范围 | 不得直接修改 |
|---|---|---|
| DeepSeek | `config/`、`.streamlit/config.toml`、`db/` 的应用连接与 schema 闸门、`app.py`、`components/`、`views/`、`tests/` 中运行时与 UI 测试 | Qwen 的发布脚本、备份保留策略、systemd 工具实现 |
| Qwen | `scripts/` 发布工具、`deploy/`、`utils/backup.py`、release/manifest 工具测试、systemd unit/timer、部署文档 | 业务服务、页面实现、DeepSeek 的迁移内部实现 |

共同修改 `pyproject.toml` 或 `requirements*` 时由 Qwen 统一收口；DeepSeek 只提出新增依赖，不并行改锁文件。

合并顺序：

1. DeepSeek 完成 Stage 0A 并提交运行时契约与测试。
2. Qwen rebase 到该基线，完成 Stage 0B 工具链接入。
3. Qwen 主导 Stage 0C；发现应用缺陷只提交复现用例，由 DeepSeek 修应用，Qwen 修工具。
4. 双方提交均保持原子：运行时、迁移、备份、部署、文档不得揉成一个大提交。
5. AI 可以准备验收记录，不得代替负责人批准 prod 发布。

### 给 DeepSeek 的执行指令

> 按 `docs/环境隔离与发布规划_执行版.md` 负责 Stage 0A。只改分工表中的应用侧文件，先完成数据根与测试隔离，再做 schema/迁移和手机/水印开关。不得动生产数据、Qwen 发布脚本或现有未归属改动。交付提交 sha、变更文件、测试证据和供 Qwen 调用的 CLI。

### 给 Qwen 的执行指令

> 按同一执行版负责 Stage 0B，并在 DeepSeek 基线上 rebase。所有工具先在临时目录和副本验证，默认 dry-run，不得直接部署 prod。完成构建、备份恢复、故障注入回滚和 systemd 配置后，主导 Stage 0C，交付可复现命令、日志、演练报告及剩余阻塞项。

## 8. 强制质量门禁

每次集成至少执行：

```bash
pytest
python scripts/check_layers.py
python scripts/check_consistency.py
python scripts/check_pages.py
./scripts/check_all.sh
```

`check_all.sh` 必须汇总而非替代专项测试，并增加：

- 四库/附件/日志测试路径泄漏断言；
- prod/beta 缺失数据根即失败；
- 版本数值比较、禁复用、晋升同版和祖先检查；
- 离线安装、制品必需文件和哈希校验；
- 备份 roundtrip、缺失附件、错误哈希、半程迁移、整份恢复；
- 双 profile 页面、水印、`/m` 关闭态和监听地址；
- prod 冒烟零业务写入；
- 备份保留跨年、跨盘、最后快照和被引用 release 防删除。

历史门禁债务按原基线单独列出，不得借“历史问题”新增失败。最终报告写实际通过数和跳过数，禁止沿用旧的 623 数字。
