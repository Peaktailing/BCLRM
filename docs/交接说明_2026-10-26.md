### 3.1 组模型

```
work_group(name, kind) + work_group_member(group_name, person_name)
```

四条硬规则（破了会出静默 bug）：

1. `kind` 只影响显示，**不参与权限判定**
2. 成员表是唯一口径，`person.department` 只作主组兜底（否则「退组」永远不生效）
3. 判定一律 `custodian_key IN (...)`，写成等值会让科研组的单从待办消失
4. 迁移 9.5 已按 `person.department` 回填

### 3.2 两种「退」，方向相反

| | 谁做 | 含义 | 落点 | 状态 |
|---|---|---|---|---|
| 退回修改 | 管理员 | 单有问题 | `person:申请人` | 离开在办 |
| 退回上一层 | **申请人** | 指定的人不批，放给更多人 | `person` → 组 → `all` | **一字不动，还在办** |

退回**不要求写原因**（Q22）——强迫填只会得到一百条「再改改」。

### 3.3 管制双签

两条路径断点不同：

- **借出单**：`approve_order()` 置「待复核」（不动库存）→ `approve_second()` 发料
- **需求单**：没有审批动作，复核卡在 `issue()` 算完 plan 之后（未过返回 `CONTROLLED_REVIEW_REQUIRED`）

第二签写 `second_approval_*` 五列，**不覆盖第一签**；复核人不能是自己或申请人；`controlled_flag` 建单落库不重算；一轮一签。

### 3.4 调配台

```
报缺口 → 撮合（TransferBroker 一行不改）→ 对方点头 → 平账（改 manager，瓶子不动）
```

| 决定 | 理由 |
|---|---|
| 点头只能是 `from_manager` 本人 | 与组池逻辑**故意不一致**：组池判「单该谁办」，保管权判「货归谁」 |
| 不同意必填理由 | 与 Q22 相反：对发起人是可行动信息 |
| 一人一单 + 逐行勾选 | 「3 瓶给 2 瓶」是常态 |
| `accepted` 即生效 | 不设「已同意待执行」的悬挂态 |
| 不进待办队列 | 队列是「谁该发料」，调拨是「谁该点头」，横幅提示即可 |
