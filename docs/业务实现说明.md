## 1. 单据体系全景

系统里有**六种**单据。分不清它们，后面全乱。

| 单据 | 表 | 谁发起 | 干什么 | 动库存吗 | 动保管权吗 |
|---|---|---|---|---|---|
| **借出单** | `borrow_order` | 教师（或管理员代填） | 零星/课程领用，逐瓶借出 | 是（借出量） | 否 |
| **需求单** | `requirement_sheet` + `requirement_line` | 教师（按配方算量） | 课程/实验要多少料，走两段管线 | **兑付时**是 | 否（第一段） |
| **调拨单** | `transfer_order` + `transfer_order_item` | 管理员（手上缺口） | 保管权在管理员之间流转 | **否**（一瓶不动） | **是** |
| **采购计划** | `purchase_plan` + `purchase_plan_item` | 管理员 | 缺口转采购 | 否 | 否 |
| **预定单** | `reservation_order` | 教师 | 提前占位 | 否 | 否 |
| **归还记录** | `return_record` | 借用人 | 还回来 | 是（加回） | 否 |

### 1.1 关键分界：三种「料从哪来」

```
借出单     —— 我手上这瓶，借给他用一阵子，瓶还在我名下
需求单兑付 —— 我手上这瓶，发给他，量算在我头上（第一段，保管权不变）
调拨单     —— 他名下这批货，责任转给我，瓶子原地不动（第二段，保管权流转）
```

**调拨单是唯一「动保管权不动库存」的单据。** 这是它必须单独成表的根本原因——塞进 `allocation_order`（那张是需求驱动的「算够不够」，没有出料人、没有双方确认、明细只有瓶号文本）会让两种语义永久纠缠。

### 1.2 两段管线（需求单的核心）

教师提交需求单后，料不是凭空出现的，分两段：

| 段 | 名字 | 干什么 | 保管权 | 落到哪 |
|---|---|---|---|---|
| 第一段 | **承接** | 本课管理员把自己名下够的料发出去 | **不变**（管理员仍是临时所有人） | `business/requirement_issue_service.py` 的 `issue()` |
| 第二段 | **平账** | 某管理员不够，由其他管理员调拨补上 | **流转** | `business/transfer_service.py` 的 `request()` |

**不能合成一种单据。** 第一段管理员是试剂临时所有人，教师只是使用者；第二段是管理员之间的责任转移。合成一张会出现「这瓶到底算谁的」永久说不清。

**不变量**：`Σ实发 + Σ缺口 ≡ 需求`；第二段永不调受理人自己的料；教师不出现在任何瓶的 `manager` 上。

## 2. 归属：谁能看、能办

### 2.1 四层归属（`custodian_scope` + `custodian_key`）

每张单都有归属。归属决定**谁能在待办队列里看见它、谁能办它**。

| scope | key 是什么 | 谁能看见/办 | 典型场景 |
|---|---|---|---|
| `person` | 人名 | 只有这个人 | 课程规则命中具体教师 |
| `department` | **组名**（不是科室字段） | 该组全体管理员 | 有教研室但没指定人 |
| `all` | 空 | 全院管理员 | 明确没人负责 |
| （空） | 空 | 按 `all` 处理 | 升级前的老单 |

代码落点：`domain/assignment.py` 的 `Assignment`（值对象）+ `business/assignment_service.py` 的 `resolve_target()`（三级降级：课程规则 → `person`，有主组 → `department`，否则 `all`）。

### 2.2 「组」是一等公民（v0.8.16 新增）

原来只有 `person.department` 一个字段，装不下「一个管理员分属多个组」。

```
work_group(name UNIQUE, kind, note, created_at)
work_group_member(group_name, person_name, created_at, UNIQUE(group_name, person_name))
```

四条硬规则：

1. **`kind`（教研室 / 科研组 / 其他）只影响显示与筛选，不参与权限判定。** 否则明天加第三种组就要改权限代码。
2. **成员表是唯一口径。** `person.department` 退化为「主组兜底」——只在成员表查不到时用。否则「退组」永远不生效（人退了组，字段还留着）。
3. **判定一律用集合。** SQL 写 `custodian_key IN (...)`，写成 `= '化学教研室'` 会让科研组的单从待办里消失。
4. **提交时可以选组。** `assignment_service.resolve_target_for_group(requester, group_name)`——只在「确是成员」时生效，否则退回三级降级。

### 2.3 判定矩阵（`Assignment` 的方法）

| 判断 | 方法 | 说明 |
|---|---|---|
| 能看见吗 | `visible_to(me, my_groups, is_super_admin)` | 队列列表用 |
| 能接单吗 | `can_claim(me, my_groups, is_super_admin)` | 组池/全院池收窄到人 |
| 能办理吗 | `can_handle(me, my_groups, is_super_admin)` | 发料、审批 |
| 能退回给申请人吗 | `can_return(me, my_groups, is_super_admin)` | 见 §3 |
| 能放给别人吗 | `can_escalate(me, requester, is_super_admin)` | 见 §3 |
| 能改派吗 | `can_transfer(me, requester, is_super_admin)` | 三种人：当前持有人、申请人、超管 |

**权限 = 当前归属的成员集合。** 可见 / 接单 / 受理审批 / 退回 / 转交全从这一个集合派生，不另设权限表。

### 2.4 收窄到人以后就看不见了

这是设计意图，不是 bug：`person` 层的单，同室的其他管理员**当场看不见也动不了**。要放宽，走 §3 的「申请人退回」或「改派」。

反向：回到组池（`department`）以后，本室**任一**管理员可接、可办、可退。组池的主人是整组，不是某一个人——压成「同室不可退」会让组池只有超管能碰，变成死池。

## 3. 两种「退」，方向相反

这是最容易搞混的地方。**两个主体、两个方向、两个后果。**

| | 谁做 | 含义 | 落点 | 状态 |
|---|---|---|---|---|
| **退回修改** | 管理员（能办的人） | 单有问题，不能按现在这样批 | **恒为 `person:申请人`** | 工单「已驳回」/ 需求单 `returned`，**离开在办** |
| **退回上一层** | 申请人 | 指定的人一直不批，把单放给更多人 | `person` → `组` → `all` 逐级放宽 | **一字不动，还在办** |

一句话：**管理员退 = 单有问题；申请人退 = 人不在。**

### 3.1 退回修改（管理员侧）

- **落点恒为 `person:申请人`**，person/department/all 三层一样。不存在「退到上一级池」。
- **不要求写原因**（Q22）。强迫填一句话只会得到一百条「再改改」，既没有信息量，又把申请人挡在门外——写不出理由就不敢退，于是硬批。字段留着（工单 `approval_remark`、需求单 `return_reason`）但不校验。
- **「指定的人休假」不靠退单兜底**，靠改派。
- 需求单退到 `returned` 后：退出待办、退出学年保底、进兑付黑名单（不能直接兑付，得先改）。

### 3.2 退回上一层（申请人侧）

- `can_escalate(me, requester)`：只有申请人或超管能放。
- `escalated_to()`：`person` → 组（`target_group` 或自己的主组）→ `all`；已经在 `all` 返回 `None`（退无可退）。
- **状态不变**，单还在办。改的只是「收件人范围」。

### 3.3 改派（`transfer`）

写法三种，`resolve_target_ref()` 解析：

```
person:张三        → 指定人
group:化学教研室   → 指定组
张三               → 裸名字，先认组名再认人名
```

下拉选项由 `transfer_options()` 生成，**组排在人的前面**并带人数（`👥 化学教研室（教研室）· 3 人`）——因为「指错了组比指错了人更常见，硬塞给某个人只是把问题往下压一层」。

约束：不能改派给自己，不能改派给 `all`（那是「退回上一层」，走 `can_escalate`）。

> 「组是一等公民」和「归属三级降级」的完整推导见 `docs/领用关系与状态机设计.md` §14.6。

## 4. 管制试剂双人审批（S11）

**含管制化学品的单，两个人签完才发料。**

### 4.1 两条路径，断点不同

| 路径 | 一审 | 二审 | 为什么不同 |
|---|---|---|---|
| **借出单**（`borrow_order`） | `approve_order()` → 状态置 `待复核`，**不动库存** | `approve_second()` → 发料 | 工单本来就有「审批」这个动作，插一层最自然 |
| **需求单**（`requirement_sheet`） | 没有「审批」动作 | 复核卡在 `issue()` 算完 plan 之后 | 兑付即发料，没有中间状态可插。未复核直接返回 `CONTROLLED_REVIEW_REQUIRED` |

需求单的复核入口是 `business/requirement_review_service.py`：`request()` 送复核 → `approve()` 复核通过 → 才允许 `issue()`。

### 4.2 五条硬规则

1. **第二签不覆盖第一签。** 第一签写 `approver` / `approval_time` / `approval_remark`；复核写 `second_approval_*` 五列。谁批的一眼能分清。
2. **复核人不能是自己，也不能是申请人。** 代码返回 `SAME_SECOND_APPROVER` / `APPLICANT_CANNOT_REVIEW`。
3. **复核人认人不认归属。** 换归属就换复核人 = 让审批人自己挑裁判。
4. **`controlled_flag` 建单时落库，不每次重算。** 管制名录会更新，重算会让当年合规的单突然「不合规」。
5. **一轮一签。** 需求单兑付成功后清 `second_approval_status`，保留 `second_approver` 留痕；下一批料重新送复核。

### 4.3 判定管制品的口径

与建工单同一套：CAS 号 → 名称 → 别名，再看 `is_controlled`。落点 `business/requirement_issue_service.py` 的 `_controlled_names(plan)`。

## 5. 调配台：管理员之间的横向通道（S10）

### 5.1 为什么需要它

第一段兑付时手上不够，过去只有两条路：少发（需求单停在 `partial`）或者等采购。可院里别处有料——横向通道没有。

Q18 定了「**手上没料不构成退单理由**，单留在他名下」，缺的就是这个动作。

### 5.2 四步流程

```
报缺口 ──> 撮合建议 ──> 对方点头 ──> 平账
我的缺口    TransferBroker   逐行勾选    改 manager
（认领到我） 一行不改         accepted即生效  + manager_change_log
```

**调的是保管权，不是实物。** 走完一张调拨单，`reagent_bottle.manager` 变了，瓶子没动、库存总量没变。

**撮合一行没改**：直接转调 `capabilities/circulation/stage2.py` 的 `TransferBroker`——它早就算好了「从谁那调多少、哪几瓶」，还带着两条硬约束：排除受理人自己（他的量在第一段已承诺出去）、尊重出料方窗口保底（别人两周内自己要用的不能调走）。

### 5.3 五条设计决定

| 决定 | 理由 |
|---|---|
| **点头只能是 `from_manager` 本人** | 与组池逻辑**故意不一致**：组池判「这张单该谁办」（同组可代办），保管权判「这批货归谁」（只能本人）。同组管理员能替他办一张单，不能替他认下一批货 |
| **不同意必填理由** | **与 Q22 相反**：退回是「你的单有问题」，申请人自己知道；拒绝调拨是「我不给」，对发起人是**可行动的信息** |
| **一人一单 + 逐行勾选** | 3 瓶给 2 瓶是常态。合成一张多出料人的单会出现「甲同意了、乙还没看」的中间态，状态机要多一维，而多出来的那一维没人读得对 |
| **`accepted` 即生效** | 调的是账，不设「已同意待执行」的悬挂态（那需要超时清理，清理又要规则） |
| **不进统一待办队列** | 队列是「谁该发料」，调拨是「谁该点头」；混起来队列就不再一眼扫得完。改在队列页顶部横幅提示 |

**超管通道**：`material_pipeline_service.force_transfer()`（原 `commit_transfers`），跳过同意直接改 `manager`，留痕写 `ref_type = pipeline_forced`。「出一趟差三周、人不在岗的柜子不能一直锁着」——但代价必须显性。

### 5.4 两个实现要点

1. **一瓶都没转成 → 整单回滚。** 点了头但每瓶都失败（在借、瓶已删除），不能留一张「已同意」却没有任何一瓶易主的单——账上生效、实际没人拿到料，事后谁也说不清。实现是 `services/core/transfer_order_service.py` 里抛 `_NothingApplied` 走事务回滚。**部分成功则照常提交**，失败瓶标「执行失败」。
2. **CAS 没抢到 → 一行不写。** 抛 `_AlreadyAnswered`，页面提示刷新。

**为什么事务在数据层**：`business` 不许 import `db`（分层规则），而「改单据状态」与「改瓶的 manager」必须一起成立或一起不成立。解法是把事务放 `transfer_order_service.commit_answer()`，业务层传 `apply_line` 回调。

**明细必须拆到瓶**：建议里的 `lot_id` 可能是 `"A,B"`（一行动两瓶），落单时按瓶的顺序吃量拆成多行——不拆的话执行时只能写「A、B 共 100 g」，扣哪瓶扣多少全靠猜。落点 `_split_items()`。

## 6. 需求单兑付：粒度是「行」

`business/requirement_issue_service.py` 的 `issue(sheet_number, acceptance, operator, note="", selections=[下标])`。`acceptance` 是第一段受理结论（含逐瓶 picks），不能省略。

| 规则 | 为什么 |
|---|---|
| **逐行兑付** | 每次勾选若干行，生成一张独立借出单。整单置 `issued` 会静默吞掉没发出的项；停在 `submitted` 又按全量锁料 |
| **单头状态是行状态聚合** | issued（全发完）/ partial（发了一部分）/ submitted（一行没发） |
| **余量截断必须在服务端** | 按 `quantity − issued_quantity` 吃预算，前端算等于没算 |
| **借出即兑付** | 同一个动作里把需求单置 `issued`，兑付后退出学年保底 |
| **`IssueLine.picks` 必须一路带到底** | `lot_id` 的 `"A,B"` 串号拿不到每瓶量 |
| **`OPEN_STATUSES = ('submitted', 'partial')`** | 保底只算这两种，兑付后自动退出 |

**学年保底**（`services/demand_reserve.py`）：本学年 + `submitted` + 路由命中 + 排除当前单。算不出返回 `None` = 不锁料。学年边界 9/1 → 次年 9/1，唯一边界实现 `domain/academic_year.py`。

## 7. 本轮新增的数据表

只列本轮（组 / 双签 / 调配）新增的部分，完整表清单见 `db/database.py` 的 `init_tables()`。

### 7.1 组

```
work_group(id, name UNIQUE, kind, note, created_at)
work_group_member(id, group_name, person_name, created_at, UNIQUE(group_name, person_name))
```

`kind` 取值：教研室 / 科研组 / 其他。迁移 9.5 按 `person.department` 回填。

### 7.2 双签（两表各加五列，**追加末尾，不重排**）

```
controlled_flag INTEGER DEFAULT 0
second_approver TEXT
second_approval_status TEXT DEFAULT ''
second_approval_time TEXT
second_approval_remark TEXT
```

> **列顺序绝不重排**：项目里有 `SELECT *` 按位置取值的地方。新列只追加末尾，老库靠 `init_tables()` 幂等加列 + Python 回填（SQLite 的相关子查询 UPDATE 看不到被更新的表）。

### 7.3 调拨单

```
transfer_order(id, transfer_number UNIQUE, from_manager, to_manager, reason,
               origin_kind, origin_ref, status, requested_by, requested_at,
               respondent, answered_at, answer_remark, executed_at,
               forced, picked_up_at, note, created_at)

transfer_order_item(id, transfer_id, line_no, lot_id, substance_key, cas_number,
                    display_name, quantity, unit, line_status, note)
```

- 单号 `TR + 微秒时间戳`（与借出单 `BO` 同一做法：查表计数要加锁，撞号只是重试一次）。
- `reason`：缺口调配 / 手工借调 / 超管强平。
- `origin_kind`：`requirement_sheet` / `work_order` / `manual`。
- `forced = 1` 表示超管跳过同意。

## 9. 不变量清单（改代码前对照一遍）

改动碰这些地方时，逐条自问：

| # | 不变量 | 破了会怎样 |
|---|---|---|
| 1 | `Σ实发 + Σ缺口 ≡ 需求` | 账对不上，需求单永久卡在 partial |
| 2 | 第二段永不调受理人自己的料 | 自己调给自己，等于没调 |
| 3 | 教师不出现在任何瓶的 `manager` 上 | 保管权落到「使用者」身上，责任链断 |
| 4 | 归属判定用 `IN (...)` 不用 `=` | 科研组的单从待办里静默消失 |
| 5 | 空的归属按 `all`，且 SQL 要写 `IS NULL OR = ''` | 只写 `= 'all'` 会让历史单全部消失 |
| 6 | 第二签不覆盖第一签 | 「谁批的」写错 |
| 7 | `controlled_flag` 建单落库不重算 | 当年合规的单突然不合规 |
| 8 | 改派必须同步写归属（`reassign_approver`） | 「单上写甲、只有乙能批」的僵局 |
| 9 | 一瓶都没转成必须整单回滚 | 「已同意」的空单：账面生效、无人拿到料 |
| 10 | 明细必须拆到瓶（`"A,B"` 按序吃量） | 执行时扣哪瓶扣多少全靠猜 |
| 11 | 退回落点恒为 `person:申请人` | 单回到一个没人认领的池子，问题一个字没改 |
| 12 | 列顺序不重排，新列只追加 | `SELECT *` 按位置取值的地方全部错位 |
