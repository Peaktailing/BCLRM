## 0. 一句话结论

现在系统只回答「这瓶能不能借」，不回答「**这瓶现在在谁手上**」；而归还、用量归属、
可借性判定全都依赖后者。本设计在瓶上补这一条事实（`borrower` + `open_borrow_record`），
把「在借」从**临时标志**变成**可判定状态**，其余问题（错挂、重复借出、虚增库存）随之收敛。

## 1. 现状：五条互相打架的事实

### 1.1 瓶只有一个状态标志，没有持有人

`reagent_bottle.borrowable_flag` 取 `可借 / 已借出 / 耗尽 / 空瓶`。借出即整瓶置「已借出」，
但**不记录是谁借的**（`borrow_record.user` 有，瓶上没有指向它的指针）。

- `business/bottle_state.py:49` `borrowable_flag_on_return()`：**有量即可借**，不看有没有未结清记录。
- `business/bottle_state.py:66` `recompute_borrowable()`：只算「量 / 过期 / 报废」三要素，
  注释明确写着「不改写『已借出』」。

结果：**部分归还 → 瓶恢复可借 → 第二个人可以借走同一瓶**，而第一个人的领用记录还没结清。

### 1.2 归还是「绝对余量」，且按最新记录猜归属

`return_service.reagent_return(bottle_number, return_user, remaining_qty, ...)`：

- `remaining_qty` 是**归还后瓶里的绝对余量**，不是归还量；用量由
  `_resolve_pre_borrow_qty()` 反推（`business/return_service.py:55-76`）。
- 关联哪条领用记录？按 `borrow_time` 倒序取**最新一条**（`:157-178`）。
  瓶上没有任何信息能告诉它「这次归还属于哪笔借出」。

结果：A 的归还可能挂到 B 的领用记录上，改写 B 的 `linked_return_record_number`，
用量归属、责任人一起漂。

### 1.3 归还方向没有状态校验

`borrow_service.reagent_borrow` 有完整的状态机校验（可借、未报废、未过期、余量足够、二次刷新），
`return_service.reagent_return` **只校验瓶存在**。对一瓶「可借」的瓶调用它：

- 直接覆盖 `remaining_quantity`（填小=销毁库存，填大=凭空造库存）；
- 算出的负用量被 `max(0.0, ...)` 吞掉，不报错；
- `batch_return` 是公开 API，脚本/二次开发都能触发。

### 1.4 管控审批只建在工单层

`reagent_borrow` 命中管控名录后，只把「请及时补全审批手续」拼进成功消息
（`business/borrow_service.py:354-357`），照常扣库存写流水。

新主管线 `requirement_issue_service.issue`（第 231 行）直接调用的就是这个原语——
**需求单兑付可以不经过任何审批发出易制毒/易制爆试剂**。审计把它判为「中」，
是因为它按 0.8.15 的边缘 API 来估；对我们它是新主路径，必须按 P0 处理。

### 1.5 数量口径三处各算各的

| 位置 | 现状 | 问题 |
|---|---|---|
| `allocation_service._match_reagent` | CAS 或名称匹配，`take = min(remaining, need)` | 跨单位直接加减 |
| `purchase_service` | 按 `(名称, CAS, 单位)` 三元组 | 只有这里是对的 |
| `work_order_service:249,332` | 缺省领用量回退 `remaining_quantity or 0.1` | 0.1 无单位、无常量、无解释 |

`domain/units.py` 已经把量纲/单位/数量写成不可变值对象（`Unit` / `Quantity`，
跨量纲加减在类型层就写不出来），但**库存链路一处都没用**。

## 2. 模型：三种关系必须分开

| 关系 | 含义 | 存在哪 | 谁能改 | 变更方式 |
|---|---|---|---|---|
| **物质归属** | 这瓶是什么 | `chemical_info` | 化学品管理员 | 建档/合并 |
| **保管权**（custody） | 这批货归哪个管理员管 | `reagent_bottle.manager` | 管理员及以上 | 调配单（第二段平账） |
| **借用权**（borrow） | 这瓶现在在谁手上 | **新增** `borrower` + `open_borrow_record` | 借出/归还流程 | 借出单、归还单 |

三者**不能合并**。`manager` 是「谁负责」，`borrower` 是「谁拿着」：教师借走一瓶，
保管权仍在管理员，人却在教师手上。当前把「在借」塞进 `borrowable_flag`，等于用
一个布尔位表达三方关系，信息必然丢。

### 不变量（实现后必须成立）

| # | 不变量 |
|---|---|
| I1 | 一瓶同时最多一条未结清领用记录 |
| I2 | `open_borrow_record` 非空 ⟺ `borrower` 非空 ⟺ `borrowable_flag = 已借出` |
| I3 | `borrower` 与 `manager` 是两个人是常态；两者相等只发生在管理员自借 |
| I4 | 归还只能由未结清记录的领用人、或管理员及以上发起 |
| I5 | 需求单兑付的每一瓶借出，`borrow_order_item.requirement_line_id` 必须落值 |
| I6 | 管控试剂借出必须携带 `ApprovalRef`，否则拒绝 |
| I7 | 数量加减只在同一量纲内进行，`g` 与 `mL` 在类型层不可相加 |

## 3. 瓶级在借关系（B2 的确定解）

### 3.1 新增两列（追加到表末尾）

```sql
-- reagent_bottle 追加（列顺序绝不重排）
borrower            TEXT,   -- 当前借用人（在借时非空）
open_borrow_record  TEXT    -- 未结清领用记录号（borrow_record.record_number）
```

`borrow_record` 追加一列，用来表达「这笔借出结清了没有」：

```sql
settled_at  TEXT   -- 结清时间；NULL = 未结清
```

> 为什么不用 `linked_return_record_number` 判结清：严格模式下一次部分归还也会写这个字段
> （它记的是「最近一次归还」），拿它当结清标志会把未结清误判成结清。两件事必须两个字段。

### 3.2 生命周期

```
入库              borrowable=可借, borrower=NULL, open=NULL
  │
  ├─ 借出 reagent_borrow
  │     borrower=user, open=record_number, borrowable=已借出
  │
  ├─ 归还（结清）
  │     return_record 落库 → borrow_record.settled_at=now
  │     borrower=NULL, open=NULL, borrowable=recompute(量/过期/报废)
  │
  └─ 归还（未结清，仅严格模式 close_items=False）
        borrow_record.settled_at 仍 NULL
        borrower 不变, open 不变, borrowable 保持 已借出
```

### 3.3 判定规则（改哪里）

| 函数 | 现在 | 改成 |
|---|---|---|
| `borrowable_flag_on_return(qty)` | 有量即可借 | 删除该函数；可借性只由 `recompute_borrowable` 决定 |
| `recompute_borrowable(bottle)` | 三要素（量/过期/报废） | **四要素**：`open_borrow_record` 非空 → `已借出`（优先级高于「有量」） |
| `is_borrowable_now(bottle)` | 要求 flag=可借 | 不变（自动受益） |
| `reagent_return` 选记录 | 按时间取最新 | 取 `bottle.open_borrow_record`；为空则**拒绝**（`NO_OPEN_BORROW`） |
| `reagent_return` 状态校验 | 无 | 要求 flag=已借出 且 open 非空，否则 `BOTTLE_NOT_BORROWED` |

> 注意 `recompute_borrowable` 的既有约定「不改写已借出」要**反转**：新约定是
> 「有未结清记录就是已借出」。改动会影响 `expiry_service` 两处调用
> （`:128` 恢复正常、`:189` 批量同步），正好一并修掉审计 B7 的裸写问题。

### 3.4 为什么不用 GLM 的 M2/M3

- **M2（只加 `current_borrower`）**：能显示「在谁手上」，但无法回答「这笔还完没有」。
  归还仍要靠猜记录，B2 只修一半。
- **M3（lease 事件流水，可借性从流水推导）**：模型最干净，但要新建表 + 重算全库
  可借性 + 回填存量，成本远大于收益。**且我们已经有流水**——`borrow_record` 就是
  lease 流水，缺的只是「结清时间」这一列和「以它为准」的判定。补齐这两样，
  将来真要上事件溯源，`borrow_record` 可直接作为投影源，不需要第二次迁移。

## 4. 状态机与字段归属

### 4.1 瓶

| 字段 | 取值 | 谁写 |
|---|---|---|
| `borrowable_flag` | 可借 / 已借出 / 耗尽 / 空瓶 | 借出、归还、报废、过期同步（统一走 `recompute_borrowable`） |
| `borrowable_check` | 0/1 | 同上，与 flag 同事务 |
| `borrower` | 人名 / NULL | **只**由借出、归还结清写 |
| `open_borrow_record` | 记录号 / NULL | 同上 |
| `manager` | 人名 | 只管调配、入库指派，**任何借还路径都不碰** |

### 4.2 工单明细（`borrow_order_item`）

| 状态 | 含义 | 迁移条件 |
|---|---|---|
| 待归还 | 已借出、未提交归还 | 借出成功 |
| 已归还 | 已提交归还（默认模式：差额计使用量） | `return_items` |
| 执行失败 | 审批时该瓶已被借走/耗尽，从未借出 | 审批执行 |

规则不变，只补一条：**审批全部失败、工单退回待审批时，明细状态同步回退为「待审批」**
（审计 B9）。当前只恢复单头，明细留在「执行失败」，再从待审批列表驳回就被静默覆盖语义。

### 4.3 领用记录（`borrow_record`）

| 状态 | 判定 | 谁写 |
|---|---|---|
| 未结清（open） | `settled_at IS NULL` | 借出时插入 |
| 已结清 | `settled_at` 非空 | 归还结清时写 |

`linked_return_record_number` 语义收窄为「最近一次归还记录」，不再承担结清判断。

### 4.4 需求单行（`requirement_line`）

不动。`open / partial / issued` 与 `issued_quantity` 的粒度是对的（一行一项，
逐项兑付）。本设计只增加一条约束：兑付产生的每条 `borrow_order_item` 必须能
反查 `requirement_line_id`，用量统计才能落到行上（I5）。

### 4.5 谁在什么时候写哪个字段

| 动作 | 瓶 flag | borrower | open_record | 工单明细 | borrow_record | 需求行 |
|---|---|---|---|---|---|---|
| 借出 | 已借出 | 领用人 | 新记录号 | 待归还 | 新建，settled_at=NULL | 兑付时 issued_quantity += |
| 归还（结清） | recompute | NULL | NULL | 已归还 | settled_at=now | 不变 |
| 归还（未结清） | 已借出 | 不变 | 不变 | 待归还 | 不变 | 不变 |
| 归还（空瓶） | 空瓶 | NULL | NULL | 已归还 | settled_at=now | 不变 |
| 报废 | 空瓶 | 必须已是 NULL | 必须已是 NULL | — | — | — |
| 调配 | 不变 | 必须是 NULL | 必须是 NULL | — | — | — |

## 5. 表结构变更（只追加，不重排）

| 表 | 新增列 | 说明 |
|---|---|---|
| `reagent_bottle` | `borrower TEXT`、`open_borrow_record TEXT` | 追加在 `rev` 之后 |
| `borrow_record` | `settled_at TEXT` | 追加在末尾 |

无新表、无索引变更。`init_tables()` 走既有幂等加列机制（`PRAGMA table_info` 探测 +
`ALTER TABLE ADD COLUMN`），再跑一次 Python 回填（SQLite 的相关子查询 UPDATE 看不到
被更新的表，回填必须是 Python 循环，不能写成一条 SQL）。

### 回填顺序（脚本幂等，可重跑）

1. `borrow_record.settled_at`：有 `linked_return_record_number` 的，取对应归还记录的
   `return_time`；没有的，**仅当瓶当前是「已借出」时保持 NULL**，其余按 `borrow_time` 结清。
   目的：不让历史流水一半变成「未结清」。
2. `reagent_bottle.borrower/open_borrow_record`：对当前 `borrowable_flag=已借出` 的瓶，
   找该瓶 `settled_at IS NULL` 的最新一条记录回填；找不到的留空并在报告里列出来
   （这类瓶是历史脏数据，需要人工确认）。
3. 对账：`已借出瓶数 == open 记录条数`。不等就输出差异清单，**不自动修**。

## 6. 四条写路径的改造

### 6.1 借出 `reagent_borrow`

```python
reagent_borrow(bottle_number, user, borrow_qty, *,
               approval: ApprovalRef | None = None,
               course_id=None, item_id=None, dry_run=False)
```

- 条件更新里增加 `open_borrow_record IS NULL` 作为前置条件（现在是
  `borrowable_flag + remaining_quantity` 双条件），杜绝「同一瓶两笔在借」；
- 同一事务内写 `borrower` / `open_borrow_record`；
- 管控试剂缺 `approval` → 返回 `CONTROLLED_APPROVAL_REQUIRED`，**不写任何数据**。

### 6.2 归还 `reagent_return`

```python
reagent_return(bottle_number, return_user, remaining_qty, *,
               settle: bool = True, skip_expiry_check=False, as_empty=False)
```

- 记录来源改为 `bottle.open_borrow_record`，不再按时间猜；
- `open_borrow_record` 为空 → `NO_OPEN_BORROW`（现在这个错误只在「一条记录都找不到」时抛）；
- 瓶不是「已借出」→ `BOTTLE_NOT_BORROWED`（B3）；
- `settle=True`（默认，等价于 `close_items=True`）：写 `settled_at`，清 `borrower/open_record`；
- `settle=False`（严格模式）：只写归还记录，瓶保持已借出；
- `batch_return` 逐个走同一入口，不再有旁路。

### 6.3 工单归还 `return_items`

- **整段包进外层 `db.transaction()`**（B1）。嵌套 SAVEPOINT 已支持，照抄 `approve_order`；
- 计算 `settle`：`close_items=True` → True；否则 `new_returned >= borrow_qty`；
- 失败/异常时明细与单头一起回滚，不再出现「瓶已回库、明细还待归还」。

### 6.4 需求兑付 `requirement_issue_service.issue`

- 已有外层事务（第 228 行），保持；
- 逐瓶调用时透传 `approval`（受控行必须有审批，否则整行不兑付并写进 `skipped`）；
- 兑付生成的 `borrow_order_item` 必填 `requirement_line_id`（现在已写，补测试固化）；
- 同一瓶在同一年被第二次兑付时，因 I1 天然不成立（瓶在借中不可借），
  错挂窗口消失；若第一次已结清，则走正常新纪录。

### 6.5 调配与报废（新增拒绝规则）

| 动作 | 条件 | 行为 |
|---|---|---|
| 调配 `manager.transfer` | 目标瓶 `open_borrow_record` 非空 | 拒绝：`BOTTLE_ON_LOAN`（先结清再平账） |
| 报废 | 目标瓶 `open_borrow_record` 非空 | 拒绝（在借瓶不能报废，走「空瓶归还」） |
| 批量调配 `/ 批量报废` | 同上 | 逐瓶跳过并汇报原因，不整批失败 |

理由：保管权流转是「这批货归谁负责」，人在外面拿着货时把责任转给别人，
账面上谁也说不清。

## 7. 管控审批防线（B5）

### 7.1 审批引用值对象

```python
@dataclass(frozen=True)
class ApprovalRef:
    approval_no: str          # 审批单号（纸质/线上均可，必须可追溯）
    approver: str             # 审批人
    approved_at: str          # 审批时间
    attachment: str | None    # 审批材料路径（已有附件存储可复用）
```

放在 `domain/`（无宿主依赖），由 `business/` 组装。

### 7.2 防线位置

| 层 | 职责 |
|---|---|
| `reagent_borrow`（原语） | **强制**：命中管控名录 → 必须有 `ApprovalRef`，否则拒绝 |
| 工单 `create_order` / `approve_order` | 收集审批单号、校验审批人角色，把 `ApprovalRef` 传下去 |
| 需求单兑付 | 受控行必须有审批号；没有则该行不兑付，写进 `skipped` 说明 |
| `borrow_record` | 落 `approver` / `approved` / `approval_file`，成为事后追溯的唯一凭据 |

> 这是「纵深防御」而非「双份规则」：原语层只判断「有没有审批引用」，不判断
> 「谁能审批」——后者留在 `permission_service`，避免两处各写一份角色表。

### 7.3 兼容

- 历史 `borrow_record` 里 `is_controlled=1` 但 `approver` 为空的，保持原样，不追溯；
- 新写入一律强制；
- 现有测试里直接调 `reagent_borrow` 造数的用例，需要显式传 approval 或改用非管控试剂。

## 8. 数量口径（B6）

### 8.1 规则

1. **聚合键 = `(substance_key, unit)`**。不同单位不聚合、不加减。
2. 同一量纲内的换算（g↔mg、mL↔L）走 `domain/units.py` 的 `Unit.to_base`，
   换算后再比；跨量纲（g↔mL）**直接拒绝**，需要密度/分子量的换算不进库存账。
3. 页面显示永不带「裸数字」：`Quantity` 格式化统一出口。
4. 缺省领用量不再回退 0.1：工单必须显式给量+单位，缺省不填 → 校验失败。

### 8.2 三处改动

| 位置 | 改法 |
|---|---|
| `allocation_service._match_reagent` | 匹配键加单位；`take = min(...)` 改为 `Quantity` 运算，量纲不同直接跳过并记原因 |
| `purchase_service` | 已按三元组，改为复用 `parse_unit` 归一后比较，避免 `g` / `克` 被当两种 |
| `work_order_service` | 删除 `or 0.1` 回退；未填量 → `MISSING_QUANTITY` |

### 8.3 边界

数据库仍存 `REAL + TEXT`（不改列类型，不动存量数据）。`Quantity` 只在
「算的时候」和「显示的时候」存在，落库前 `to_float()`。这是刻意的：
改列类型会牵动四库、视图、报表，收益不抵风险。

|---|---|
| 在借关系 | 借出写 borrower/open；归还结清清空；严格模式部分归还保持已借出；一瓶两借被拒 |
| 归还归属 | A 借→部分还→B 借→A 再还，必须落到 A 的记录；无未结清记录时拒绝 |
| 状态校验 | 对可借瓶归还被拒；对耗尽瓶归还被拒；空瓶归还置空瓶+待报废 |
| 可借重算 | open 记录非空时有量也不可借；过期/报废优先级；结清后恢复可借 |
| 事务 | 明细回写前注入失败，重放不虚增库存；工单状态与明细一致 |
| 审批 | 管控试剂无 approval 拒绝；有 approval 落 approver；非管控不要求 |
| 单位 | g 与 mL 聚合被拒；g 与 mg 正常换算；缺省量缺失报错 |
| 回填 | 造老库（无新列）→ 加列 → 回填 → 对账恒等式成立 |

并发用例先做「条件更新失败必须回滚」这一条（单线程可测），多线程压测放 A1 那批。

## 11. 并发模型（A1）：读分离、写收敛、队列留位

本文的字段与状态机不依赖并发模型，但**A1 的落点会决定本文四类改造能不能统一**，
所以一并定下来。结论先说：**串行点在 `_lock`，不在 SQLite；先做读分离，再做写收敛，
队列暂时不做、只把接口留出来。**

### 11.1 现状：一把锁把读也管住了

| 事实 | 位置 |
|---|---|
| 每个库只有**一条**连接，被所有 Streamlit 会话线程共用 | `Database._instances` 单例 + `check_same_thread=False` |
| `transaction()` 整段临界区持 `RLock` | `db/database.py:1650` |
| `execute_query` / `execute_update` / `execute_insert` 抢**同一把** `RLock` | `db/database.py:1688 / 1710 / 1737` |

所以真实表现不是「一次只服务一个人」，而是：**只要有一个人在写事务里，全站连只读
页面都在门口等**。一个人点「批准并执行」（批量借 N 瓶）、导入课程、跑批量调配时，
别人的看板也转圈。

### 11.2 实测：SQLite 允许读与写并行，只不允许两个写

WAL 模式、写事务已 `BEGIN IMMEDIATE` 但未提交，其他连接同时操作：

| 动作 | 结果 |
|---|---|
| 只读连接 `SELECT` | **立刻返回旧值，0.1 ms**（不被阻塞） |
| 普通连接 `SELECT` | 同上 |
| 第二个写者 `BEGIN IMMEDIATE` | 等满 `busy_timeout` 后 `database is locked` |
| 前一个提交后，第二个写者 | 0.6 ms 成功 |

结论：**读本来就能并行，是我们自己把它们排成了一队。** SQLite 的单写者约束改不掉，
但读侧的串行是自找的。

### 11.3 三层，按收益/风险排序

**L1 读分离（必做，只改一个类）**

- 每个线程持一条只读连接（`file:<path>?mode=ro`，线程本地缓存，不复用主连接）。
- `execute_query` 分流：**当前线程有活动写事务 → 走主连接**（必须读到自己未提交的写）；
  否则走线程本地只读连接。
- `_lock` 只保护写路径（`transaction` + 三个 `execute_*` 的写分支），读不再抢锁。
- 业务代码**零改动**。

代价：跨语句读不再天然一致。实测：先读 A 表、中间别的事务提交、再读 B 表，
会拿到 `a0 / b1` 这种**混合快照**；包一层 `BEGIN DEFERRED` 后两次读都落在同一快照。

这个代价要正视：现在被全局锁**掩盖**了——所有读被排成一队，反倒"看起来一致"。
读分离会**暴露**它。所以 L1 必须同时提供 `read_transaction()`，把"一次请求读多张表"
（查瓶 → 查在借记录 → 查需求行）显式包起来。本文 §3.3 的可借性判定正好是这种多表读。

**L2 写收敛（建议做，与本文 S1–S6 并行）**

一个入口 `write_gateway.submit(operation, fn, *, user, timeout)`，同步执行，内部统一：

| 统一的事 | 现在散在哪 |
|---|---|
| `transaction()` 边界 | 18 处 `with ...transaction()`，散在 9 个文件；`return_items` 一处都没有（B1） |
| `permission_guard.enforce_write` | 各服务自己调，忘了就没人管（S2 fail-open 的根源） |
| 用户身份 | `user_context` ContextVar，靠视图层每次 `set_user()` |
| 耗时 / 影响行数 / 慢写告警 | 无 |

接口故意做成 `submit()`，**将来换队列，调用方一行不用改**。

**L3 写队列（暂不做，只留接口）**

用户提的「一个中台专门写、其他业务排队进池、它一个一个写完返回」方向是对的，
但要分清它买的是什么：

| 它买得到 | 它买不到 |
|---|---|
| FIFO 公平（不再抢锁的随机顺序） | **写吞吐**——SQLite 本来就一个写者 |
| 队列长度 / 排队时长可观测 | 读的并发（那是 L1 的事） |
| 超时、限流、慢写定位到人 | 更短的数据库锁持有时间 |

不现在做的三个具体理由：

1. **ContextVar 不跨线程。** worker 线程拿不到调用方的 `user_context`，必须显式搬运。
   一旦漏搬，写操作会以 `role=None` 执行——而在 S2 改成 fail-closed 之后，
   这条路径要么被拒（功能挂掉），要么被当成 `system` 放行（**比 fail-open 更危险**）。
2. **异步结果要改界面。** 同步写是「点一下 → 转圈 → 出结果」，与 Streamlit 的执行模型
   一致；队列化后变成「已提交 → 轮询 → 可能失败」，而现有 46 处 `st.rerun()` 全是
   同步假设（Q1 那批活）。先做队列等于把两件难事绑在一起。
3. **触发条件还没到。** 教学场景并发低、事务多为秒级。L2 会记录排队时长；等 P95
   超过 2 s 或出现长队，再换 worker，那时只是换 `submit()` 的实现。

### 11.4 队列不做业务判断（这条即使不建队列也要守住）

队列里只能放「**已经决定要做的命令**」，不能放「试试看能不能做的请求」。

管控审批（本文 §7）、可借性（§3.3）、余量截断（§6.4）都必须在提交前判定完。
否则用户点完按钮看到「已提交」，两秒后才知道「受控试剂缺审批」——在教学场景里，
这比慢更糟。

### 11.5 与本文其他部分的关系

- S1–S6 不依赖 L1/L2，可以先走；L1 只改 `db/database.py`，与字段/状态机零耦合。
- **唯一交叉在 S4**：管控审批下沉到 `reagent_borrow` 后，若没有 L2，18 处写入口仍各写
  一遍权限与事务。建议 S4 之前先落 L2 的骨架（只做同步版，不含队列）。

## 13. 判定与冲突：预检是建议，事务内是事实

用户提出的问题：两个人各自预检，看到同一份库存、抽出同一瓶；只有一瓶时，
第二个人提交会怎样？

### 13.1 先把问法校准：库存模型还是实例模型

| | 总量模型 | 实例模型 |
|---|---|---|
| 计数单位 | mL / g | 瓶（唯一编号） |
| 会超卖吗 | 会，扣成负数 | 不会，物只有一件 |
| 冲突表现 | 库存扣穿 | 两个人以为能拿到同一瓶 |
| 典型系统 | 电商 SKU 库存 | 图书馆的每一册、12306 的每个座位 |

**我们已经是实例模型**：每瓶有唯一瓶号与条码，`reagent_borrow` 里有
`is_borrowable` 校验、借出即置「已借出」（`borrowable_flag_on_borrow`）。
所以本系统**不会超卖**。

问题因此降级：不是「账算错」，而是「**承诺不一致**」——两个人得到的答复都是
「能拿到 #1」，只有一个人真拿到。

### 13.2 三层判定

| 层 | 时机 | 算什么 | 准不准 |
|---|---|---|---|
| 预检（advisory） | 页面渲染 | `ShelfPolicy.pick()` 抽卡给人看 | 会过期，**只是建议** |
| 权威判定（authoritative） | 写事务内，已 `BEGIN IMMEDIATE` | **重抽一遍** + 复核可借、余量、保底 | 唯一算数 |
| 执行 | 同一事务 | 扣量、写借出、置状态、结行 | 失败整段回滚 |

「在写管线之前判断能不能执行」这句话，前半对、后半要改：预检必须有（否则人填完
一屏表单才发现做不了），但**预检不能当判定用**。判定只有一次机会算数，就是持有
写锁的那一刻。

### 13.3 现在实际会发生什么（已核代码）

| 事实 | 位置 |
|---|---|
| `_plan()` / `_allocate()` 在 `with transaction()` **之外**执行 | `requirement_issue_service.py:208` vs `:228` |
| `_allocate` 只查瓶存在，**不查 `borrowable_flag`** | `:475` |
| `reagent_borrow` 在事务内查 `is_borrowable` | `borrow_service.py:124` |
| 兑付整段在一个事务里 | `requirement_issue_service.py:228` |

推演结果：

- 两个人抽到 #1 → A 先进事务、置「已借出」、提交；
- B 进事务后 `is_borrowable` 失败 → 抛错 → **整单回滚**；
- 账面不会错（不会两人分一瓶），但 B 看到的是「试剂瓶不可借出」，指向瓶号而
  不是「这瓶刚被拿走了」，而且他要重新抽卡、重新勾选、重来一遍。

**结论：数据是对的，体验是错的。** 用户担心的「两人分一瓶」不会发生，
「白忙一场」会发生。

### 13.4 三条路

| 方案 | 现实中的对应 | 冲突时 | 采用 |
|---|---|---|---|
| 事务内重算 + 对账 | 图书馆：每册书借出即绑借阅人，别人看到的就是「已借出」 | 抽到别的瓶就发别的，回执说明换了哪瓶 | **兜底**（见 §14） |
| 版本号 CAS | 电商扣库存；本仓已有 `reagent_bottle.rev` | 影响 0 行 → 报「已被动过」 | 受控试剂 |
| 预占 hold（超时释放） | 12306 锁座 15 分钟 | 根本不冲突 | **不做**（见 §14.3） |

**这一节的定位后来变了。** 本章原本假设「用户直接借出」，所以把「事务内重算」
当主方案。但业务前提是**领用要经管理员确认**（§14.1），用户不碰瓶，冲突从源头
就不成立。所以这条现在是「管理员点确认那几秒」的兜底，不再是主方案。

**为什么不选预占**：预占防的是「用户慢慢挑、期间被别人拿走」。我们的用户不挑瓶
（只说要多少），没有这个过程。真要说「锁」，该锁的是**单**不是瓶（§14.3）。

**为什么受控试剂用 CAS 而不是重算**：受控试剂要拍照取证，照片和瓶必须对得上。
自动换瓶会让「照片里的瓶」和「回执上的瓶」不一致，等于证据链断了。所以这种情况下
宁可拒绝，让人重来。

### 13.5 落点

本批（S2 范围内）做三件小事：

1. `_plan` / `_allocate` **复核 `borrowable_flag`**，不可借的瓶记进 `skipped`
   并给出人能看懂的提示（「#1 刚被 X 借走」），不再硬塞进 plan；
2. 复核挪进事务：`_plan` 现在在事务外，等于判定不作数。至少把「瓶是否仍可借」
   这一步放进 `with transaction()` 内；
3. 回执加 `changed` 字段，页面醒目显示「原抽 #1，实发 #2」。

不本批做、但方向已定的一件事：**提交意图，不提交瓶号**。现在 `Acceptance` 带着
逐瓶 `picks` 从页面传到服务端，等于页面替服务端做了决策，服务端只能"照单扣"。
改成提交 `(物质, 数量, 约束)`、服务端在事务内抽卡，冲突就自然消失了——因为
第二个人在事务里抽到的本来就是剩下的。这要改 `intake → Acceptance → issue` 三段
接口，建议 S2 落地、状态机稳定之后再评估。

### 13.6 这件事要不要调研

不用。座位预占、库存扣减、馆藏借阅这三类问题，业界解法已经收敛成上面三种，
差异只在「**什么时候占**」：写的时候占（CAS）、写之前占（hold）、写之后按实际
重算（reconcile）。真正要定的是我们自己的业务语义——**借出是即时动作还是可预约**。
定了这个，方案就唯一。我们的是即时动作，所以选 reconcile + CAS 兜底。

## 14. 业务队列：申请与出库分开

§13 的结论是「事务内重算」。这一节换个前提重问：**用户根本不该直接借出**，
那 §13 的整个冲突场景就不成立了。这不是技术优化，是把业务前提摆正。

### 14.1 前提：领用要有人管

领试剂不是药房下单、商铺付款。教师说「我明天要用 5 mL 乙醇」，不等于「现在就把
3 号瓶划给他」。中间必须有**管理员确认发料**这一步——发哪瓶、发多少、什么时候发，
是管理员在事发现场判断的。

这个前提一立，§13 的竞态自动消失：**用户提交的只是申请，从来不碰瓶**。两个人
同时提交，拿到的是两张排队中的申请单，不是「都以为能拿 3 号瓶」。

我上一轮（§13）的方案是在「用户直接借」这个错误前提下打补丁，补丁本身没错，
但前提错了就不需要打了。

### 14.2 现状：队列已经存在，但是有两条

| 队列 | 表 | 排队标志 | 谁在用 |
|---|---|---|---|
| 零星领用 | `borrow_order` | `approval_status='待审批'` | 一两次、临时要 |
| 实验需求 | `requirement_sheet` | `status in ('submitted','partial')` | 整门课/整套实验的批量领料 |

两条都走「申请 → 审批 → 借出」，但数据结构不同，**管理员要跑两个页面才看得全**。
所以「唯一排队」的第一步不是加锁，是**先让它们在同一个列表里出现**。

还有一个不对称：

| 路径 | 申请时带不带瓶 |
|---|---|
| 需求单 | **不带**——`requirement_line` 只有物质 + 数量，瓶在 `intake` 时抽 |
| 工单 | **带**——`borrow_order_item.bottle_number` 是申请人在购物车里自己选的 |

也就是说：需求单路径已经符合「只说你要啥」，**工单路径是自助售货**。要改的是后者。

### 14.3 归属先于抢占：单据本来就有主

教师提交的是「这门课的实验需求」，业务上归那门课的受理管理员；教研室提交的工单
也指定了提交人。**大多数单在创建那一刻就有主，不需要抢。**

「谁能看到这批单」是数据问题，「谁能抢先拿到」是并发问题。**有主的单根本不该出现在
别人的待办里——先把归属做对，就没有抢这回事。**

| 单据 | 有没有主 | 归属从哪来 | 现状 |
|---|---|---|---|
| 课程领用工单 | **有** | 课程 → `custodian_route` | 待办页不分人，全院混在一起 |
| 实验需求单 | **有** | `source_code` 命中路由 | 同上；算出的 custodian 只在内存里 |
| 教研室工单 | **有** | 提交时指定 | 同上 |
| 零星领用工单 | 无 | 谁都能接 | 公共池，**只有这里需要认领** |

所以真正会撞的只剩两种，而且都不是「抢瓶」：

| 情况 | 本质 | 解法 |
|---|---|---|
| 同一管理员开两个标签页，各确认一次 | **重复提交**，不是抢夺 | 单据状态机（已 issued 就拒绝） |
| A 请假，B 顶上处理 A 的单 | 业务动作「**转交**」，不是抢占 | 改 `custodian` + 记日志，显式动作 |

### 14.4 归属算得出，但没落库（已核代码）

路由这一环其实早就写好了，而且写得挺完整：

| 已有 | 位置 |
|---|---|
| `custodian_route` 表（`scope_type` = course / project / department / person） | `db/database.py:906` |
| 四种路由实现（Static / Source / Department / Composite） | `capabilities/circulation/routing.py` |
| `RoutingError`：配不出人就显式失败，不随便兜 | 同上 |

但 `stage1.plan()` 第 67 行拿到 `custodian` 之后，只用来 `ledger.subset(custodian)`
筛「这个人名下有什么可发」，**没有回写到任何单据**。

于是：

| 表 | 有的字段 | 缺的字段 |
|---|---|---|
| `requirement_sheet` | `requester`（申请人）、`issued_by`（发料人） | **`custodian`（该谁受理）** |
| `borrow_order` | `applicant`、`approver`（谁批的，建单时为空）、`created_by` | **`custodian`（该谁批）** |

`approver` 不是归属——它是「事后记下谁点的批准」，建单时是空的，所以管理员打开
待办页看到的是**全院所有待批单**，而不是「我的」。

要补的不是锁，是**两个字段 + 一次过滤**：

```
requirement_sheet.custodian   提交时由路由算出并落库；算不出 → 拒绝提交
borrow_order.custodian        建单时落；零星领用留 NULL = 公共池
待办视图                       WHERE custodian = 当前用户 OR custodian IS NULL
```

算不出就拒绝，`routing.py` 那个 `RoutingError` 已经是这个语义（「请先在保管人路由里
配上这门课归谁管」）。这条比「随便找个人兜底」重要：**断掉的账本比空账本更危险**。

### 14.5 「时间 = 0」落在 `needed_at`，不落在锁上

用户提的「实时和预约走同一条路，只是有时间」，落点不是预留到期，而是**需求时间**：

```
申请单(needed_at, status)
   实时领用：needed_at = 现在
   预约领用：needed_at = 明天 9:00
```

两者走完全相同的路径，区别只有一个字段。**不需要 `reserved_until`**——申请本身
不占瓶。占料的只有保底（`DemandReserve`），它算的是「这张单要多少量」，不是
「锁了哪几瓶」。

好处：不用给实时场景引入超时释放的复杂度，也不用维护两套流程。队列排序按
`needed_at` 升序 + 提交时间，预约单自然排在后面。

### 14.6 认领只在无主单上才有意义

只有 `custodian IS NULL` 的单（零星领用）需要抢。这时一条带条件的 UPDATE 就够：

```python
def claim(order_id: int, operator: str) -> ServiceResult:
    changed = db.execute_update(
        "UPDATE borrow_order SET custodian=?, claimed_at=? "
        "WHERE id=? AND custodian IS NULL",
        (operator, now(), order_id),
    )
    if changed == 0:
        return ServiceResult.fail("这张单已被别人接走", error_code="ALREADY_CLAIMED")
```

关键点：**认领不需要事务，也不需要超时租约**。`WHERE custodian IS NULL` 就是乐观锁，
`rowcount=0` 就是「别人先到」。判定和写入在同一条 SQL 里，中间没有窗口。

刻意不加租约：加了就要定时扫描回收、要处理「管理员关页面走人」、要区分「在办」和
「挂着」。而**认领之后这张单就归属于他**——人走了单留着，本来就是他要负责的事；
真需要换人，走「转交」，是显式动作。租约解决的是「临时占位」，我们没有占位。

### 14.7 为什么不在「选中瓶」时加状态锁

「我选中某瓶试剂，后台就同步状态锁」——这个想法本质是 hold 预占。**不做**，三个理由：

**一、「选中」不是业务意图，是渲染副作用。** Streamlit 每次 widget 交互都会 rerun，
展开折叠、切 tab、改下拉，都可能让某一瓶重新出现在「当前选中」的位置。服务器分不清
「我在看」和「我要发这瓶」。让渲染动作去改数据库状态，是最容易写出幽灵锁的写法。

**二、锁漏的代价高于撞瓶。** 管理员接个电话走开二十分钟，瓶锁着，别人拿不到，库存页
还得显示「已锁定」；为此要加超时回收、异常解锁、进程重启清锁、崩溃残留清理。一个人
管几百瓶，**锁漏的概率远高于真撞**——而且撞瓶最多是重抽一次，锁漏是「这瓶明明在架上
却谁都发不出去」。

**三、判定点应该在写，不在选。** 这个机制我们已经有：`reagent_bottle.rev` +
`update(..., expect=rev)`。

```sql
UPDATE reagent_bottle
   SET borrowable_flag = 0, rev = rev + 1
 WHERE bottle_number = ? AND borrowable_flag = 1 AND rev = ?
```

`rowcount = 0` 就是「这瓶刚被动过」，报错让人重抽。**锁是预防，可能漏；条件是判定，
不会漏。**

| | hold 预占 | CAS 条件更新 |
|---|---|---|
| 什么时候占 | 选中时 | 写入时 |
| 需要超时释放 | 要 | 不要 |
| 锁漏了会怎样 | 瓶被冻结，谁都发不出去 | 不存在这个状态 |
| 撞了以后 | 别人看不到 | 报错 + 重抽，人就在现场 |
| 我们的成本 | 新表 + 定时清理 + 每处交互都判断 | 一条 `WHERE` |
| 什么时候才需要 | 用户自己挑瓶、挑完隔很久才付款 | 我们的场景 |

**受控试剂更不能 hold**：要拍照取证，照片必须和瓶对得上。锁着反而更危险——管理员
以为锁住了，实际拍的是另一瓶，回来发现锁的那瓶早被人拿走。CAS 直接失败，照片和回执
就不会脱节。

### 14.8 三道防线，都不需要租约

| 防线 | 时机 | 防什么 | 冲突时 |
|---|---|---|---|
| 归属过滤 | 打开待办 | 不该我处理的单不出现 | 看不到，无感 |
| 单据状态机 | 点「确认发料」 | 同一张单被确认两次 | 单已 `issued` → 提示「这张单已处理」 |
| 条件更新 | 写每一瓶 | 抽完卡到确认之间被拿走 | `rowcount=0` → 「3 号瓶刚被 X 发走」，重抽 |

三道防线**都不需要新表、不需要定时任务、不需要租约**。§13 的 reconcile 退到最后一道：
只有前两道都漏过去（同一人双开 + 恰好同秒）才会触发。

### 14.9 用户看「有没有」，管理员看「哪瓶」

| 角色 | 看到什么 | 为什么 |
|---|---|---|
| 教师 | 「乙醇：现有 80 mL，可满足」 | 不填单才发现没货；但不给瓶号，避免「看到就是承诺」 |
| 管理员 | 抽卡结果（3 号瓶 40 mL + 5 号瓶 40 mL） | 发料要具体到瓶，还要对得上照片 |

这个信息分层同时消掉了落差：用户从来没看到「第 3 瓶」，就不会有「说好的 3 号瓶
怎么变成 5 号了」。

### 14.10 与现有切片的关系

| 阶段 | 内容 | 依赖 |
|---|---|---|
| S9a | 队列视图 `v_issue_queue`（两表 union）+ 统一待办页，**先全院可见、标出归属人** | 无（纯读） |
| S9b | 两表加 `custodian`（追加末尾）+ 提交/建单时由路由落库 + 待办按人过滤 + 转交动作 | S9a |
| S9c | 零星领用公共池的认领（仅 `custodian IS NULL`）+ `needed_at` | S9b |

然后按人过滤。S9c 只覆盖零星领用那一小撮。S9d 是行为变更（申请人不再挑瓶），单独评估。
