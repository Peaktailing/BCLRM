# BCLRM 部署与运维说明

本文是 Stage 0B 发布/备份工具链的运行手册，对应
`docs/环境隔离与发布规划_执行版.md` 的 D01–D22。所有命令默认只读或 dry-run；
真正改生产必须显式加 `--execute`，prod 还必须同时具备 `--confirm-prod` 与
`--service-stopped`。

- 部署根：`/home/biochm/BCLRM`
- prod：`current_prod -> releases/<version>`，`127.0.0.1:8501`
- beta：`current_beta -> releases/<version>`，`127.0.0.1:8601`
- 运行时：Python **3.10.12**，每个 release 自带 `.venv`
- 事实源：`release.json` + `releases-index.json` + `deployments/<env>.json`
- 退出码：`0` 成功；`2` 预检/契约不满足；`3` 执行阶段失败

> 本阶段只交付工具、unit/timer 模板和测试，不启用、不启动任何 unit，也不触碰
> 现有 `/home/biochm/Reagent-manager` 生产进程。

## 1. 首次准备（Stage 2 前由负责人执行）

1. 确认 `python3 --version` 为 `3.10.12`，根分区可用空间不低于 5 GiB。
2. 建立目录并放置环境文件（env 文件不得含明文密码）：

   ```bash
   mkdir -p /home/biochm/BCLRM/{releases,data,backups,config-backups,env,acceptance,deployments,logs,wheelhouse}
   chmod 700 /home/biochm/BCLRM/env
   # env/prod.env、env/beta.env 由负责人按 3.2 节填写：
   # BCLRM_ENV / BCLRM_DATA_DIR / BCLRM_RELEASE_FILE / BCLRM_MOBILE_UI=0
   ```

3. 第二副本挂载点 `/media/biochm/3696A6CB96A68B47` 必须已挂载且可写；
   未挂载时备份会显式失败，不会静默跳过。
4. 部署 unit 时只复制到用户目录，不自动 enable：

   ```bash
   mkdir -p ~/.config/systemd/user
   cp systemd/user/*.service systemd/user/*.timer ~/.config/systemd/user/
   systemctl --user daemon-reload
   ```

   需要开机自启时由负责人决定是否 `loginctl enable-linger biochm` 并
   `systemctl --user enable --now bclrm-prod.service`。beta 与备份 timer
   同理，均由负责人逐项确认后再启用。

## 2. 构建不可变 release

```bash
python3 scripts/build_release.py \
  --root /home/biochm/BCLRM \
  --repo /path/to/BCLRM/git-repo \
  --version 0.8.19.1 \
  --sha <完整40位sha>
```

构建行为：

- 只从 git 归档**已跟踪文件**；断言 `docs/用户使用手册.md`、
  `.streamlit/config.toml`、非空 `assets/` 必须存在。
- 由当前 3.10.12 解释器生成 `payload/requirements.lock`，并收集离线
  wheelhouse；先查本地 pip 缓存与 `--wheelhouse-cache`，缺失时才联网。
  `--offline` 下缺 wheel 直接失败并列出缺失项。
- 计算 payload 树哈希（路径 + 内容 + 可执行位，符号链接按目标字符串），
  写 `releases/<version>/release.json`。字段固定为 version、git_sha、
  artifact_sha256、python_version、requirements_lock_sha256、
  schema_versions、built_at；**不含 channel**。
- 版本号必须是四段纯数字且全局不可复用；`releases-index.json` 或已有
  目录命中即拒绝，即使目录已被保留策略清理。
- 最后按 lock 建 `.venv`。`--skip-venv` 只允许测试使用，真实发布禁止。

构建成功后检查：

```bash
python3 scripts/release_status.py --root /home/biochm/BCLRM --verify-artifacts
```

## 3. 备份

四库使用 SQLite online backup API，库在前、附件在后；附件包记录文件数、
sha256 与索引引用，索引指向的文件缺失即整次备份失败，多余物理文件只记为
孤儿。每份快照包含四合一 manifest、逐文件哈希、user_version、行数、关键
聚合与 schema 快照，并在落盘后自校验。

```bash
# 每日热备（timer 也会调用）
python3 scripts/backup.py --root /home/biochm/BCLRM --env prod \
  --kind daily --mode hot --source manual \
  --second-copy-root /media/biochm/3696A6CB96A68B47/bclrm-backup

# 升级前/回滚冷备：调用方必须先停服，并显式声明
python3 scripts/backup.py --root /home/biochm/BCLRM --env prod \
  --kind pre_change --mode cold --service-stopped --source manual

# 半月档从最近已验证每日快照复制
python3 scripts/backup.py --root /home/biochm/BCLRM --env prod \
  --kind semimonthly --copy-latest-from daily --source timer
```

目录为 `backups/<env>/{daily,semimonthly,pre_change,annual}`；beta 只用
`daily`。`--dry-run` 只打印计划，`--json` 输出机器可读摘要。成功后更新
`backups/<env>/last_verified.json` 与 `logs/cron_status.json`。

校验与恢复：

```bash
python3 scripts/verify_backup.py --snapshot /home/biochm/BCLRM/backups/prod/daily/<id>
python3 scripts/verify_backup.py --root /home/biochm/BCLRM --env prod --latest

# 先 dry-run 看目标与动作
python3 scripts/restore.py --root /home/biochm/BCLRM \
  --snapshot <快照> --env prod --target /home/biochm/BCLRM/data/prod/restored

# prod 真正恢复：目标必须是 data/prod 下的绝对路径，先停服
python3 scripts/restore.py --root /home/biochm/BCLRM \
  --snapshot <快照> --env prod --target /home/biochm/BCLRM/data/prod \
  --confirm-prod --service-stopped --replace --execute
```

恢复顺序固定为“校验 → 恢复 → 再校验”，默认只恢复数据库与附件；配置包只在
整机灾难重建时加 `--with-config` 显式恢复。不存在通用 `--force`。

保留策略（`prune_backups.py`，默认 dry-run）：

- 每日 7 天；每月 1/15 日保留过去 3 个自然月（含跨年）；
- `pre_change` 最近 2 份且不删当前回滚点；
- beta 最近 2 份；release 最近 3 个 + 所有被引用者；
- `annual` 在合规期限确认前永不自动删除；
- 最后一份已验证快照始终保留。

```bash
python3 scripts/prune_backups.py --root /home/biochm/BCLRM --env prod
python3 scripts/prune_backups.py --root /home/biochm/BCLRM --env prod --execute
python3 scripts/prune_backups.py --root /home/biochm/BCLRM --releases --execute
```

## 4. 升级演练

演练必须先有已验证快照，再恢复到临时目录，用 8700 起的空闲端口启动目标
release，执行 `runtime_cli check → migrate → check → smoke`，报告写入
`logs/rehearsals/` 与 `logs/cron_status.json`。8501/8601 永不被占用。

```bash
python3 scripts/rehearse_upgrade.py --root /home/biochm/BCLRM \
  --env prod --release /home/biochm/BCLRM/releases/0.8.19.1
```

`--no-server` 仅用于离线排查；真实演练必须让服务启动并通过健康检查。
失败时清理临时目录并以退出码 3 结束；`--keep` 可保留现场供排查。

## 5. beta 重建与修复

- `release` 模式：要求 prod 已短停（`--prod-stopped`）且指定 prod 冷备
  （`--cold-backup`）；恢复快照到 beta、清除 `mobile.base_url`、重置独立
  凭据、灌入 fixture、显式迁移。
- `repair` 模式：只处理 beta，**不得停 prod**，使用最近已验证快照。

```bash
# 先 dry-run
python3 scripts/beta_reset.py --root /home/biochm/BCLRM --mode release \
  --cold-backup <prod 冷备 id> --prod-stopped
python3 scripts/beta_reset.py --root /home/biochm/BCLRM --mode release \
  --cold-backup <prod 冷备 id> --prod-stopped --execute

python3 scripts/beta_reset.py --root /home/biochm/BCLRM --mode repair --execute
```

fixture 位于 `fixtures/beta_edge/<schema_version>/seed.py`，只含合成数据，
`BETA-` 前缀且幂等。超级管理员使用强随机初始密码，其他账号使用一次性密码；
密码只在终端打印一次，不写 manifest/日志。`reset_manifest.json` 只记录快照、
版本、fixture 和账号数量。

注意：当前 person 表没有持久化的 `must_change_password` 列，重置后会记录
`flag_persisted=false` 并在输出中告警；首次登录强改密需应用侧配合完成。

## 6. prod 部署与回滚

部署流程固定为：预检 → 停服 → 冷备并校验 → 用目标 release 显式迁移 →
schema 校验 → 切 `current_prod` → 启动 → 只读冒烟。任何一步失败都会保持
停机、恢复冷备、切回旧指针并做旧版冒烟；恢复失败则保持停机并保留现场。

预检要求：`acceptance/<version>.json` 有非 AI 验收人与签字；四库 schema
map 与 release 一致；最近演练成功；prod 版本低于候选且候选未在 prod 用过；
beta 与候选同版本同 release 同 artifact；`git merge-base --is-ancestor`
成立；release 已登记；磁盘充足；8501 未被占用（真实 systemd 模式）。

```bash
# 1) 预检（只读）
python3 scripts/deploy_prod.py --root /home/biochm/BCLRM \
  --repo /path/to/BCLRM/git-repo --version 0.8.19.1

# 2) 维护窗口内执行；unit 已安装时使用默认 systemctl 停/起
python3 scripts/deploy_prod.py --root /home/biochm/BCLRM \
  --repo /path/to/BCLRM/git-repo --version 0.8.19.1 --execute
```

`--no-systemd`、`--skip-http-health` 只供自动化测试；真实部署不得使用。

回滚：

```bash
# 默认 dry-run；目标版本与快照默认取 deployments/prod.json
python3 scripts/rollback_prod.py --root /home/biochm/BCLRM

python3 scripts/rollback_prod.py --root /home/biochm/BCLRM \
  --to 0.8.18.1 --snapshot <冷备> \
  --confirm-prod --service-stopped --execute
```

`--legacy` 是首次上线前的占位接口，仅接受已存在的 legacy 目录与
`legacy_manifest.json`，工具不会创建该目录。数据恢复使用 merge 方式，只替换
数据库与附件，保留 legacy 代码。

> **生产库现状（2026-10-28 负责人确认）**：`/home/biochm/Reagent-manager/db`
> 四库里，只有 `person`（人员）、`chemical_info`（化学品信息）、
> `controlled_list`（管控化学品名录）三张表是正式台账；其余业务表的内容一律是
> 测试数据，不具有保全价值。因此 Stage 2 首次切换不需要为其它表做数据核对：
> legacy 恢复后可以只保留这三张表的数据，其余清空再切指针。清空前仍要留一份
> 冷备——"不需要"和"不可恢复"是两件事；清空后用
> `scripts/check_consistency.py` 和 `runtime_cli.py smoke` 复核一遍再对外开服。

## 7. 状态检查与故障处理

```bash
python3 scripts/release_status.py --root /home/biochm/BCLRM --check
python3 scripts/release_status.py --root /home/biochm/BCLRM --verify-artifacts
```

状态输出两轨版本、指针、artifact 哈希、schema map、观察期、祖先关系，并按
四整数比较版本。`--check` 在门禁不满足时返回 2。

故障处理顺序：

1. 看 `logs/cron_status.json`、`logs/rehearsals/` 与
   `deployments/<env>.json` 的失败阶段。
2. 半程迁移（`schema_migrations` 存在 running 记录）时禁止继续备份/部署，
   按 4.2 节恢复到升级前冷快照，不得断点续跑。
3. 备份哈希/完整性失败：保留现场，用 `verify_backup.py` 定位文件；不要手工
   改 manifest 绕过校验。
4. 第二副本失败必须显式告警；根分区低于 10 GiB 警告、低于 5 GiB 拒绝新
   release/备份。
5. 恢复失败不得开放服务，保留现场并通知负责人。

## 8. 定时任务一览

| timer | 时间 | 动作 |
|---|---|---|
| `bclrm-backup-daily` | 每日 02:15 | prod 热备 + 第二副本，保留 7 天 |
| `bclrm-backup-semimonthly` | 每月 1/15 02:45 | 从已验证每日备份复制，保留 3 个自然月 |
| `bclrm-backup-beta` | 每日 02:30 | beta 热备，保留 2 份 |
| `bclrm-backup-annual` | 每年 01-01 03:30 | 短停 prod 做年度冷存，永不自动删除 |
| `bclrm-rehearse-weekly` | 每周一 04:00 | 恢复 + 升级演练，报告写 `logs/` |

所有 timer 均 `Persistent=true`，补跑错过的时间点。启用/停用由负责人执行：

```bash
systemctl --user list-timers 'bclrm-*'
systemctl --user status bclrm-prod.service
journalctl --user -u bclrm-prod.service -n 100 --no-pager
```
