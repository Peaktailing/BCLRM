# BCLRM 部署与运维说明

本文是 Stage 0B 发布/备份工具链的运行手册，对应
`docs/环境隔离与发布规划_执行版.md` 的 D01–D22。所有命令默认只读或 dry-run；
真正改生产必须显式加 `--execute`，prod 还必须同时具备 `--confirm-prod` 与
`--service-stopped`。

- 部署根：`/home/biochm/BCLRM`
- prod：`current_prod -> releases/<version>`，`127.0.0.1:8501`
- beta：`current_beta -> releases/<version>`，`127.0.0.1:8601`
- 运行时：Python **3.10.12**，每个 release 自带 `.venv`
- 事实源：`release.json` + `releases-index.json` + `deployments/<env>.json`
- 退出码：`0` 成功；`2` 预检/契约不满足；`3` 执行阶段失败

> 本阶段只交付工具、unit/timer 模板和测试，不启用、不启动任何 unit，也不触碰
> 现有 `/home/biochm/Reagent-manager` 生产进程。

## 1. 首次准备（Stage 2 前由负责人执行）

1. 确认 `python3 --version` 为 `3.10.12`，根分区可用空间不低于 5 GiB。
2. 建立目录、备份盘与符号链接（env 文件不得含明文密码）：

   ```bash
   # 主备份在 /data（sda3 ext4）；根分区只留符号链接
   sudo mkdir -p /data/bclrm
   sudo chown -R biochm:biochm /data/bclrm
   mkdir -p /home/biochm/BCLRM/{releases,data,config-backups,env,acceptance,deployments,logs,wheelhouse,ops}
   chmod 700 /home/biochm/BCLRM/env
   # env/prod.env、env/beta.env 由负责人按 3.2 节填写：
   # BCLRM_ENV / BCLRM_DATA_DIR / BCLRM_RELEASE_FILE / BCLRM_MOBILE_UI=0
   ```

3. **主备份卷加密（LUKS2 文件容器）**：`/data/bclrm/vault.img` 保存全部
   主备份，挂载点为 `/data/bclrm/vault`；`/home/biochm/BCLRM/backups`
   符号链接指向 `/data/bclrm/vault/backups`。密钥文件
   `/etc/bclrm-vault.key` 仅 root 可读（0400），**不得进入 git、日志或
   备份清单**。首次创建（只做一次）：

   ```bash
   sudo dd if=/dev/urandom of=/etc/bclrm-vault.key bs=64 count=1 status=none
   sudo chmod 400 /etc/bclrm-vault.key
   sudo truncate -s 150G /data/bclrm/vault.img   # 可按需扩大
   sudo chmod 600 /data/bclrm/vault.img
   sudo cryptsetup luksFormat --type luks2 --batch-mode \
     --key-file /etc/bclrm-vault.key /data/bclrm/vault.img
   sudo cryptsetup open --key-file /etc/bclrm-vault.key \
     /data/bclrm/vault.img bclrm-vault
   sudo mkfs.ext4 -q -L bclrm-vault /dev/mapper/bclrm-vault
   sudo mkdir -p /data/bclrm/vault
   sudo mount /dev/mapper/bclrm-vault /data/bclrm/vault
   sudo chmod 755 /data/bclrm/vault
   sudo mkdir -p /data/bclrm/vault/backups /data/bclrm/vault/code
   sudo chown -R biochm:biochm /data/bclrm/vault/backups /data/bclrm/vault/code
   sudo chmod 700 /data/bclrm/vault/backups /data/bclrm/vault/code
   ln -sfn /data/bclrm/vault/backups /home/biochm/BCLRM/backups
   ```

   开机解锁/挂载由 root 单元负责（`deploy/systemd-root/`）：

   ```bash
   sudo install -m 0644 deploy/systemd-root/bclrm-vault.service \
     /etc/systemd/system/bclrm-vault.service
   sudo install -m 0644 deploy/systemd-root/data-bclrm-vault.mount \
     /etc/systemd/system/data-bclrm-vault.mount
   sudo systemctl daemon-reload
   sudo systemctl enable --now bclrm-vault.service data-bclrm-vault.mount
   findmnt /data/bclrm/vault
   ```

   卷未挂载时 `/data/bclrm/vault` 是 root 拥有的空目录，应用用户无权写入，
   备份会显式失败，**不会**静默退回明文落点。密钥只在本机 root 分区：
   根盘与 `/data` 同时损坏时，用异地明文归档恢复，再重建新卷与新密钥。
   扩大容量：先卸载并 `cryptsetup close`，`truncate` 扩大 `vault.img`，
   再 `cryptsetup resize bclrm-vault`、`resize2fs`、重新挂载。

4. 异地归档目标为 `ph@210.45.37.13:/mnt/external_hdd/ph/DatabaseBackup`；
   `ssh ph@210.45.37.13` 必须免密可用。远端不可达时备份 unit 失败，并把
   原因写入 `logs/offsite_status.json`，不静默跳过。异地归档按负责人决定
   **保持明文**（兜底副本），主备份由上述 LUKS 卷负责加密。
5. 部署运维脚本（仓库更新后需重新复制；unit 调用的是部署副本）：

   ```bash
   mkdir -p /home/biochm/BCLRM/ops/deploy
   cp scripts/offsite_sync.py /home/biochm/BCLRM/ops/offsite_sync.py
   cp scripts/daily_maintenance.py /home/biochm/BCLRM/ops/daily_maintenance.py
   cp deploy/offsite.py /home/biochm/BCLRM/ops/deploy/offsite.py
   chmod +x /home/biochm/BCLRM/ops/offsite_sync.py /home/biochm/BCLRM/ops/daily_maintenance.py
   ```
6. 部署 unit 时只复制到用户目录，不自动 enable：

   ```bash
   mkdir -p ~/.config/systemd/user
   cp systemd/user/*.service systemd/user/*.timer ~/.config/systemd/user/
   systemctl --user daemon-reload
   ```

   需要开机自启时由负责人决定是否 `loginctl enable-linger biochm` 并
   `systemctl --user enable --now bclrm-prod.service`。beta、每日维护与
   演练 timer 同理，均由负责人逐项确认后再启用。

## 2. 构建不可变 release

```bash
python3 scripts/build_release.py \
  --root /home/biochm/BCLRM \
  --repo /path/to/BCLRM/git-repo \
  --version 0.8.19.1 \
  --sha <完整40位sha>
```

构建行为：

- 只从 git 归档**已跟踪文件**；断言 `docs/用户使用手册.md`、
  `.streamlit/config.toml`、非空 `assets/` 必须存在。
- 由当前 3.10.12 解释器生成 `payload/requirements.lock`，并收集离线
  wheelhouse；先查本地 pip 缓存与 `--wheelhouse-cache`，缺失时才联网。
  `--offline` 下缺 wheel 直接失败并列出缺失项。
- 计算 payload 树哈希（路径 + 内容 + 可执行位，符号链接按目标字符串），
  写 `releases/<version>/release.json`。字段固定为 version、git_sha、
  artifact_sha256、python_version、requirements_lock_sha256、
  schema_versions、built_at；**不含 channel**。
- 版本号必须是四段纯数字且全局不可复用；`releases-index.json` 或已有
  目录命中即拒绝，即使目录已被保留策略清理。
- 最后按 lock 建 `.venv`。`--skip-venv` 只允许测试使用，真实发布禁止。

构建成功后检查：

```bash
python3 scripts/release_status.py --root /home/biochm/BCLRM --verify-artifacts
```

## 3. 备份

四库使用 SQLite online backup API，库在前、附件在后；附件包记录文件数、
sha256 与索引引用，索引指向的文件缺失即整次备份失败，多余物理文件只记为
孤儿。每份快照包含四合一 manifest、逐文件哈希、user_version、行数、关键
聚合与 schema 快照，并在落盘后自校验。主备份全部存放在 LUKS2 加密卷
`/data/bclrm/vault` 内（符号链接仍是 `/home/biochm/BCLRM/backups`）。

### 3.1 每日 05:00 自动流程

`bclrm-maintenance.timer` 每日 05:00 触发 `bclrm-maintenance.service`，
由 `ops/daily_maintenance.py` 串行执行（固定顺序，可用
`systemctl --user start bclrm-maintenance.service` 手动重跑）：

1. 停 `bclrm-prod.service`，确认 inactive 且 8501 释放；
2. `backup.py --kind daily --mode cold --service-stopped`；
3. 校验新快照；按保留策略轮换（每日 7 天、1/15 日档 3 个自然月等），
   再校验全部保留快照；
4. 生成代码 git bundle（含未提交 diff 与清单）到加密卷 `code/`；
5. 重启 prod 并等待健康端点；
6. 服务恢复后做异地同步（不占停服窗口）。

该流程**绝不清理业务表**；清表是人工操作，不属于任何 timer。unit 的
`ExecStopPost` 兜底：只要脚本结束时 prod 未运行就拉回。任一步失败时
prod 仍会重启，失败详情写入 `logs/maintenance_status.json` 并让 unit
失败。全部通过约 5 秒停服；异地同步在服务恢复后进行。

### 3.2 手工命令

```bash
# 每日热备（手动；timer 使用停服冷备）
python3 scripts/backup.py --root /home/biochm/BCLRM \
  --env prod --kind daily --mode hot --source manual

# 备份后归档到异地（手工热备要补跑）
python3 /home/biochm/BCLRM/ops/offsite_sync.py \
  --root /home/biochm/BCLRM --env prod

# 升级前/回滚冷备：调用方必须先停服，并显式声明
python3 scripts/backup.py --root /home/biochm/BCLRM --env prod \
  --kind pre_change --mode cold --service-stopped --source manual

# 半月档从最近已验证每日快照复制
python3 scripts/backup.py --root /home/biochm/BCLRM --env prod \
  --kind semimonthly --copy-latest-from daily --source timer

# 代码备份（独立于每日流程）
git -C /home/biochm/WorkBuddy/2026-10-21-14-45-03/repos/BCLRM \
  bundle create /tmp/BCLRM.bundle --all
```

### 3.3 异地归档规则

- 每份快照打成 `env/kind/<snapshot>.tar.gz`，存放在
  `/mnt/external_hdd/ph/DatabaseBackup`（`ph@210.45.37.13` 的 40T 外置存储）。
- 远端根目录只保留一个 `SHA256SUMS.txt`，内容是当前全部归档的相对路径与
  sha256，可直接 `sha256sum -c`；不写表头。
- 本地按保留策略删掉的快照，其远端归档与清单行在下一次同步时一起删除；
  某类本地一份不剩时跳过该类清理并告警，避免挂载丢失时误删远端。
- 上传先写 `.partial` 再改名，落盘后回读 sha256 比对；清单同样原子替换。
- 暂存归档写到 `/data/bclrm/tmp/offsite`，不占根分区。
- **主备份加密、异地明文**：主备份位于 LUKS2 卷内；异地归档按负责人决定
  保持明文压缩包，作为整机/密钥同时丢失时的兜底副本。
- 代码 bundle 与快照不同步到异地；代码的异地副本以 git 远端
  (`git@github.com:Peaktailing/BCLRM.git`) 为准，本地 bundle 保留 90 天
  （至少保留最新 2 份）。

目录为 `backups/<env>/{daily,semimonthly,pre_change,annual}`；beta 只用
`daily`。`--dry-run` 只打印计划，`--json` 输出机器可读摘要。成功后更新
`backups/<env>/last_verified.json` 与 `logs/cron_status.json`。

校验与恢复：

```bash
python3 scripts/verify_backup.py --snapshot /home/biochm/BCLRM/backups/prod/daily/<id>
python3 scripts/verify_backup.py --root /home/biochm/BCLRM --env prod --latest

# 先 dry-run 看目标与动作
python3 scripts/restore.py --root /home/biochm/BCLRM \
  --snapshot <快照> --env prod --target /home/biochm/BCLRM/data/prod/restored

# prod 真正恢复：目标必须是 data/prod 下的绝对路径，先停服
python3 scripts/restore.py --root /home/biochm/BCLRM \
  --snapshot <快照> --env prod --target /home/biochm/BCLRM/data/prod \
  --confirm-prod --service-stopped --replace --execute
```

恢复顺序固定为“校验 → 恢复 → 再校验”，默认只恢复数据库与附件；配置包只在
整机灾难重建时加 `--with-config` 显式恢复。不存在通用 `--force`。

保留策略（`prune_backups.py`，默认 dry-run）：

- 每日 7 天；每月 1/15 日保留过去 3 个自然月（含跨年）；
- `pre_change` 最近 2 份且不删当前回滚点；
- beta 最近 2 份；release 最近 3 个 + 所有被引用者；
- `annual` 在合规期限确认前永不自动删除；
- 最后一份已验证快照始终保留；
- 远端归档镜像本地保留结果：本地删掉后，远端归档与清单行在下次同步时清除。

```bash
python3 scripts/prune_backups.py --root /home/biochm/BCLRM --env prod
python3 scripts/prune_backups.py --root /home/biochm/BCLRM --env prod --execute
python3 scripts/prune_backups.py --root /home/biochm/BCLRM --releases --execute
```

## 5. beta 重建与修复

- `release` 模式：要求 prod 已短停（`--prod-stopped`）且指定 prod 冷备
  （`--cold-backup`）；恢复快照到 beta、清除 `mobile.base_url`、重置独立
  凭据、灌入 fixture、显式迁移。
- `repair` 模式：只处理 beta，**不得停 prod**，使用最近已验证快照。

```bash
# 先 dry-run
python3 scripts/beta_reset.py --root /home/biochm/BCLRM --mode release \
  --cold-backup <prod 冷备 id> --prod-stopped
python3 scripts/beta_reset.py --root /home/biochm/BCLRM --mode release \
  --cold-backup <prod 冷备 id> --prod-stopped --execute

python3 scripts/beta_reset.py --root /home/biochm/BCLRM --mode repair --execute
```

fixture 位于 `fixtures/beta_edge/<schema_version>/seed.py`，只含合成数据，
`BETA-` 前缀且幂等。超级管理员使用强随机初始密码，其他账号使用一次性密码；
密码只在终端打印一次，不写 manifest/日志。`reset_manifest.json` 只记录快照、
版本、fixture 和账号数量。

schema v2 起 `person.must_change_password` 已落库，重置会写入 `1`，登录后
改密成功即清零；`reset_manifest.json` 记录 `flag_persisted` 供核对。只有
降级到 v2 之前的库时才可能出现 `flag_persisted=false` 并告警。

## 6. prod 部署与回滚

部署流程固定为：预检 → 停服 → 冷备并校验 → 用目标 release 显式迁移 →
schema 校验 → 切 `current_prod` → 启动 → 只读冒烟。任何一步失败都会保持
停机、恢复冷备、切回旧指针并做旧版冒烟；恢复失败则保持停机并保留现场。

预检要求：`acceptance/<version>.json` 有非 AI 验收人与签字；四库 schema
map 与 release 一致；最近演练成功；prod 版本低于候选且候选未在 prod 用过；
beta 与候选同版本同 release 同 artifact；`git merge-base --is-ancestor`
成立；release 已登记；磁盘充足；8501 未被占用（真实 systemd 模式）。

```bash
# 1) 预检（只读）
python3 scripts/deploy_prod.py --root /home/biochm/BCLRM \
  --repo /path/to/BCLRM/git-repo --version 0.8.19.1

# 2) 维护窗口内执行；unit 已安装时使用默认 systemctl 停/起
python3 scripts/deploy_prod.py --root /home/biochm/BCLRM \
  --repo /path/to/BCLRM/git-repo --version 0.8.19.1 --execute
```

`--no-systemd`、`--skip-http-health` 只供自动化测试；真实部署不得使用。

### 6.1 首次切换（Stage 2 legacy 路径）

`deploy_prod.py` 的预检假定已有 `current_prod`，因此首次上线必须手工走
legacy 路径；预检、演练、验收记录仍然全部复用：

1. 窗口内停旧实例。本机旧实例是**系统级** unit，需要 sudo：
   `sudo systemctl stop reagent-manager.service`，并执行
   `sudo systemctl disable reagent-manager.service`，避免重启后与
   `bclrm-prod.service` 抢 8501。
2. 冷复制旧代码、可用 `.venv`、`db/`、`attachments/` 到
   `legacy/prod-<旧 git sha>/`；`legacy_manifest.json` 的 `copy_mode` 改为
   `cold`。legacy 不识别 `BCLRM_DATA_DIR`，回滚数据只放回它自己的目录。
3. 把旧库与附件冷复制到 `data/prod`。附件索引若引用不存在的文件，先清掉
   这些悬空行（只删索引，不动文件），再跑 `check_consistency.py`。
4. `backup.py --env prod --kind pre_change --mode cold --service-stopped`
   生成回滚快照，并 `verify_backup.py` 复核；随后
   `ops/offsite_sync.py --env prod` 归档到异地。
5. 用 `0.8.17.1` 的 release 执行 `runtime_cli.py migrate`（prod 口径）与
   `check`；迁移前 `check` 因 schema 落后失败属预期。
6. `switch_pointer(prod, 0.8.17.1)` → 启动 `bclrm-prod.service` → 健康检查
   `127.0.0.1:8501` → `runtime_cli.py smoke`（只读）。
7. 写 `deployments/prod.json`：`status=deployed`、`first_switch=true`、
   `previous` 记旧 sha 与 legacy 目录、`rollback_snapshot` 记第 4 步快照。
8. 安装但**不 enable** `bclrm-prod-legacy.service`（仅 8501），只在首次
   回滚时由负责人启动。旧目录、legacy 副本与快照保留 ≥1 周。

回滚：

```bash
# 默认 dry-run；目标版本与快照默认取 deployments/prod.json
python3 scripts/rollback_prod.py --root /home/biochm/BCLRM

python3 scripts/rollback_prod.py --root /home/biochm/BCLRM \
  --to 0.8.18.1 --snapshot <冷备> \
  --confirm-prod --service-stopped --execute
```

`--legacy` 是首次上线前的占位接口，仅接受已存在的 legacy 目录与
`legacy_manifest.json`，工具不会创建该目录。数据恢复使用 merge 方式，只替换
数据库与附件，保留 legacy 代码。

> **生产库现状（2026-10-28 负责人确认）**：`/home/biochm/Reagent-manager/db`
> 四库里，只有 `person`（人员）、`chemical_info`（化学品信息）、
> `controlled_list`（管控化学品名录）三张表是正式台账；其余业务表的内容一律是
> 测试数据，不具有保全价值。因此 Stage 2 首次切换不需要为其它表做数据核对：
> legacy 恢复后可以只保留这三张表的数据，其余清空再切指针。清空前仍要留一份
> 冷备——"不需要"和"不可恢复"是两件事；清空后用
> `scripts/check_consistency.py` 和 `runtime_cli.py smoke` 复核一遍再对外开服。

## 7. 状态检查与故障处理

```bash
python3 scripts/release_status.py --root /home/biochm/BCLRM --check
python3 scripts/release_status.py --root /home/biochm/BCLRM --verify-artifacts
```

状态输出两轨版本、指针、artifact 哈希、schema map、观察期、祖先关系，并按
四整数比较版本。`--check` 在门禁不满足时返回 2。

故障处理顺序：

1. 看 `logs/maintenance_status.json`、`logs/cron_status.json`、
   `logs/offsite_status.json`、`logs/rehearsals/` 与
   `deployments/<env>.json` 的失败阶段。每日维护的停服、冷备、校验、
   轮换、代码备份、重启各步骤都带耗时与错误原因。
2. 半程迁移（`schema_migrations` 存在 running 记录）时禁止继续备份/部署，
   按 4.2 节恢复到升级前冷快照，不得断点续跑。
3. 备份哈希/完整性失败：保留现场，用 `verify_backup.py` 定位文件；不要手工
   改 manifest 绕过校验。
4. 异地归档失败必须显式告警；根分区低于 10 GiB 警告、低于 5 GiB 拒绝新
   release/备份；主备份盘 `/data` 的可用空间需单独监控（371 GiB，当前占用
   不到 1%）。
5. 加密卷未挂载时备份会以“加密备份卷未挂载”失败：
   `sudo systemctl status bclrm-vault.service data-bclrm-vault.mount`；
   密钥文件 `/etc/bclrm-vault.key` 缺失或损坏时，用异地明文归档恢复数据，
   再按 1 节重建卷与新密钥。不要把密钥复制到 `/data` 或仓库。
6. 恢复失败不得开放服务，保留现场并通知负责人。

## 8. 定时任务一览

| timer | 时间 | 动作 |
|---|---|---|
| `bclrm-maintenance` | 每日 05:00 | 停 prod → 冷备 → 校验/轮换（3 个月半月档）→ 代码 bundle → 重启 → 异地同步 |
| `bclrm-backup-beta` | 每日 02:30 | beta 热备 + 异地归档，保留 2 份 |
| `bclrm-backup-annual` | 每年 01-01 03:30 | 短停 prod 做年度冷存 + 异地归档，永不自动删除 |
| `bclrm-rehearse-weekly` | 每周一 04:00 | 恢复 + 升级演练，报告写 `logs/` |

每日维护替代了旧的 `bclrm-backup-daily` 与 `bclrm-backup-semimonthly`
timer：每日档在停服窗口内冷做，老旧的每日/半月 unit 已从仓库移除。
所有 timer 均 `Persistent=true`，补跑错过的时间点。停服窗口只覆盖备份与
校验，异地同步在 prod 恢复后执行。启用/停用由负责人执行：

```bash
systemctl --user list-timers 'bclrm-*'
systemctl --user status bclrm-prod.service
systemctl --user start bclrm-maintenance.service   # 手动立即执行
journalctl --user -u bclrm-maintenance.service -n 100 --no-pager
```
