# 手机取证与瓶身二维码（v0.8.16）

## 为什么是「取证」，不是「支持上传附件」

账本上「某人领走 30 g 乙醇」证明的是**有人点了按钮**。它不证明料真的出了库、
瓶子交到了手上。出事之后要回答的问题往往是：

- 那天是谁来拿的？
- 拿的是不是这一瓶？
- 归还的时候瓶里还剩多少、瓶身有没有破损？

这三个问题都只能靠现场照片答。所以这一块的设计目标不是「让附件能传上去」，
而是**给每一笔借出/归还留一个物理现场的快照，并且和单号绑死**。

## 三个环节

```
                         ┌─ 固定/当前地址 → 码里是 URL → 手机相机扫，直接进页面
贴码（库存页打印） ──→ 扫 ─┤
                         └─ 短码 → 页面里的摄像头扫，或手输

进页面（/m?bottle=xxx）──→ 认瓶 ──→ 找这一瓶的在办工单 ──→ 拍照 ──→ 挂到单上
```

### 1. 码里放什么

| 配置 | 码内容 | 怎么扫 | 依赖 |
|---|---|---|---|
| 固定地址（系统设置） | `http://192.168.1.10:8601/m?bottle=202610230001` | 手机系统相机 / 微信扫一扫 | 手机能直连这个地址 |
| 跟随当前访问地址（打印时选） | `http://localhost:8501/m?bottle=202610230001` | 手机系统相机 / 微信扫一扫 | 手机也走同一条 SSH 隧道/入口 |
| 短码 | `BCLRM:3:202610230001;64-17-5;202706;乙醇` | 页面内的 `BarcodeDetector` 或手输 | 浏览器支持；不依赖网络 |

**两条都支持，是因为纸质标签会用两年，而服务器 IP 半年就变一次。** 同一个
货架上一定同时贴着多种码（早期贴的和近期贴的），所以 `parse_fields()` 四种
都认（URL / v3 / v2 / v1），页面拿到哪种都能用。

**URL 只带瓶号，短码带三个字段。** 这不是不一致，是两种模式的前提不同：

- URL 模式的前提是**能联网**。联网就该问系统——页面会把 CAS、入库日期、
  剩余量、保管人、在办工单一次列全，码里再抄一份只是多 26 字节。
- 短码模式的价值恰恰是**不依赖系统活着**。瓶子漏了、仓库着火了、或者被人
  从柜子里拿错，用任意扫码工具（微信、系统相机）扫一下就能读出「这是什么
  物质、哪天进来的」——那正是断网、宕机、或者根本没登账号的时候。

短码的三个字段用分号分隔（`;`）：瓶号是 12 位数字，CAS 形如 `64-17-5`，
日期是 `2026-10-23`，都不含分号，不会歧义。**空字段保留位置**——CAS 缺失
（混合物、自制试剂、未建档的历史瓶）时写 `;;` 而不是省掉，否则按位置取值
会把日期读成 CAS；尾部空段可以省，`;CAS` 与 `;CAS;` 等价。

`BCLRM:3:` 里的 `3` 是载荷版本，不是二维码版本。v3 在 v2 的
「瓶号;CAS;入库日期」后面加了效期和试剂名；老标签（v1/v2/URL）照样能扫出
瓶号，解析入口不需要分支。将来再加规格，同样从尾部追加。

### 1.1 码能装多少：容量表是陷阱，物理尺寸才是约束

二维码的容量表很好查：版本 40、L 级纠错、字节模式能装 **2953 字节**。但那
是 177×177 = 31329 个模块，按手机能对准的最小模块 0.4 mm 印出来要 **71 mm
见方**——比 500 mL 试剂瓶还宽。**能装下和扫得动是两件事**，中间隔着一条
物理约束：

```
单个模块边长(mm) = 打印边长(mm) / (模块数 + 静区)
```

经验阈值：**≥0.45 mm** 手机一扫即中；**0.30–0.45 mm** 得凑近、光线要好；
**<0.30 mm** 小瓶标签上基本扫不动（模块本身不到 1 像素，相机的去马赛克会
把它抹平）。

按本系统 19.5 mm 见方的标签（480 px 宽标签的 48%，300 dpi）实测：

| 版本 | 模块数（含静区） | 每模块 | M 级容量 | 判定 |
|---|---|---|---|---|
| 1 | 23 | 0.85 mm | 14 B | 好（只有瓶号的短码 20 B） |
| 2 | 27 | 0.72 mm | 26 B | 好 |
| 3 | 31 | 0.63 mm | 42 B | 好 ← **当前三字段短码 39 B** |
| 4 | 35 | 0.56 mm | 62 B | 好（当前 URL 46 B；再加效期 50 B） |
| 6 | 43 | 0.45 mm | 106 B | 好 ← **舒适区上限** |
| 7 | 47 | 0.42 mm | 122 B | 勉强 |
| 10 | 59 | 0.33 mm | 213 B | 勉强 ← **天花板** |
| 12 | 67 | 0.29 mm | 287 B | 扫不动 |
| 15 | 79 | 0.25 mm | 412 B | 扫不动 |
| 40 | 179 | 0.11 mm | 2331 B | 只能印在 A4 上 |

结论：**这块标签的现实预算约 100 字节（舒适）、200 字节（上限）**。
`utils/qr_label.fit()` 就是把这笔账算给页面看——「实时库存 → 打印瓶身
二维码标签」在生成前会显示版本、模块数和每模块毫米数，超了就提示
「缩短地址」或「放大打印」，而不是等贴到瓶上才发现扫不出。

**为什么不在码里塞满信息。** 能塞的那几百字节，塞进去的都是会变的
（剩余量、保管人、位置），印上去就过期；真正不变的（瓶号、批次、效期）
本来就在瓶身标签上用字印着，扫一次查库比印在码里更准。**码是钥匙，不是
档案柜**——这也是短码短到 22 字节的原因。

### 1.2 一维条码在这里不合适

瓶上可能还有厂商贴的 Code 128 条码（本系统的 `get_by_barcode` 认它，
用于入库时直接带出物质信息）。但自印标签不用一维码，三个原因：

| | Code 128 | QR |
|---|---|---|
| 装相同内容的面积 | 约 1 cm 高 × 3–5 cm 宽（一条） | 1.3 cm 见方 |
| 手机扫 | 要正对、要横向铺满取景框，抖动就断 | 任意角度，有的相机免对焦 |
| 装一条 URL | 太长，条码会又宽又密，小瓶贴不下 | 48 字节毫无压力 |

一维码只适合「一串 12–13 位数字」这种身份号，且必须用激光扫描枪读得最稳；
它能装的字数是 20–40 个数量级，**装不下一条 URL**。所以厂商条码保留为
「入库免手输」的便利，自印标签一律用二维码。

### 1.3 SSH 隧道 / 端口转发怎么办

当前测试环境的访问方式是 **SSH 上服务器、再用 22 端口转发**，浏览器里看到的
地址通常是 `http://localhost:8501`，不是服务器内网 IP。这带来两个结论：

**照片上传本来就走当前路由。** 上传是 Streamlit 组件把文件发给「当前这个
页面所在的连接」，没有任何地方拼绝对地址。所以只要手机能打开这一页，拍照、
上传、看原图都能用，不需要为了端口适配改业务代码。

**页内扫码也跟当前路由走。** 扫码器读到一个瓶号后，跳转目标由
`st.context.url` 反推（`app_root_of()`），也就是「你此刻正在用的入口」：
直连就是内网 IP，隧道就是 `localhost:8501`，反向代理挂在 `/lims` 下就保留
`/lims`。系统设置里的固定地址**只影响印在瓶子上的二维码**，不影响页内扫码。

**打印标签时多了一个选项。** 「实时库存 → 打印瓶身二维码标签」里「码里放
什么」可以选：

| 选项 | 适用 | 代价 |
|---|---|---|
| 固定地址（系统设置） | 手机能直连服务器，标签长期有效 | 地址变了要重打 |
| 跟随当前访问地址 | SSH 隧道、临时端口、反向代理 | 只对同一条入口的设备有效；换端口/换机器要重打 |
| 短码（离线可读） | 不想到处配地址，或要保留离线可读信息 | 只能页内扫码或手输 |

隧道模式下打印出来的码是 `http://localhost:8501/m?bottle=...`。它能在手机上
打开的前提是**这台手机也做了同样的本地端口转发**（例如手机上的 SSH 客户端
把 8501 转到 localhost:8501）。没开隧道的手机打不开，这不是二维码的问题，
而是它根本连不到服务器。若要让全实验室的手机直接扫，必须有一条手机可达的
入口（内网直连或 HTTPS 反向代理），而那会触发安全测评，属于部署决策。

> 顺带一个好处：`localhost` 属于浏览器的安全上下文例外，所以隧道模式下
> `getUserMedia` 不会被 HTTP 拦截，安卓 Chrome 的页内扫码反而能用；iPhone
> 仍然因为没有 `BarcodeDetector` 而只能系统相机扫或手输。

### 2. 为什么页内扫码不引 jsQR

实验室是内网，很多机器出不了外网。引一个 CDN 脚本的结果是「页面看着正常、
扫码永远不出结果」——这比没有扫码更糟，因为人会把时间花在反复对着码晃。

所以只用浏览器原生的 `BarcodeDetector`，不支持就老实说「请用系统相机或手输」，
**不摆一个装样子的取景框**。手输框始终在，它不是备用方案，是等价的入口。

### 3. 照片挂在哪

```
ref_type = borrow_order      （所有取证照片都挂在借用工单上）
ref_id   = order_number      （工单号）
category = evidence_borrow   （发料现场）
         = evidence_return   （回库、剩余量、瓶身）
```

**不按瓶挂**：同一瓶一年可能借十次，按瓶挂照片分不清哪张属于哪次交接。

**不用归还单号**：一笔归还动作在系统里可能产生多条明细记录（一单多瓶），
而照片是「这一次交接」的整体。挂工单号才能一张照片覆盖整笔，也不会因为部分
归还产生一堆只有一张图的孤儿单。两个阶段用 `category` 区分，互不覆盖——同一
张单既有发料照片又有回库照片，正是要的。

## 压缩

手机原图 4–8 MB、4000×3000。一次取证四五张，直接存有三个后果：附件目录一
学期涨到几十 G、内网 Wi-Fi 上传要等半分钟（人就不拍了）、页面翻照片卡到没法用。
而核对「这瓶是谁拿的」根本不需要 1200 万像素。

四件事：EXIF 方向转正 → 长边压到 1280 → 重编码 JPEG → 另存一张 480 px 缩略图。

实测（一张 4032×3024、3.5 MB 的手机原图，内容偏碎，属偏高值）：

| 参数 | 体积 | 说明 |
|---|---|---|
| 原图 | 3545 KB | 手机直出 |
| 1600 / q82 | 460 KB | 第一版 |
| 1280 / q75 | 235 KB | **现在的默认** |
| 1024 / q72 | 127 KB | 标签小字开始吃力 |
| 480 / q72 | 17 KB | 缩略图 |

**页面传的是缩略图，不是原图**，这一条比继续降分辨率有用得多：

| | 一屏 6 张照片 |
|---|---|
| 照片墙读原图 | 1.4 MB，手机上等两三秒，滚动卡 |
| 照片墙读缩略图 | 100 KB，一闪即出 |

原图仍然留在盘上（长边 1280，标签上的批号看得清），要看细节在页面上选一张
「看原图」即可，也能单独下载。缩略图按命名规则 `<原名>.thumb.jpg` 存在主文件
旁边，**不进附件索引**——索引一行代表「一张照片」，缩略图登记进去会让照片计数
翻倍、「必拍是否已满足」跟着错。读不到缩略图（老照片）自动回落到原图。

**转正必须在缩放之前**：EXIF 的 90° 会让宽高互换，先缩放再转正会把长边算错。
**必须在服务端做**：客户端压缩（canvas）能省流量，但换个浏览器或直接调接口就
绕过了。**压失败不丢证据**：一张处理不了的照片仍然存下来，只标注「没压成」。
取证这件事不能因为压缩失败就把证据扔了。

长边与质量都是 `system_config` 里的旋钮（`evidence.photo_max_edge` /
`evidence.photo_quality`），超管在「系统设置 → 现场取证」改，改完立刻生效，
不用发版。调到 1024 能再省一半，代价是台账整页的照片会糊。

## 必拍是开关，不是代码

有的实验室要求每次借出都拍，有的只在管控试剂上要求，还有的嫌麻烦只留痕不强制。
这件事不该由代码定，所以开关进 `system_config`，超管在「系统设置 → 现场取证」改。

`evidence_service.require()` 是**唯一读取口**——页面校验和服务端校验必须看同一
个值，否则会出现「界面显示必填但能提交」或者「界面没提示却提交不了」。

**空值回落到出厂默认，不当成「关」**。配置项被误清空一次，取证要求就静默消失，
这种事故没人会发现。

**允许「之前传过的抵账」**：现场信号差，人可能先拍照存相册、回头再补传；也可能
管理员先发料、事后统一补。同一笔交接只要有证据就不该被卡。

## 落点：为什么只做 BCLRM

Lims 是能力沙盒，界面只有一套；这一批的交互与它的 `Capture` 通用采集是两回事：

| | `Capture`（Lims） | 取证（BCLRM） |
|---|---|---|
| 触发 | 人在货架边想到什么就记下 | 一笔具体的借出/归还发生了 |
| 产物 | 待结构化的原料，等助手转成记录 | 已定型的物证，挂在单号下 |
| 归属 | 只有本人可见 | 单的经办人与管理员都能查 |

硬并过去会让两个语义混在一个模型里。等 Lims 并入 `domain/` + `capabilities/`
之后，取证能力（`business/evidence_service.py` + `utils/photo_utils.py` +
`utils/qr_label.py`）可以整体搬过去，不需要改语义。

## 操作手册

**管理员第一次配置：**

1. 「系统设置 → 现场取证」按部署方式二选一：
   - 手机能直连：填「手机访问地址」，形如 `http://192.168.1.10:8601`。
     只写 `192.168.1.10:8601` 也可以，保存时会自动补 `http://`；路径只填到
     端口，不要带 `/m` 以外的内容。
   - 只走 SSH 隧道：可以留空，打印标签时选「跟随当前访问地址」。
2. 按实验室口径决定「借出必须拍照」「归还必须拍照」。
3. 「实时库存 → 打印瓶身二维码标签」批量输入瓶号，选「码里放什么」，
   打包下载 ZIP，打印贴上。**改过入口或地址后，旧标签不会自动更新，需要重打。**

**教师/管理员现场办：**

1. 手机相机扫瓶身二维码 → 直接进「手机取证」页。若此时还没登录，会先显示
   登录页；登录成功后仍停在这一瓶，不会跳回首页。
2. 页面显示这一瓶的余量、保管人、位置，以及它现在的在办工单。
3. 点「补拍」→ 拍照 → 上传。两个阶段按工单状态自动选。
4. 上传成功/部分失败会在页面顶部给提示；照片墙两列显示缩略图，点下方
   「看原图」可核对批号并下载原图。

**电脑端办借还时：**

「批准并执行领用」和「提交归还」上方各有一个上传框，可以直接从电脑传；
也可以只办业务、回头在手机上按工单号补拍。

## 已知限制

| 限制 | 原因 | 影响 |
|---|---|---|
| 页内扫码要安全上下文 | `getUserMedia` 在 HTTP 下被浏览器拦；HTTPS 与 `localhost` 例外 | 内网 HTTP 只能靠系统相机扫 URL 码或手输；SSH 隧道走 localhost 时可用 |
| iOS 无 `BarcodeDetector` | 原生接口只有安卓 Chrome 系有 | iPhone 只能系统相机扫或手输，隧道模式下也一样 |
| 隧道标签按设备生效 | 码里写的是 `localhost:8501`，只有同样做了端口转发的手机能打开 | 同事手机没开隧道就打不开；要全员可用必须有手机可达入口 |
| 换入口要重打标签 | 二维码是静态的，入口变化它不会跟着变 | 固定地址/隧道端口变化后，旧标签全部失效 |
| HEIC 不处理 | Pillow 默认不认，需 `pillow-heif` | iOS 在 `accept="image/jpeg"` 下会转 JPEG，正常路径碰不到 |
| 没有离线队列 | 现场没信号就传不上去 | 得回到有网的地方按工单号补拍 |
| 登录态 30 分钟 | `SESSION_TIMEOUT_MINUTES`，且没有持久登录 cookie | 现场放久了要重新登录；关标签页即丢失 |
| 直接 `streamlit run` 可能只监听 localhost | `.streamlit/config.toml` 已补 `address = "0.0.0.0"`，但旧部署/反向代理仍需确认 | 手机连不上时先查监听地址与防火墙 |
